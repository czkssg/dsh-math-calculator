# 更新日志

本项目遵循 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) 与 [语义化版本](https://semver.org/lang/zh-CN/)。

## [2.2.0] — 2026-11-03

按三份实测反馈修缺陷。**重点：这一版修的都是「结果看着正常但其实是错的」**——
它们比直接报错更危险，因为看不出来。

分两批：前半是三份文档里已实测确认的真问题；后半是对三份文档逐条复核后，
把「没做」与「做了却看不出来」分开处理的结果。

### 修复

- **小数值被定点截断，误差可达 5.8%**（实测最危险的一条）。

  `σ = 5.670374419e-8` 在 8 位小数下曾显示成 `0.00000006` ——
  相对误差 5.8%，而数字看着完全正常。判据原本是「会不会四舍五入成 0」，
  但 `5.67e-8` 并不归零，只是**错了**，后者远比归零隐蔽。

  现在判据改为**相对误差超过万分之一就自动改用科学计数法**：

  ```
  修复前  0.00000006      相对误差 5.8%
  修复后  5.67037442e-8
  ```

  同时把显示精度提示收窄成「只在真丢精度时附一句具体说明」，噪音从 10/10 降到 0/20。
  提示走独立的 `notice` 字段，**不拼进 `result`**（拼进去会让 `0.1+0.2` 变成两行，
  破坏依赖 `result` 精确相等的调用方）。

- **未定义的单字母标识符被静默当成单位**。

  ```
  rho=2035; rho*V  → 2.035 kV    ← V 被当成伏特，不报错、不警告
  rho=2035; rho*m  → 2.035 km
  rho=2035; rho*g  → 2.035 kg
  ```

  物理推演里最规范的变量名恰恰都是单字母（`m`/`V`/`W`/`T`/`g`），
  旧行为等于**在惩罚最规范的命名习惯**。

  难点：mathjs 把 `5 V`（单位）与 `rho*V`（变量）解析成**完全相同的 AST**，
  语法层无法区分，只能看上下文。现在的判据是——与已定义变量同级、或单独出现时报错；
  父节点是乘法且兄弟含数字（`5 V`）、或幂指数是数字（`s^2`）时照旧当单位。
  范围只覆盖实测确认的 20 个单字母单位，且有 13 条断言专门守「真单位用法不能坏」。

- **`integral` 静默忽略 `from`/`to`**，只回不定积分。

  静默忽略已传入的参数是最伤信任的行为。现在真的算 `F(to) − F(from)`。
  顺带修掉一个精度陷阱：定积分代入**必须用 Fraction 引擎** ——
  BigNumber 的 `1/3` 是截断小数，乘 27 回不到整数（`8.999999…`），Fraction 能得 `9`。

- **`overrides` 里拼错的 key 被静默丢弃**，公式照常出数、参数用默认值，
  结果"合理但错误"（实测曾导致一次「236 倍缺口」误判）。

  现在会点名哪些 key 已被忽略，并列出该公式的真实参数。
  判据分清：不在 params 里、**且**不在常数表里的才算错拼 ——
  `g`/`c`/`G` 是公式可引用的世界常数，拿它覆盖是合法用法。

### 新增

- **直觉写法**：`2**10`、`ln(10)`、`π`、`2 × 3`、`6 ÷ 2` 现在都可直接用。
  根因是其它 operation 内部都调了 `normalizeSource`，只有 `evaluate` 与批量路径漏了；
  归一化会跳过引号内的内容（`5 cm to "inch"` 的单位名不会被改）。
- **批量 label**：`expressions` 支持 `{label:"储耗比-中值", expr:"139e8/152e4"}`，
  解决「只有顺序号区分、一度差点引错」。回显格式为 `储耗比-中值（139e8/152e4） = 9144.73684211`。
- **`terse:true`**：只回「表达式 = 结果」，去掉标题与统计。**失败信息绝不隐藏**，有专门断言守着。

### 新增（第二轮：参数层不再静默）

- **认不出的参数名会报错，不再静默吞掉**。

  ```
   {operation:'evaluate', expression:'1+3', foo_bar_baz:123}
   修复前 → ok=true, 返回 3        ← 参数被整个吞掉
   修复后 → ok=false, unknown_argument，点名 foo_bar_baz
  ```

  这是本轮**风险最大**的一条：三份文档里提到的 `format`、`sigfigs`、`anchor` 等
  未实现的参数，以前都是「传了不报错、也不生效」——调用方以为做了，实际没做。
  与 `overrides` 里 key 拼错被丢弃是同一类问题，只是发生在顶层。

  白名单**从真实数据源派生**，不手写。踩过一个坑：第一版只从 `MathArgs` 接口取键，
  而 `starMass`/`starTemp` 等 world 顶层简写参数**不在接口里**，
  于是合法调用被自己的校验拦下（world 套件当场红）。现改为同时承认 `WORLD_KEYS`。

  刻意**不做大小写归一**：试过「`DisplayPrecision` 自动映射到 `displayPrecision`」，
  结果参数被接受却因为代码只读小写键而完全不生效——那比报错更难排查。

- **`displayPrecision: 0` 现在真的生效**（只留整数部分）。

  ```
   修复前  {expression:'22/7', displayPrecision:0} → 3.14285714   ← 0 被当成「没给」
   修复后  {expression:'22/7', displayPrecision:0} → 3
  ```

  根因是入口把 `<= 0` 当作未给，而 schema 上白纸黑字写着「0-64」。
  两处 0 的语义**刻意不同**（各有各的理由，已在两处注释里写明）：
  单次参数的 0 = 「0 位小数」，工作区 set 的 0 = 「清除固化值」。

- **语法错误现在会给括号定位，不再只说「检查括号是否配对」**。

  ```
   缺左括号 ((1+2)/3  → 「这几个左括号没有闭合: 第 1 字符；补上 1 个 ")" 即可」
   多右括号 (1+2)/3)  → 「第 8 个字符处的 ")" 没有对应的左括号；多是前面漏了一个 "("」
   并回显表达式，在下方标出每个括号的层级
  ```

  不做「自动补括号」——猜错了会把报错变成一个**算错的数**，比报错糟得多。

- **英制单位补齐**：长吨/短吨/英担/英石、BTU/therm、ft·lbf/s，
  并新增**压力量纲**（Pa/kPa/MPa/bar/atm/psi/mmHg/Torr）。

  ```
   107000 lb → 47.7679 longton     14.7 psi → 1.01353 bar
   1260000 BTU → 1.32937 GJ        760 mmHg → 101325 Pa
  ```

  实测反馈里这些系数被手打过 8 次以上——「记错数」变成「打错名」，
  后者更容易被发现。这也是文档二 P1-1 里真正可行的那一半。

- **help 补全 derivation 的 29 个子命令**（按用途分组，并注明各子命令的关键参数），
  以及**账本闭合配方**（用 `expressions` + `label` 逐项列值 + 差值，
  不做成 PASS/FAIL：差 3 与差 3% 是两种情况，压成一个布尔就全糊了）。

### 修复（输出单位归位，按用户 2026-11-06 指示）

用户原话：**「重量单位使用常见的 kg/公斤、t/吨，大数用科学计数法，
其他单位依次类推用常用的公制单位。」**

实测确认的问题：mathjs 会按数量级自动选 SI 前缀，但它**只按数量级走**，
不管现实中人说哪个词。于是：

```
  一个很大的重量 → 1 Tg（太克）    ← 现实中没人这么说
  1e6 m         → 1 Mm（兆米）     ← 没人这么说
  1e6 s         → 1 Ms（兆秒）     ← 没人这么说
```

改为**按量纲的常用单位阶梯表**（`src/format.ts` 的 `PREFERRED_UNIT_LADDER`）：

| 量纲 | 阶梯（从大到小取第一个跨过的档） |
|---|---|
| 质量 | t / kg / g / mg |
| 长度 | km / m / cm / mm / µm |
| 时间 | year / day / h / min / s |
| 功率 | GW / MW / kW / W |
| 能量 | TJ / GJ / MJ / kJ / J |
| 压强 | MPa / kPa / Pa |

效果：

```
  1e12 g      → 1e6 t        （不是 1 Tg）
  1e6 m       → 1000 km      （不是 1 Mm）
  1e6 s       → 11.57 day    （不是 1 Ms）
  2 kg * 1e6  → 2000 t
  0.5 g       → 500 mg
```

**超出最大常用档时用科学计数法配该单位**（`1e6 t`、`1e9 km`），
而不是引入更冷门的前缀。

## 三个踩过的坑（都已写成注释）

**1. `unit.value` 已经是基准单位的数值，不要再乘前缀**
第一次乘了 `prefix.value`（`2 kg` 变成 0.002 kg），
第二次乘了 baseFactor（`1 t` 变成 1e6 kg）。
两次都是「凭直觉推断第三方库内部表示」而不是实测反推 —— 教训明确。

**2. 整数绝不能为「好读」改科学计数法**
试过「≥1e15 改科学计数法」，被 **12 条断言当场打回**：
那违反本项目最硬的不变量「整数永不丢位」——
`10^20` 与 `10^20+5` 会长得一样，那是丢信息不是简洁。
大数占行宽的问题改由**批量显示补千分位**解决（纯视觉分组、不改值）。

**3. 体积刻意不做归位**
试过 L↔m³ 互换，结果 `1000 L` 变 `1 m^3` 而 `1 m^3` 变 `1000 L` ——
两者互相吞吐。体积的「常用写法」本身就不统一（水用 L、土方用 m³），
强行归位只会改掉调用方给的语义，收益为零。

### 修复（按 2026-11-06 第二份实测报告）

一份 99 层架空世界观的设定推演，约 18 次调用 / 130 余个算式。
它的 P0 是**中文量级词**——恰好是上一轮修中文单位时漏掉的一环：
单位表收了「里/丈/亩/斤」，却没收入「万/亿/万亿」。

报告作者两次把「吨」当成「亿吨」，起因就是必须手写 `/1e8`：

```
  0.591e8 * 330 / 1e3  → 19503000 (~10⁷)   被读成「1.95 万吨」，实为 1,950 万吨
  2.66e8 * 330 / 1e3 / 1e8 → 0.8778        被读成「878 万吨」，实为 8,780 万吨
```

**「两步除法」本身就是错误源**，而工具原本可以替调用方消掉这一步。

- **中文量级词 `万` / `亿` / `万亿` 现在可直接参与运算**。

  ```
  2.66亿 * 330        → 87780000000
  450 亿吨 / 31.39 亿吨 → 14.33577572   （比值无量纲）
  3万亿               → 3000000000000
  ```

  实现走**乘数展开**（`2.66亿` → `(2.66 * 1e8)`），而不是把它们注册成单位：
  单位表的机制是「factor × 基准量纲」，而量级词是无量纲乘数 ——
  硬塞进去会把「亿米」和「亿吨」搞成同一种东西。

  三个必须注意的细节（都已写成注释与断言）：
  · **长词优先**：`万亿` 必须排在 `万` 与 `亿` 之前，否则 `3万亿` 会被拆错
  · **展开后要再包一层括号**：否则 `450 亿吨 / 31.39 亿吨` 因乘除左结合变成先除再乘，
    结果带上 `Mg^2` 量纲 —— 数值对、量纲错，这种最难发现
  · **「人」「畜」在量级词后面是计数**，不是功率单位（`2.66亿人` 不能变成 `19.95 GW`）

- **数字数组不再静默全失败**。

  ```
  expressions: [0.5, 9.9, 10]
  修复前 → （空表达式）→ 跳过 ×3，成功 0
  修复后 → 0.5 = 0.5 / 9.9 = 9.9 / 10 = 10
  ```

  这是**类型错误被伪装成内容错误** —— 用户传的是合法数字，
  工具说「空表达式」，会让人去翻数据源而不是检查类型。纯数字元素现在自动转字符串。

- **非法变量键不再中止整批**。

  ```
  variables: {"P":1000, "Q":5, "人口":1}
  修复前 → ok:false，连合法的 P*330 都没算
  修复后 → P*330 = 330000 照算，notice 里点名「人口」被跳过
  ```

  这类语料的概念名几乎全是中文（人口/粮食/石料），用户第一反应就会用中文命名。
  现在合法键照常进作用域，非法的记进 notice —— **算出来的数仍然是对的**。
  不做「支持中文变量名」：那要放宽 mathjs 的词法，会引入新的歧义。

- **语法错误给子类型与位置**，不再一律说「检查括号是否配对」。

  ```
  1,000 * 2   → 「表达式里有千分位逗号，去掉即可」（旧提示说查括号，指错了方向）
  / 112.5e8   → 「运算符位置不对（第 1 个字符附近「/ 112.5」）」
  某中文*2    → 「表达式里有中文；中文单位与量级词可直接写，其它请改英文变量名」
  ```

  **顺带修掉一个很隐蔽的漏判**：这条正则原来写的是 `SyntaxError`（无空格），
  而 mathjs 报的是 `Syntax error`（有空格）——于是这类错误落到兜底分支，
  表现为「错误类型对、但没有任何 hint」。报告里 `2.66亿 * 330` 无提示就是这个原因。
  靠对照实验才揪出来（`1+*2` 有提示而 `某中文*2` 没有）。

- **质量 SI 前缀补中文量级参照**。

  ```
  2.66e8*330 kg  → 87.78 Tg（= 8778 万吨）
  ```

  「87.78 Tg」读不出「8,778 万吨」，而中文语料里这个量级就叫亿吨。
  只对「质量 × 克」这一族、且 ≥ 万吨时补 —— `1 Gg（= 1000 吨）` 那种注了等于没注。

- **大整数补千分位**（只在批量显示里，`result` 数据通道不变）。

  ```
  1e20*3 → 300000000000000000000（300,000,000,000,000,000,000） (~10²⁰)
  ```

  报告原话：「一条 21 位数字就占满一行，且位数多到无法目视核位
  ——本次我数错过一次 0 的个数。」

- **三角函数按弧度算时给一句说明**。

  ```
  sin(30)     → -0.98803162，notice 提示「按弧度；要角度请写 sin(30 deg)」
  sin(30 deg) → 0.5，不提示
  ```

  中文工程语境里 `sin(30)` 的默认读法是 30 度。按数学惯例走弧度是对的，
  但不给提示就是静默错误 —— `-0.988` 看起来像个正常数。
  判据保守：只对三角函数 + 裸数字 + 数值在 [0,360] 时提示。

### 修复（按 2026-11-06 实测报告）

一份 200 余条表达式的实测报告，**先讲自己的错、再讲工具的缺陷**，每条带可复现调用。
逐条实测后确认 6 条真缺陷，另有 3 条判断有误（未照做，理由记在评审记录里）。

- **批量求值失败时顶层 `ok` 仍是 `true`**（最严重的一条）。

  ```
  {expressions:[{label:'未定义变量', expr:'unknown_var*2'}], terse:true}
  → result 里写着「失败[unknown_symbol]」
  → ok: true        ← 失败却报成功
  → error: undefined
  ```

  报告原话：「我多次写 `if (!r.ok)` 来判断成败，得到的结果是『永远成功』
  ——因为 `ok` 永远是 `true`。」任何依赖 `ok` 的自动化流程都会把失败当成功。

  现在 `ok` 按失败数决定，并补三个结构化字段：
  `partial`（有失败但仍有可用条目）、`failed`、`succeeded`。
  刻意**不**塞 `error` —— 那是「批量里某条错」，不是「整个调用错」，
  硬塞一个会把「只有第 3 条错」读成「全部错」。

- **label 量级警告 100% 误报**（上一轮防呆层引入的回归）。

  ```
  {label:"1亿棵树日产台", expr:"1e8*25000"}
  → ⚠ label 含「亿」，若按字面读成「亿」则为 2.50e20
  ```

  `1亿棵树日产台` 是**条件描述**（以 1 亿棵树为输入），不是「结果单位是亿」。
  旧判据用 `label.includes(词)`，于是每个含量级词的 label 都会触发一条无意义警告。

  判据改为「量级词必须处在单位位置」：结尾、或紧接短单位/数量名词。
  条件描述（后面还跟一长串）一律放过。

  **同时修掉一个更隐蔽的漏报**：`年耗H2O万吨` 这类 label 里的数字是
  **化学式下标**，不是「一天产出 2 亿」那种条件。旧判据见到数字就放过，
  导致报告里「同一个错犯了四次」的原始案例全都不检查。

- **中文单位不能参与表达式运算**。

  ```
  3 km + 500 m   → 3.5 km       ✓
  1 里 + 3 米    → Syntax error ✗
  5 亩 + 100 m²  → Syntax error ✗
  ```

  两条路径的单位表没打通（`units` 认「里」「亩」，表达式不认）。

  实现走**文本归一化**而不是往 mathjs 注册中文单位 ——
  因为 `buildMath` 里刻意删掉了 `createUnit`（那是安全边界的一部分）。
  现在「数字 + 中文单位」在解析前展开成「数字 * 系数 基准单位」：

  ```
  1 里 + 3 米              → 503 m
  3 公里 + 500 米          → 3.5 km（公里优先于里，不被拆错）
  2 斤 + 300 克            → 1.3 kg
  1 丈 + 2 尺              → 3.84 m
  5 亩 + 100 m²            → 3433.33 m²
  1 时辰 + 30 分钟         → 9 ks
  ```

  顺带修掉两处相关缺陷：mathjs 不认上标（`m²` 报 Syntax error），
  现在表达式里统一换成 `m^2`；面积别名 `km2` / `m2` 也能用。

- **`units` 的代入过程有同义重复**。

  ```
  · 1 kg = 1 kg
  · 9.0000e+15 kg = 9.0000e+15 kg
  · 1 t = 1000 kg，故结果 = 9000000000000 t
  ```

  前两行是废话（源单位是基准单位时，「1 X = 1 X」什么也没说明）。
  而且它让输出**看起来有内容，其实没有** —— 这比啰嗦更值得修。
  现在按信息量分四种情况，只写有意义的步骤。

- **`terse` 对 `units` 不生效**。

  `{operation:"units", terse:true}` 原来仍返回 6 行带框。现在只回一行，
  但**保留适用域提示**（「里在周制约 415 m」这类信息被省掉，
  调用方会拿错朝代的值去写设定 —— 那比多几行更糟）。

- **英文全称别名缺失**：`ton` / `tonne` / `meters` / `metre` / `hectare` /
  `grams` / `seconds` 全不认，只认缩写。而英文文献里全称极常见。
  已在 length / mass / time / area 四个最常用量纲补齐（没有给冷门单位长别名表，
  那是每轮计费的固定成本）。

- **`expressions` 元素里的未知键被静默忽略**（本报告未提，实测发现）。

  ```
  {expressions:[{label:'a', expr:'1+1', unit:'kg/day'}]}  → ok=true，unit 被丢弃
  {expression:'1+1', unit:'kg/day'}                       → 报 unknown_argument ✓
  ```

  顶层严格拦截，元素内部不查。危险在于：将来加 `unit` / `assumption`
  这类按条参数时，它们必然写在这个位置，会被静默吞掉。
  现在该条失败并点名键名，其余条目不受影响（保持「逐条独立」的约定）。

### 新增（防呆层：在数字旁边多放一句「这个数看起来不对劲」）

来自一份 **200 余条表达式**的实测复盘。那份文档的核心结论是：

> math_execute 现在是一个准确的算术器，但还不是一个可靠的验算伙伴。
> 它给数字，不给判断 —— 所以它最该做的不是算得更准（它已经很准），
> 而是**在数字旁边多放一句「这个数看起来不对劲」**。

文档里记录的真实事故：

```
 2645.6*28*3600*8000/1e9  →  2133.41184
 调用者贴上「万吨」标签    →  以此为据指控原文「错了 10 倍」
 真相：2133 是千吨，万吨应为 /1e10 → 213.34（原文完全正确）
```

**四条年度物料全部犯同一个错、全部偏大 10 倍、全部报「成功」。**

这一版做了三件事：

**1. 量级标注** —— 裸数字旁边配 `(~10³)`

```
   年耗N2万吨 = 2133.41184 (~10³)
```

10⁰~10³ 这个日常区间不标（标了反而吵）。

**2. label 与结果的量级核对**

label 里明确写了量级词（万/亿/千…）时，比对该量级与结果本身的数量级：

```
   年发电量亿度 = 288000000 (~10⁸)     ← label 说「亿」，裸数字已到 10⁸
   ⚠ 若按字面读成「亿」则为 2.88e16，请核对换算。
```

**3. 同批次一致性比对**（文档里说「这条能一次性拦住同一个错犯了四次」）

按 label 的量级词分组，组内 ≥2 条且量级一致、与该组声称的量级差**恰好一个数量级**时才报：

```
   ⚠ 本批有 4 条 label 含「万」（=10⁴），但结果全部落在 10³ 量级
     量级与 label 声称的差 1 个数量级 —— 除数可能少除了一个 10
     （例如该用 /1e10 却用了 /1e9）
```

**判据刻意保守**：差 0（口径已对齐，如 213 万吨）不报；差 ≥2（可能是正常的大数/小数）不报。
只报「差恰好一个数量级」——那正是「千吨被当成万吨」的特征。

**4. 「成功」改为分级语义**

文档原话：「『成功 7，失败 0』会让调用者跳过复核，因为『成功』两个字读起来像『对了』。」

```
   算式全部求值成功（4 条，只表示算式无语法/符号错，不含结论正确性判断）
```

**5. terse 不许吞掉风险提示**

terse 的承诺是「省掉标题与统计」，不是省掉 ⚠。第一版把提示一起省了，
于是 terse 用户看到的是一行干净数字 —— 而干净正是最危险的。

新增 `test/guards.mjs`（23 项）。**第 4 节守「正确用例零误报」** ——
误报会让整条通道被关掉，比漏报更糟。反向对照已验证：撤掉防呆后 11 项变红。

低频段压到 120 字符内、不许出现矛盾表述、关键行为约束不许砍。

### 修复（多步计算：失败步骤的下游曾静默变「虚成功」）

批量内按书写顺序执行、前一条赋值对后一条可见 —— 这条路本身是好的。
但**一个依赖失败步骤的下游**曾经不算失败，而是被 mathjs 当成「2 b（单位）」
算出一个合法结果，批量汇总里显示为**成功**：

```
 {expressions:["a=5","b=oops*2","d=b*2"]}
 修复前   d=b*2 = 2 b          ← 合法单位结果，汇总「成功 2，失败 1」
 修复后   d=b*2 → 失败[unknown_symbol]，汇总「成功 1，失败 2」
```

根因是**两个独立缺陷叠在一起**：

1. **单位判据只看「同级有没有数字」，不看顺序**。
   mathjs 保留书写顺序：`2 b` 是 `[数字, 符号]`（单位），`b*2` 是 `[符号, 数字]`（变量）。
   旧判据一律放过，于是 `b*2` 被当成单位。

2. **赋值语句的右半部分挂在 `value` 上，而 AST 遍历只走 `args/items/content/object/index`**。
   `d=b*2` 的 AST 是 `AssignmentNode(name=d, value=OperatorNode(*))`，
   赋值右侧**整个不被判据看到** —— 所以第 1 条即使修好了也不生效。

这类「下游悄悄变成虚成功」比报错难发现得多：批量汇总里它算成功，
而结果是 `2 b` 这种看着完全正常的量。

新增 `test/multistep.mjs`（26 项）：第 3 节专守这条；第 5 节用 9 种真单位写法
守「修复不能误伤单位」（`5 V`、`9.81 m/s^2`、`s^2`、`(2+3) V`、`1/2 h` 等）。

### 新增（工作区命名变量，默认关闭）

工作区的 `variables` 字段、写入（`workspaceVariables`）、删除（`remove-variable`）、
显示（`show`）**本来都已存在**，唯独**读取路径缺失** —— 存进去的变量在计算里用不到：

```
 {action2:"set", workspaceVariables:{BTU_LB:1260000}}  → 变量 1 个      ✓ 存住了
 {expression:"BTU_LB/1000"}                            → Undefined symbol  ✗ 用不了
```

「能删不能加、加了用不了」是设计不一致，这一版把最后一环接上：

```
 workspace set useWorkspaceVariables:true   → 打开开关（逐工作区）
 evaluate BTU_LB/1000                      → 1260
 evaluate variables:{BTU_LB:999000}        → 本次参数优先，得 999
```

**默认关闭**。打开后同一表达式在不同工作区状态下结果可能不同，
会削弱「同输入同输出」——那是本项目做 hash 复现与回归对比的基础，
所以它是一个显式的、逐工作区的选择，不默认生效。
关闭时行为与未引入该功能时**完全一致**（变量仍存着，能看能删）。

**缓存必须跟着变量走**：缓存键原本只含工作区名与常数指纹，不含变量内容。
若不修，`改变量 → 再算 → 命中旧缓存 → 静默返回改之前的数`——
与文档批评过的「改常数后返回旧值」是同一类。现在变量内容进指纹：

```
 改前 BTU_LB=1260000 → 1260
 改后 BTU_LB=1055000 → 1055    ← 不是命中旧缓存的 1260
```

顺带把 `workspaceVariables` 与 `useWorkspaceVariables` 补进工具 schema：
前者此前代码支持但参数表里没有（模型看不见），属同批「可发现性」问题。

  （138.8 KB）、9 个客户端测试套件、`tsconfig.client.json`、`package.json` 的

### 新增

- **世界参数校验（三档）**：`world-params.ts` 的 `range` 此前是**纯装饰** ——
  22 处声明没有任何代码读取，实测 `planetMass=-5`、`planetRadius=0`、`albedo=5`
  都 200 OK 存进去了。新增 `src/world-validation.ts` 让范围真正生效：
  - **硬拒绝 400**：`range.hard` 且**低于下界** —— 会算出无穷/非数/负物理量
    （零半径 → 重力 Infinity、零质量 → 离心比 Infinity、零轨道 → 80 处 Infinity）；
  - **软警告 200 + `warnings[]`**：越界但仍照设定算（`planetMass=500`、`albedo=1.5`），
    消息里给出范围与代价。**上界一律走这一档** —— 「质量大得离谱」是设定自由，
    拦了就违反「不反驳用户设定」；
  - **静默接受**：在范围内。

  哪些参数标 `hard` 是**实测**出来的（逐个取极端值跑推演、统计产物里 `Infinity`/`NaN`
  个数），不是拍的。实测还暴露了探针自身的 bug：`planet.surfaceGravity` 其实是
  显示串（`'Infinity'` 字符串），只看 `typeof === 'number'` 会整片漏判。

- **`invalid` 判定档**（`dead-universe.ts`）：检出物理量非有限/为负时判 `invalid`，
  与 `dead` 分开 —— `dead` 是「死寂宇宙」这种合法设定，`invalid` 是「参数本身算不出数」。
  混在一起会让作者以为「世界设得太狠」，实际是把半径写成了 0。渲染措辞仍只讲怎么改，
  不写「错误/禁止/必须」。

- **逐颗卫星 `moons` 可存档**：`world.ts` 早已支持 `MoonSpec[]`（洛希极限/希尔球/
  相邻间距/观感），但 `moons` 不在白名单里，导致「多卫星系统」只能直接调 tool、
  存不进工作区。`ParamSpec.kind` 新增 `'array'` 与 `itemShape`，现在能存能校验。

### 修复

- **`Infinity`/`NaN` 会流到 AI**（最伤可信度的一条）：`/summary` 的
  `derived[].value` 曾是裸 `Infinity`（只有 `text` 被格式化成 `—`），
  `verdict.causes` 里也有 `"表面重力不成立：Infinity m/s²"`。AI 会当成真数字写进结语
  ——「这颗星球重力是 Infinity」。现在 `deriveAll` 用 `finite()` 统一归一化，
  `judgeDead` 的原因描述改成中文（不出现字面量），整个响应不含 `Infinity`。
- **`save-world` 的双白名单事故**：该路由曾自带一份 14 键硬编码白名单，
  而 `WORLD_PARAMS` 有 23 个基础量 —— 于是 `starClass`（「我要 G2V 恒星」）、
  `hasLiquid`、`materialStrength/Density`、`moonCount/Mass/Distance`、
  `lightPollution`、`galaxyBand` 共 9 个键被**静默丢弃**：返回 200 OK，不报错不提示。
  现在白名单只留一个真相。
- **类型静默强转**：`Number(true)===1`、`Number([])===0`、`Number(['7'])===7` ——
  `{planetMass:true}` 曾静默存成 1。现在只接受 `number` 与数字字符串，其余 400。
- **注入给 AI 的 operation 数量是旧的**：`awareness.ts` 的系统提示写「共 25 个」，
  实际 27 个（漏了 `derivation` 与 `custom`）。`integration.mjs` 的断言清单同样只有 25 个，
  现在补齐到 27 并加了**反向断言**（schema 里不许有清单外的名字）。
- **`npm run preflight` 因 UI 移除而崩溃**：它仍在 `readFileSync('lib/client.js')`，
  文件已删 → `ENOENT`，装机前自检直接非零退出。改为反向断言（客户端产物确实不存在、
  无 `dsh.client`、无 `exports["./client"]`、无 `tsconfig.client.json`），
  与 `test/integration.mjs` 第 5 节互为印证。
- **`tsconfig.json` 仍排除 `src/client.ts`**：文件早不存在，排除项清掉。

## [2.0.0] — 2026-10-24（内部定稿，未发布）

### 能力

- **计算内核**：BigNumber 64 位高精度求值、符号微积分（求导/积分/化简/展开）、
  解方程与线性系统、矩阵（秩/行列式/迹/奇异值/零空间/逆）、统计与概率分布、
  回归、ODE（RK4）。
- **UI（令牌化）**：左栏「全局管理」与右栏「本工作区工作台」共用同一套宿主设计令牌
  （`--dsw-alias-*` / `--dsw-font-*` / `--dsw-radius-*`），无写死颜色；
  **新建工作区即生成同名数据表**（`<工作区名>.json`，含常数/公式/地点/变量四张子表），
  切换工作区后右栏自动跟随。
- **公式库 342 条**，每条带**三轴标签**：
  `layer`（离最底层规则的远近：基本/数学/导出/经验/工程/约定）、
  `domains`（学科领域，多标签）、`frequency`（**主角视角感知频率**）。
  检索：`freq:` / `layer:` / `domain:` / `symbol:` / `keyword`。
- **两级公式扩展**：全局公式包（`$DSH_HOME/math-calc/formula-packs/global.json`，写盘即生效）
  + 工作区临时公式；新增时校验 id、表达式可解析、**符号必须已定义**（拼错变量当场拒绝）。
- **符号消歧**：同一字母不同含义（`m` = 质量/米）可查 `symbol:m@质量`。
- **常数推演**：无量纲优先（α/μ/α_s/α_G）、尺度阶梯、单位旋钮与物理改动分离、矛盾清单。
- **世界推演**：恒星（质光/寿命/宜居带/α 敏感度）→ 气候 → 天空配色 → 卫星系统 →
  化学窗口与生命硬否决 → 跨模块一致性检查 → 经验系数可信度标注。
- **UI**：左侧入口 = **全局管理**（所有工作区：创建/切换/删除，常数表、公式表、设置）；
  右侧边栏页签 = **本工作区工作台** —— 工作区切换器、本区数据表（常数/公式/地点/变量）、
  **开关**（提示档位、公式启停）、**管理**（变量与地点的增删）。
  左栏切换工作区后右栏**自动跟随**（同一 client bundle 内的订阅 + 宿主 `sidebarRight` store）。

### 工程质量

- 全量 **41 套 / 1716 项**测试；含确定性、真机宿主契约、**对抗性兼容性**（敌意 ctx、
  服务抢占、全局污染、数据损坏）与**客户端注册契约**回归。

### 修复（相对内部早期版本）

- **客户端注册 id 必须等于包名**：此前用 `<包名>-client`，宿主按包名查找不到模块，
  导致桌面端每次启动都报 `import failed` 并致命退出。
- **客户端入口幂等**：宿主会重放 bundle，重复注册会抛错并升级为致命错误。
- **peer 依赖接受 prerelease**：`>=0.1.0 <0.3.0` 不接受 `0.1.7-rc.2`，改为 `>=0.1.0-0 <0.3.0`。
- **工作区切换自动落盘**：此前切到不存在的工作区只产生内存对象，`current` 会指向幽灵工作区。
- 工作区创建兼容 `name` 参数（此前只认 `workspace`，误报「不能是 default」）。
