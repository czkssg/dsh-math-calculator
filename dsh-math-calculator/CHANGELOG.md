**这个缺口的价值不在「多一个变量」，而在「过程建模最常用的一类式子之前根本写不出来」。**

## [2.3.18] — 2026-11-10

补**复合路径（compounds）**—— 这是「把公式连成体系」这件事的最后一块。

### 它解决什么问题

22 条链各自只覆盖一步到十几步。但真实推演里最难的**不是算某一步，而是跨 4 条链**：

```
  「有铁矿」能不能变成「有帝国」？
  材料链 → 产能链 → 财政链 → 军事链
```

这些路径在图上**本来就连通**（图直径 5 跳、单一连通分量），但读者要自己一段段拼。
现在登记下来了：

```
  formulas query="sys:compound"               → 7 条复合路径清单
  formulas query="sys:compound:mine-to-empire" → 逐跳展开，含接点公式与说明
```

### 7 条路径

| id | 路线 | 回答什么 |
|---|---|---|
| `mine-to-empire` | 材料→产能→财政→军事 | 「有铁矿」能否变成「有帝国」 |
| `water-to-army` | 水利→食物→财政→军事 | 灌溉能力最终能养多少兵 |
| `info-to-capacity` | 信息→财政→产能 | 治理半径决定产能上限 |
| `material-to-fly` | 材料→结构→交通 | 这个世界的材料能否造出飞行器 |
| `energy-to-output` | 能源→产能 | 产量瓶颈卡在燃料还是工艺 |
| `quantum-to-industry` | 量子→信息控制→产能 | 能否做出电子工业 |
| `queue-to-output` | 排队→产能 | 再加一个人有没有用 |

### 设计决定：只登记「经过哪几条链」，不复制公式与参数

```
  复制 → 公式改了、链条调整了，复合路径不跟着变 → 必然漂移
  引用 → 每次从 FORMULA_SYSTEMS 现查 → 永远与代码一致
```

所以一条路径只写 `via`（链的顺序）+ `hops`（每跳用哪个接点作为提示）+ `purpose`。
具体参数去查那条链。

### 最关键的一条：不许登记假路径

第一版我写了 `sys-climate → sys-food`（用 `gdd_accumulated` 当接点），
**实测发现这两条链之间根本没有任何真实接点** —— 那条路径是我拼出来的。

所以 `traceCompound` 每次都回到 `FORMULA_SYSTEMS` 现查证据，依次尝试：

1. 本链声明的 `bridges`（且接点公式必须真在目标链的步骤里，否则是死链）；
2. 对方链声明的 `bridges`（反向）；
3. 两链 `steps` 里的**共用公式**（弱一些但也是真实连接）。

三条都不成立就判 `ok: false`。

测试里还加了一条**反向对照**：构造一条不存在的路径（`sys-astronomy → sys-military`），
`traceCompound` 必须报断。若实现里漏了判断永远返回 true，这条会红 ——
否则第 3 节的全部「每跳连通」断言都会假通过。

### 顺手删掉的假路径

`civ-sustainability`（光→气候→食物→财政）—— 气候与食物之间没有接点，
按上面的规则**直接删掉，不是硬凑一个**。假关系比没有关系更糟。

补化学工程单元操作 11 条。这批回答的是**「能不能量产酸、碱、药」** —— 之前库里只有实验室化学。

### 缺口：23 条化学公式全是「实验室」，没有一条「工厂」

```
  已有：摩尔、浓度、滴定、pH、溶度积、能斯特、阿伦尼乌斯、吉布斯能
  没有：反应器尺寸、转化率、传质、萃取级数、精馏板数、吸附穿透、干燥
```

区别不是「多几条」，而是能不能回答：

```
  实验室问题：这杯溶液 pH 多少（已有）
  工业问题：  这个反应釜一天能产多少、要多大、几级萃取够（全空）
```

### 本批的组织方式：围绕「放大」而不是「单元操作名称」

化学工程的核心是 scale-up，而放大问题的三条主线是：

```
  停留时间 τ = V/Q       → 决定装置**体积**
  级数（萃取/精馏板）     → 决定装置**高度**
  传质系数 K·a           → 决定设备能多快达到平衡
```

所以 11 条全按这三条组织。

### 新增 11 条，最实用的六条

| 公式 | 关键结论 |
|---|---|
| `reactor_conversion_first_order` | **指数饱和**：kτ=3→95%、kτ=6.9→99.9% —— 「最后几个百分点最贵」 |
| `cstr_conversion` | 同 kτ 下 **75% vs 95%** —— 返混的代价，工业用多釜串联的原因 |
| `distillation_min_stages` | α 2.2→1.2，板数 **7.5→32（4.3 倍）**；α→1 时发散=共沸物蒸不出来 |
| `extraction_stages` | K_D 0.5→5，级数 **11.4→2.6** —— **选对溶剂比多加级数重要** |
| `crystallization_supersaturation` | **过饱和度越大晶体越细**；想要大晶体必须慢冷却（数天到数周） |
| `heat_exchanger_area_chemical` | **放大困境**：放热 ∝L³ 而面积 ∝L² —— 体积放大 10 倍时单位体积散热降到 1/2.15 |

### 放大困境：本批最有价值的一条

```
  反应放热量 ∝ L³，换热面积 ∝ L²
  → 放大后单位体积的散热能力按 L 下降
  → 「小试能控温、中试就飞温」不是操作问题，是几何决定的
```

而放热剧烈的反应（硝化、氧化、聚合）**放大时最危险** —— 这正是化工事故的典型模式。

补流体力学与空气动力 13 条。这批回答的是**「能不能飞、船能多快」** —— 之前库里根本答不了。

### 缺口：能算「水多深压多大」，算不了「这东西能不能飞」

```
  已有（10 条）：静水压、浮力、流量、雷诺数、弗劳德数、达西损失、泵功率、孔口出流
  没有：伯努利、升力、阻力、边界层、Stokes 沉降、马赫角、波阻
```

### 本批的主轴：两种阻力必须分开

```
  压差阻力  ∝ v²   高速主导（drag_force）
  粘性阻力  ∝ v    低速主导（viscous_drag_stokes）
```

这不是「同一公式的两个近似」，是**两种不同的物理机制**。混用会得出「船越快越省力」这种荒谬结论。
所以测试专门验这两条标度：速度翻倍时，压差阻力必须 ×4、粘性阻力必须 ×2。

### 新增 13 条

| `drag_force` | C_D 量级：流线型 0.04~0.1、球 0.47、平板 1.28、**鱼 0.01** |
| `viscous_drag_stokes` | 低速 ∝ v；**沉降速度 ∝ r²** —— 粗砂瞬沉、黏土悬浮数天 |
| `terminal_velocity_sphere` | 1mm 砂 3.6 m/s；**1µm 黏土 3.6e-6 m/s（1 米深要 77 小时）** |
| `lift_force` | 升力 ∝ v² —— **人力扑翼机要 700W 持续输出，人能维持的只有 200~400W** |

## [2.3.15] — 2026-11-10

补热机循环 11 条。这批的价值不是「多了几个效率公式」，而是**把卡诺从「唯一答案」降回「上限」**。

### 缺口：库里有 17 条热力学，但全是「物性」不是「循环」

```
  已有：理想气体、热容、潜热、导热、卡诺效率、卡诺 COP、熵变
  没有：Rankine、Otto、Diesel、Brayton、联合循环、实际制冷 COP
```

后果很直接：**卡诺只是天花板，而真实机器从来达不到它。**
只有引入循环形式，才能回答「这台蒸汽机效率 8% 是差还是已经接近极限」。

### 本批最重要的结论：两条技术树从这里分叉

```
  卡诺/Rankine   效率只由**温度**决定    → 提效率必须提蒸汽温度（材料问题）
  Otto/Brayton   效率只由**压缩比**决定  → 提效率必须提压缩比（爆震/结构问题）
```

这个区别不是设计偏好，是**公式结构决定的**。所以测试直接验结构性质：
改温度时 Otto 效率必须不变、改压缩比时 Rankine 效率必须不变。这比验数值更能守住真正的知识。

### 新增 11 条

| 公式 | 关键结论 |
|---|---|
| `rankine_efficiency` | 3MPa 饱和算例 **34.4%**（同温限卡诺 39.6%，达到 87%） |
| `otto_efficiency` | r=8→56.5%、r=10→60.2%；**公式里没有温度项** |
| `diesel_efficiency` | 优势是压缩比能到 18，代价是**rc 越大效率越低**（rc=3 时 58.9% < rc=1.5 时 65.6%） |
| `brayton_efficiency` | 优势不在效率而在**功率密度**（无往复件）—— 喷气式的基础 |
| `combined_cycle_efficiency` | 60% 不是提高单机，是**用燃机废热再驱动汽轮机**；高于任一单机但低于两者相加 |
| `condenser_vacuum_gain` | **「把排气冷下来」与「把蒸汽烧热」等价** —— 冷却塔不是为环保，是为真空 |
| `refrigeration_cop_real` | 空调 COP≈18、冷冻≈3.6 —— **同一台机器差 5 倍**，只因温差 |
| `heat_pump_cop` | COP_供暖 = COP_制冷 + 1；室外 −10℃ 时骤降（热力学决定） |
| `cooling_load` | **渗透热往往与围护热同量级** → 「密封门窗」比「加厚墙」更有效 |
| `thermal_storage_capacity` | 水比热是岩石 5.2 倍 —— 蓄热用水是数值决定的；一次相变≈升温 80K |
| `rankine_reheat_gain` | 再热不只是提效率，更是**防止末级叶片被水滴打坏** |

### 修掉的采样陷阱（这次改的是采样器，不是公式）

`formulas-all.mjs` 用描述关键词填参数，导致三处 non_finite：

```
  condenser_vacuum_gain   三个温度全填 300 → 分母 0
  diesel_efficiency       cutoff_ratio 填 1 → 分母 (rc−1)=0
  rankine_efficiency      三个焓全填 10 → 分母 0
```

## [2.3.14] — 2026-11-10

补分布矩与可靠性 11 条。这批不是「再加一类公式」，而是补 `dist` operation 的**分布缺口**。

### 缺口在哪

`dist` 只支持 normal / binomial / poisson / exponential 四种。而冷战到千禧年
工程与可靠性最常用的另外几种**连基本矩都算不出来**：

```
  Weibull      疲劳/寿命分析的标准分布（k 是它的全部价值）
  对数正态     收入、粒径、修复时间 —— 乘法过程的结果
  卡方         方差检验、拟合优度
```

### 分工：这批与 dist 不是重复

```
  dist      → 某一点上的概率密度/累积（需要完整参数）
  本条一批  → 这个分布长什么样（均值/方差/中位/失效率/存活率）
```

即：**先用这批判断该用哪个分布、参数大概多少，再用 dist 算点值。** 分工写进了 desc。

### 新增 11 条

| 公式 | 关键结论 |
|---|---|
| `weibull_reliability` | **t=λ 时恒有 36.8% 存活**（与 k 无关）—— 这才是「特征寿命」的定义 |
| `weibull_failure_rate` | 浴盆曲线**不是一条曲线，是三段不同的 k** |
| `weibull_mean_life` | 均值永远 < 特征寿命（k=2 时只有 0.886 倍） |
| `lognormal_median_vs_mean` | 均值/中位 = exp(σ²/2)，**必然 ≥1** —— 「平均收入」为何无描述力 |
| `lognormal_mean` / `lognormal_variance` | 方差含两个指数项，**比均值敏感得多**（σ 1→2，均值 ×4.5，方差 ×627） |
| `poisson_mean_variance` | E=Var，真正的用途是**模型选择**：方差≫均值即有聚集 |
| `binomial_mean_variance` | 相对误差 ∝ 1/√n —— 「10 个里 7 个痊愈=70%」经不起追问 |
| `exponential_mean_life` | 无记忆的真正含义：旧的不比新的更容易坏 |
| `chi_square_mean_variance` | E=k，Var=2k；用于「偏差是否只是随机波动」 |
| `coefficient_of_variation` | 唯一能跨单位比离散度的指标：50±5 与 500±50 都是 0.1 |

### 最实用的两条推论（写设定时能直接用）

**① 维护策略只看 k：**

```
  k<1  早期失效  → 换新的反而更容易坏，「磨合」比「更换」有意义
  k=1  随机失效  → 换不换一样，定期更换纯属浪费
  k>1  磨损失效  → 到点就换能避免失效，定期维护才划算
```

**② 精度门槛可以用 CV 自查：**

```
  CV<0.1  精密（需要模具与质检）
  0.2~0.4 手工常态
  「50±1g」= CV 0.02 → 这已经是量产级工艺，不是作坊能做的
```

### 新增：储备损耗（A10）

N = N₀·(1−r)^t。**「存两年还够不够」的唯一算法。**

```
  谷仓   r=0.04  存 2 年剩 92.2%   存 5 年剩 81.5%
  露天   r=0.15  存 3 年剩 61.4%   存 5 年剩 44.4%
```

**为什么必须是指数而不是线性**：损耗作用在**当时的剩余量**上。写成 `N₀−r·N₀·t`
会在 t > 1/r 时算出负数 —— 而损耗永远拿不光存量。这是最容易犯的错，因为 t 小时两者几乎重合。

**可操作推论：损耗率减半的收益大于储量翻倍。** 而且后者受地力限制，前者不受。
测试里守了这条：3 年差距约 31 个百分点，5 年拉大到 37 个百分点。

### 新增：干燥时间（A6）

t = −ln[(M_f−M_e)/(M_0−M_e)]/k。形式与牛顿冷却、电容放电同源（速率正比于超出量），
所以天然给出「先快后慢」。

```
  新谷 25% 晒到 14%（k=0.30）→ 6.2 天
  同样目标改阴干（k=0.10）   → 18.7 天
  想干到 12.1%（只差一点）   → 16.2 天
```

**关键推论：目标定得越低，时间不是线性增加而是发散**（趋近平衡含水率时 t → ∞）。
这就是「安全含水率 13~14%」是工程红线、而不是越干越好的数学原因。

与 `case_depth`、`sintering_porosity` 是同一条教训：**提速率比延时间有效**。

### 新增：公差叠加（P12）

σ_装配 = √(n·σ²) = √n·σ。**单件差也能装出高精度。**

```
  5 件 ±0.05：最坏叠加 ±0.25，统计叠加 ±0.112 —— 差 2.2 倍
  20 件 ±0.05：最坏 ±1.00，统计 ±0.224        —— 差 4.5 倍
```

比值 √n，所以件数越多优势越大 —— 这是「互换性装配」的经济价值来源。

**这条不是无条件的，desc 与测试都守了失效条件**：前提是误差独立且随机。
同一个人、同一台设备、同一批料做出的 n 件，误差同向偏（共因），
此时必须退回线性叠加 Σσᵢ。判据：


### 土壤养分平衡：连作能不能持续

N(t+1) = N(t) + 投入 − 吸收 − 淋失。三档实测（每公顷每年 kg N）：

```
  传统连作（草木灰回田）  15 − 60 − 20 = −65
  施绿肥/沤肥            80 − 60 − 25 = −5
  轮作休耕年             40 − 10 − 15 = +15
```

**连作每年亏 65，库存 2000 只够 31 年** —— 这是「为什么要休耕」的定量理由。

配套一条 `nutrient_sustainable_input`：令净变化为零的最低投入 = 吸收 + 淋失 = 80，
与连作的 15 相比缺口 65，正是要开垦新地或休耕的原因。

最有用的推论：**减少淋失等于增加投入**。黏土比沙土少淋 30~40 kg，
效果相当于多施同量肥，而改土成本远低于年年买肥。

### 投资回本期：M1 的通用化

T = 投入 / 年节省。三条实测锚点与设定集吻合：

```
  铁斧     40/20  = 2 年
  第二座窑  480/120 = 4 年
  终极墙    336/24 = 14 年
```

与库里已有的互补：`roi` 给回报率、`npv_simple` 给折现净值，
而回本期给的是**时间尺度** —— 它更容易判断，因为你只需要知道「我活不活得到那天」。

判据不是「回本期越短越好」，而是**回本期 < 你还打算干活的年数**。
这就是为什么乱世里长回本周期的工程没人做。

化工单元与误差传播 4 条，公式库 516 → 520。

```
  误差传播     → 谁主导精度 → 钱该花在哪     （通用，不归链）
```

### 蒸馏：富集倍数随浓度下降

y = αx/(1+(α−1)x)。α=2.2 时实测：

```
  x=0.05 → 富集 2.08 倍
  x=0.30 → 1.62
  x=0.80 → 1.12
```

**这就是「为什么蒸馏器要做成塔」的定量理由** —— 单锅只能提 2 倍，
10%→70% 约需 6~8 块理论板。desc 里同时标了共沸点限制：乙醇-水在 95.6% 共沸。

### 结晶：收率由「溶解度差」而非「降温幅度」决定

实测锚点（硝石提纯）：100g 水配 246g KNO₃（100℃ 饱和），冷到 20℃ 析出 214g、收率 87%。

关键推论：降温更狠收益递减（20℃→0℃ 只多析出 19g），
**而蒸发一部分水比继续降温有效得多** —— 海盐晒盐正是走这条路。

反向对照守住了：NaCl 溶解度几乎不随温度变（39.1→35.7），此法析出 <5g，无效。

### 坯体收缩：掺熟料是减收缩的主要手段

总收缩 = 干燥 6% + 烧成 4% = 10%（普通陶土），瓷可达 17%。
**每掺 10% 熟料约减 1~1.5 个百分点** —— 熟料已收缩过，不再收缩。

### 误差传播：真正价值是「找出谁主导」

σ_y = |y|·√(Σ(wᵢ·σᵢ/xᵢ)²)

实测案例：ρ=m/V，m=100±0.1g、V=50±0.5mL → ρ=2.000±0.020，
其中**体积贡献 99%、质量只占 1%** —— 于是结论明确：改进天平毫无意义，要换更准的量筒。

**这条故意不归入任何链**：它服务于所有计算，挂到某一条链上反而误导。测试里有断言守着。

## [2.3.5] — 2026-11-08

### 修复（precision 调低后结果被截成 0，却 ok=true + notice 空）

反馈原话：「precision=20 时结果静默变成 0，`ok` 依然是 `true`，`notice` 为空」。

```
  (10^20+1)-(10^20), precision=20  →  0    ok=true, notice 空
```

根因不是「没检查」，而是**检查只看了输出**：结果被截成 0 后只有 1 位，
判据「整数位数 > precision」立刻放行 —— **越离谱的结果越容易逃过检查**。

修法：改成**看输入而不只看输出**。表达式里出现 `10^n`（n ≥ precision）或长整数串时，
无论结果多小都提示：

```
  notice: 表达式里出现了超出 precision=20 能表示的大数，
          结果可能已失真（本次结果 0）。需要精确值请用 precision:64…
```

临界点是 `>=` 不是 `>`：`10^20` 是「1 后跟 20 个零」= **21 位**，precision=20 装不下它。
第一版写成 `>`，恰好漏掉了这个案例。

### 修复（label 括号内的「输入条件」被当成「结果单位」）

反馈原话：label「煤储量/年耗 可支撑年数(2万吨)」被警告「若按字面读成万则为 1.47e8」，
而作者真实意思是「**2 万吨煤**能支撑多少年」—— 括号里是输入口径，不是结果单位。

判据：括号内含「数字 + 量级词 + 单位词」（`2万吨`、`300万件`）→ 判为输入条件，放过；
括号内只有「量级词 + 单位词」（`亿`、`万吨`）→ 仍按结果单位处理。

反向对照守住了：`年发电量（亿）` 仍正常报警，`1亿棵树日产台`、`年耗H2O万吨` 仍不误报。

### 新增（符号带单位运算，与公式量纲校验）

用户要求「计算要带单位和物理意义」，例子是 `V*T=L`、`V=10m/s`、`T=1s` → `L=10m`。

```
  variables:{V:'10 m/s', T:'1 s'}, expression:'V*T'   →  10 m
  V='30 里/h', T='2 时辰'                              →  60 km
```

修复前 `V*T` 返回 `"V T"` —— 带单位的字符串值被 `bignumber()` 解析失败后整个丢弃，
单字母随即被当成单位符号相乘。现在失败后回退到「按表达式求值」。

公式的参数也带上单位了 —— 库里每个参数的描述本来就写着单位（`s → "位移 m"`），
以前只用于显示：

```
  overrides:{s:'10 km', t:'1 h'}    → 2.77777778 m/s，并交代换算过程
  overrides:{s:'10 kg', t:'1 s'}    → 量纲不符报错（以前静默按数字算）
  overrides:{s:10, t:1}             → 照旧接受（不猜 10 是米还是公里）
```

**同体系折算**：输入用了里/时辰时，主结果仍保持 SI（那是公式参数的口径），
但补一行折算 —— `60 里 / 2 时辰` 会给出 `约 30 里/时辰`，可直接心算核对。

## [2.2.0] — 2026-11-03

按三份实测反馈修缺陷。**重点：这一版修的都是「结果看着正常但其实是错的」**——
它们比直接报错更危险，因为看不出来。

分两批：前半是三份文档里已实测确认的真问题；后半是对三份文档逐条复核后，
把「没做」与「做了却看不出来」分开处理的结果。

### 修复

- **小数值被定点截断，误差可达 5.8%**（实测最危险的一条）。

  `σ = 5.670374419e-8` 在 8 位小数下曾显示成 `0.00000006` ——
  相对误差 5.8%，而数字看着完全正常。判据原本是「会不会四舍五入成 0」，
  但 `5.67e-8` 并不归零，只是**错了**，后者远比归零隐蔽。

  现在判据改为**相对误差超过万分之一就自动改用科学计数法**：

  ```
  修复前  0.00000006      相对误差 5.8%
  修复后  5.67037442e-8
  ```

  同时把显示精度提示收窄成「只在真丢精度时附一句具体说明」，噪音从 10/10 降到 0/20。
  提示走独立的 `notice` 字段，**不拼进 `result`**（拼进去会让 `0.1+0.2` 变成两行，
  破坏依赖 `result` 精确相等的调用方）。

- **未定义的单字母标识符被静默当成单位**。

  ```
  rho=2035; rho*V  → 2.035 kV    ← V 被当成伏特，不报错、不警告
  rho=2035; rho*m  → 2.035 km
  rho=2035; rho*g  → 2.035 kg
  ```

  物理推演里最规范的变量名恰恰都是单字母（`m`/`V`/`W`/`T`/`g`），
  旧行为等于**在惩罚最规范的命名习惯**。

  难点：mathjs 把 `5 V`（单位）与 `rho*V`（变量）解析成**完全相同的 AST**，
  语法层无法区分，只能看上下文。现在的判据是——与已定义变量同级、或单独出现时报错；
  父节点是乘法且兄弟含数字（`5 V`）、或幂指数是数字（`s^2`）时照旧当单位。
  范围只覆盖实测确认的 20 个单字母单位，且有 13 条断言专门守「真单位用法不能坏」。

- **`integral` 静默忽略 `from`/`to`**，只回不定积分。

  静默忽略已传入的参数是最伤信任的行为。现在真的算 `F(to) − F(from)`。
  顺带修掉一个精度陷阱：定积分代入**必须用 Fraction 引擎** ——
  BigNumber 的 `1/3` 是截断小数，乘 27 回不到整数（`8.999999…`），Fraction 能得 `9`。

- **`overrides` 里拼错的 key 被静默丢弃**，公式照常出数、参数用默认值，
  结果"合理但错误"（实测曾导致一次「236 倍缺口」误判）。

  现在会点名哪些 key 已被忽略，并列出该公式的真实参数。
  判据分清：不在 params 里、**且**不在常数表里的才算错拼 ——
  `g`/`c`/`G` 是公式可引用的世界常数，拿它覆盖是合法用法。

### 新增

- **直觉写法**：`2**10`、`ln(10)`、`π`、`2 × 3`、`6 ÷ 2` 现在都可直接用。
  根因是其它 operation 内部都调了 `normalizeSource`，只有 `evaluate` 与批量路径漏了；

- **批量 label**：`expressions` 支持 `{label:"储耗比-中值", expr:"139e8/152e4"}`，
  解决「只有顺序号区分、一度差点引错」。回显格式为 `储耗比-中值（139e8/152e4） = 9144.73684211`。

### 新增（第二轮：参数层不再静默）

- **认不出的参数名会报错，不再静默吞掉**。

  ```
   {operation:'evaluate', expression:'1+3', foo_bar_baz:123}
   修复前 → ok=true, 返回 3        ← 参数被整个吞掉
   修复后 → ok=false, unknown_argument，点名 foo_bar_baz
  ```

  这是本轮**风险最大**的一条：三份文档里提到的 `format`、`sigfigs`、`anchor` 等
  未实现的参数，以前都是「传了不报错、也不生效」——调用方以为做了，实际没做。
  与 `overrides` 里 key 拼错被丢弃是同一类问题，只是发生在顶层。

  白名单**从真实数据源派生**，不手写。踩过一个坑：第一版只从 `MathArgs` 接口取键，
  而 `starMass`/`starTemp` 等 world 顶层简写参数**不在接口里**，
  于是合法调用被自己的校验拦下（world 套件当场红）。现改为同时承认 `WORLD_KEYS`。

  刻意**不做大小写归一**：试过「`DisplayPrecision` 自动映射到 `displayPrecision`」，
  结果参数被接受却因为代码只读小写键而完全不生效——那比报错更难排查。

- **`displayPrecision: 0` 现在真的生效**（只留整数部分）。

  ```
   修复前  {expression:'22/7', displayPrecision:0} → 3.14285714   ← 0 被当成「没给」
   修复后  {expression:'22/7', displayPrecision:0} → 3
  ```

  根因是入口把 `<= 0` 当作未给，而 schema 上白纸黑字写着「0-64」。
  两处 0 的语义**刻意不同**（各有各的理由，已在两处注释里写明）：
  单次参数的 0 = 「0 位小数」，工作区 set 的 0 = 「清除固化值」。

- **语法错误现在会给括号定位，不再只说「检查括号是否配对」**。

  ```
   缺左括号 ((1+2)/3  → 「这几个左括号没有闭合: 第 1 字符；补上 1 个 ")" 即可」
   多右括号 (1+2)/3)  → 「第 8 个字符处的 ")" 没有对应的左括号；多是前面漏了一个 "("」
   并回显表达式，在下方标出每个括号的层级
  ```

  不做「自动补括号」——猜错了会把报错变成一个**算错的数**，比报错糟得多。

- **英制单位补齐**：长吨/短吨/英担/英石、BTU/therm、ft·lbf/s，
  并新增**压力量纲**（Pa/kPa/MPa/bar/atm/psi/mmHg/Torr）。

  ```
   107000 lb → 47.7679 longton     14.7 psi → 1.01353 bar
   1260000 BTU → 1.32937 GJ        760 mmHg → 101325 Pa
  ```

  实测反馈里这些系数被手打过 8 次以上——「记错数」变成「打错名」，
  后者更容易被发现。这也是文档二 P1-1 里真正可行的那一半。

- **help 补全 derivation 的 29 个子命令**（按用途分组，并注明各子命令的关键参数），
  以及**账本闭合配方**（用 `expressions` + `label` 逐项列值 + 差值，
  不做成 PASS/FAIL：差 3 与差 3% 是两种情况，压成一个布尔就全糊了）。

### 新增（带单位结果的说明注释，按用户 2026-11-06 要求）

用户原话：「面向 AI 的运算信息最好把信息注释写到位。」

实测对比：**同一个数，两条路径的信息量差得远**：

```
  units 操作  →  30 里 = 15 km【代入过程】【注意】成熟的说明
  evaluate   →  87.78 Mt       notice 为空，什么都没说
```

模型看到 `87.78 Mt` 并不知道它是 8778 万吨、量级 10⁷ 吨。
而这正是长链推演里最容易数错 0 的地方。

现在带单位的结果会补一句（走 `notice`，不动 `result` 数据通道）：

```
  2.66e8 * 330 kg  →  87.78 Mt
    notice: 注：87.78 Mt = 8.778e7 t，约 8778 万吨，量级 10⁷。
```

三样信息，都是模型判断「这个数合不合理」时真正要用的：
展开成基准单位（便于和其它数比）、中文量级说法（语料的习惯表达）、量级。

**批量路径也有**（跟在结果行后）：

```
  年产（2.66e8*330 kg） = 87.78 Mt｜注：87.78 Mt = 8.778e7 t，约 8778 万吨，量级 10⁷。
```

## 判据刻意收紧：只在 ≥ 10⁴ 时注

试过「带前缀就注」，结果 `3 km = 3000 m，量级 10³` —— 注了等于没注，反而占行宽。
日常量级人本来就有直觉，只有跨到万吨级/亿米级才值得说一句。

复合单位（`9.81 m/s^2`）不注 —— 量级词在那个位置不适用。

## 顺带修掉的一个失效

批量显示行的量级标注走 `annotateMagnitude`，而它内部做 `Number(text)` ——
`87.78 Mt` 会得到 NaN，于是**带单位时那个标注静默失效**。
现在按结果形态分派：纯数字走 `(~10^N)`，带单位走新的说明注释。

### 修订（SI 前缀可斟酌使用，按用户 2026-11-06 追问）

上一版把 SI 前缀**全部禁用**、超出常用档一律丢给科学计数法（`1e6 t`），
那是矫枉过正。用户纠正：「K,M,G,T,P,E,Z,Y,R,Q，不是禁止，可以斟酌使用。」

`Mt`（百万吨）、`Gt`（十亿吨）、`kt`（千吨）、`Gm` 那些是**正经写法**，
工程与气候文献里常见；`1e12 t` 反而不如 `1 Tt` 好读。

规则改成两层：

1. **先按阶梯选常用单位** —— 保证不会出现 `Tg`、`Mm`、`ML` 这种冷门组合
2. **数值仍超出该档时，在常用单位上叠前缀** —— `t` → `kt` / `Mt` / `Gt` / `Tt` …

```
  1e12 g  → 1 Mt       （不是 1 Tg，也不是 1e6 t）
  1e15 g  → 1 Gt
  1e9 m   → 1 Gm
  1e12 W  → 1 TW
  1e18 J  → 1 EJ
  2.66亿吨 → 266 Mt     （2.66 亿吨的可读写法）
```

长度/功率/能量把高阶档位**直接摊平在阶梯表里**（`Mm/Gm/Tm/Pm/Em`），
而不是靠前缀叠加 —— 因为长度阶梯里已有 `km`（自带前缀），
再叠一层会拼出 `kkm` 这种无效组合。质量则用叠加，因为阶梯只到 `t`（不带前缀）。

**踩过一个倍率错**：`steps` 算出来是「除以 10³ 几次」，
而前缀数组 0 号是 `k`，所以下标应是 `steps - 1`。
第一版直接用 `steps`，于是 `1e4 t` 输出成 `10 Mt` —— 差一千倍。

**同时守住的不变量**：整数一律完整输出（`10^20+5` 一位不少），
常用值（`1 kg`/`3 km`/`2 L`/`1 m^3`）不受影响。

### 修复（输出单位归位，按用户 2026-11-06 指示）

用户原话：**「重量单位使用常见的 kg/公斤、t/吨，大数用科学计数法，
其他单位依次类推用常用的公制单位。」**

实测确认的问题：mathjs 会按数量级自动选 SI 前缀，但它**只按数量级走**，
不管现实中人说哪个词。于是：

```
  一个很大的重量 → 1 Tg（太克）    ← 现实中没人这么说
  1e6 m         → 1 Mm（兆米）     ← 没人这么说
  1e6 s         → 1 Ms（兆秒）     ← 没人这么说
```

改为**按量纲的常用单位阶梯表**（`src/format.ts` 的 `PREFERRED_UNIT_LADDER`）：

| 量纲 | 阶梯（从大到小取第一个跨过的档） |
|---|---|
| 质量 | t / kg / g / mg |
| 长度 | km / m / cm / mm / µm |
| 时间 | year / day / h / min / s |
| 功率 | GW / MW / kW / W |
| 能量 | TJ / GJ / MJ / kJ / J |
| 压强 | MPa / kPa / Pa |

效果：

```
  1e12 g      → 1e6 t        （不是 1 Tg）
  1e6 m       → 1000 km      （不是 1 Mm）
  1e6 s       → 11.57 day    （不是 1 Ms）
  2 kg * 1e6  → 2000 t
  0.5 g       → 500 mg
```

**超出最大常用档时用科学计数法配该单位**（`1e6 t`、`1e9 km`），
而不是引入更冷门的前缀。

## 三个踩过的坑（都已写成注释）

**1. `unit.value` 已经是基准单位的数值，不要再乘前缀**
第一次乘了 `prefix.value`（`2 kg` 变成 0.002 kg），
第二次乘了 baseFactor（`1 t` 变成 1e6 kg）。
两次都是「凭直觉推断第三方库内部表示」而不是实测反推 —— 教训明确。

**2. 整数绝不能为「好读」改科学计数法**
试过「≥1e15 改科学计数法」，被 **12 条断言当场打回**：
那违反本项目最硬的不变量「整数永不丢位」——
`10^20` 与 `10^20+5` 会长得一样，那是丢信息不是简洁。
大数占行宽的问题改由**批量显示补千分位**解决（纯视觉分组、不改值）。

**3. 体积刻意不做归位**
试过 L↔m³ 互换，结果 `1000 L` 变 `1 m^3` 而 `1 m^3` 变 `1000 L` ——
两者互相吞吐。体积的「常用写法」本身就不统一（水用 L、土方用 m³），
强行归位只会改掉调用方给的语义，收益为零。

### 修复（按 2026-11-06 第二份实测报告）

一份 99 层架空世界观的设定推演，约 18 次调用 / 130 余个算式。
它的 P0 是**中文量级词**——恰好是上一轮修中文单位时漏掉的一环：
单位表收了「里/丈/亩/斤」，却没收入「万/亿/万亿」。

报告作者两次把「吨」当成「亿吨」，起因就是必须手写 `/1e8`：

```
  0.591e8 * 330 / 1e3  → 19503000 (~10⁷)   被读成「1.95 万吨」，实为 1,950 万吨
  2.66e8 * 330 / 1e3 / 1e8 → 0.8778        被读成「878 万吨」，实为 8,780 万吨
```

**「两步除法」本身就是错误源**，而工具原本可以替调用方消掉这一步。

- **中文量级词 `万` / `亿` / `万亿` 现在可直接参与运算**。

  ```
  2.66亿 * 330        → 87780000000
  450 亿吨 / 31.39 亿吨 → 14.33577572   （比值无量纲）
  3万亿               → 3000000000000
  ```

  实现走**乘数展开**（`2.66亿` → `(2.66 * 1e8)`），而不是把它们注册成单位：
  单位表的机制是「factor × 基准量纲」，而量级词是无量纲乘数 ——
  硬塞进去会把「亿米」和「亿吨」搞成同一种东西。

  三个必须注意的细节（都已写成注释与断言）：
  · **长词优先**：`万亿` 必须排在 `万` 与 `亿` 之前，否则 `3万亿` 会被拆错
  · **展开后要再包一层括号**：否则 `450 亿吨 / 31.39 亿吨` 因乘除左结合变成先除再乘，
    结果带上 `Mg^2` 量纲 —— 数值对、量纲错，这种最难发现
  · **「人」「畜」在量级词后面是计数**，不是功率单位（`2.66亿人` 不能变成 `19.95 GW`）

- **数字数组不再静默全失败**。

  ```
  expressions: [0.5, 9.9, 10]
  修复前 → （空表达式）→ 跳过 ×3，成功 0
  修复后 → 0.5 = 0.5 / 9.9 = 9.9 / 10 = 10
  ```

  这是**类型错误被伪装成内容错误** —— 用户传的是合法数字，
  工具说「空表达式」，会让人去翻数据源而不是检查类型。纯数字元素现在自动转字符串。

- **非法变量键不再中止整批**。

  ```
  variables: {"P":1000, "Q":5, "人口":1}
  修复前 → ok:false，连合法的 P*330 都没算
  修复后 → P*330 = 330000 照算，notice 里点名「人口」被跳过
  ```

  这类语料的概念名几乎全是中文（人口/粮食/石料），用户第一反应就会用中文命名。
  现在合法键照常进作用域，非法的记进 notice —— **算出来的数仍然是对的**。
  不做「支持中文变量名」：那要放宽 mathjs 的词法，会引入新的歧义。

- **语法错误给子类型与位置**，不再一律说「检查括号是否配对」。

  ```
  1,000 * 2   → 「表达式里有千分位逗号，去掉即可」（旧提示说查括号，指错了方向）
  / 112.5e8   → 「运算符位置不对（第 1 个字符附近「/ 112.5」）」
  某中文*2    → 「表达式里有中文；中文单位与量级词可直接写，其它请改英文变量名」
  ```

  **顺带修掉一个很隐蔽的漏判**：这条正则原来写的是 `SyntaxError`（无空格），
  而 mathjs 报的是 `Syntax error`（有空格）——于是这类错误落到兜底分支，
  表现为「错误类型对、但没有任何 hint」。报告里 `2.66亿 * 330` 无提示就是这个原因。
  靠对照实验才揪出来（`1+*2` 有提示而 `某中文*2` 没有）。

- **质量 SI 前缀补中文量级参照**。

  ```
  2.66e8*330 kg  → 87.78 Tg（= 8778 万吨）
  ```

  「87.78 Tg」读不出「8,778 万吨」，而中文语料里这个量级就叫亿吨。
  只对「质量 × 克」这一族、且 ≥ 万吨时补 —— `1 Gg（= 1000 吨）` 那种注了等于没注。

- **大整数补千分位**（只在批量显示里，`result` 数据通道不变）。

  ```
  1e20*3 → 300000000000000000000（300,000,000,000,000,000,000） (~10²⁰)
  ```

  报告原话：「一条 21 位数字就占满一行，且位数多到无法目视核位
  ——本次我数错过一次 0 的个数。」

- **三角函数按弧度算时给一句说明**。

  ```
  sin(30)     → -0.98803162，notice 提示「按弧度；要角度请写 sin(30 deg)」
  sin(30 deg) → 0.5，不提示
  ```

  中文工程语境里 `sin(30)` 的默认读法是 30 度。按数学惯例走弧度是对的，
  但不给提示就是静默错误 —— `-0.988` 看起来像个正常数。

一份 200 余条表达式的实测报告，**先讲自己的错、再讲工具的缺陷**，每条带可复现调用。

  ```
  1 里 + 3 米              → 503 m
  3 公里 + 500 米          → 3.5 km（公里优先于里，不被拆错）
  2 斤 + 300 克            → 1.3 kg
  1 丈 + 2 尺              → 3.84 m
  5 亩 + 100 m²            → 3433.33 m²
  1 时辰 + 30 分钟         → 9 ks
  ```

  顺带修掉两处相关缺陷：mathjs 不认上标（`m²` 报 Syntax error），
  现在表达式里统一换成 `m^2`；面积别名 `km2` / `m2` 也能用。

- **`units` 的代入过程有同义重复**。

  ```
  · 1 kg = 1 kg
  · 9.0000e+15 kg = 9.0000e+15 kg
  · 1 t = 1000 kg，故结果 = 9000000000000 t
  ```

  前两行是废话（源单位是基准单位时，「1 X = 1 X」什么也没说明）。
  而且它让输出**看起来有内容，其实没有** —— 这比啰嗦更值得修。
  现在按信息量分四种情况，只写有意义的步骤。

- **`terse` 对 `units` 不生效**。

  `{operation:"units", terse:true}` 原来仍返回 6 行带框。现在只回一行，
  但**保留适用域提示**（「里在周制约 415 m」这类信息被省掉，
  调用方会拿错朝代的值去写设定 —— 那比多几行更糟）。

- **英文全称别名缺失**：`ton` / `tonne` / `meters` / `metre` / `hectare` /
  `grams` / `seconds` 全不认，只认缩写。而英文文献里全称极常见。
  已在 length / mass / time / area 四个最常用量纲补齐（没有给冷门单位长别名表，
  那是每轮计费的固定成本）。

- **`expressions` 元素里的未知键被静默忽略**（本报告未提，实测发现）。

  ```
  {expressions:[{label:'a', expr:'1+1', unit:'kg/day'}]}  → ok=true，unit 被丢弃
  {expression:'1+1', unit:'kg/day'}                       → 报 unknown_argument ✓
  ```

  顶层严格拦截，元素内部不查。危险在于：将来加 `unit` / `assumption`
  这类按条参数时，它们必然写在这个位置，会被静默吞掉。
  现在该条失败并点名键名，其余条目不受影响（保持「逐条独立」的约定）。

### 新增（防呆层：在数字旁边多放一句「这个数看起来不对劲」）

来自一份 **200 余条表达式**的实测复盘。那份文档的核心结论是：

> math_execute 现在是一个准确的算术器，但还不是一个可靠的验算伙伴。
> 它给数字，不给判断 —— 所以它最该做的不是算得更准（它已经很准），
> 而是**在数字旁边多放一句「这个数看起来不对劲」**。

文档里记录的真实事故：

```
 2645.6*28*3600*8000/1e9  →  2133.41184
 调用者贴上「万吨」标签    →  以此为据指控原文「错了 10 倍」
 真相：2133 是千吨，万吨应为 /1e10 → 213.34（原文完全正确）
```

**四条年度物料全部犯同一个错、全部偏大 10 倍、全部报「成功」。**

这一版做了三件事：

**1. 量级标注** —— 裸数字旁边配 `(~10³)`

```
   年耗N2万吨 = 2133.41184 (~10³)
```

10⁰~10³ 这个日常区间不标（标了反而吵）。

**2. label 与结果的量级核对**

label 里明确写了量级词（万/亿/千…）时，比对该量级与结果本身的数量级：

```
   年发电量亿度 = 288000000 (~10⁸)     ← label 说「亿」，裸数字已到 10⁸
   ⚠ 若按字面读成「亿」则为 2.88e16，请核对换算。
```

**3. 同批次一致性比对**（文档里说「这条能一次性拦住同一个错犯了四次」）

按 label 的量级词分组，组内 ≥2 条且量级一致、与该组声称的量级差**恰好一个数量级**时才报：

```
   ⚠ 本批有 4 条 label 含「万」（=10⁴），但结果全部落在 10³ 量级
     量级与 label 声称的差 1 个数量级 —— 除数可能少除了一个 10
     （例如该用 /1e10 却用了 /1e9）
```

**判据刻意保守**：差 0（口径已对齐，如 213 万吨）不报；差 ≥2（可能是正常的大数/小数）不报。
只报「差恰好一个数量级」——那正是「千吨被当成万吨」的特征。

**4. 「成功」改为分级语义**

文档原话：「『成功 7，失败 0』会让调用者跳过复核，因为『成功』两个字读起来像『对了』。」

```
   算式全部求值成功（4 条，只表示算式无语法/符号错，不含结论正确性判断）
```

**5. terse 不许吞掉风险提示**

terse 的承诺是「省掉标题与统计」，不是省掉 ⚠。第一版把提示一起省了，
于是 terse 用户看到的是一行干净数字 —— 而干净正是最危险的。

新增 `test/guards.mjs`（23 项）。**第 4 节守「正确用例零误报」** ——
误报会让整条通道被关掉，比漏报更糟。反向对照已验证：撤掉防呆后 11 项变红。

```
 {expressions:["a=5","b=oops*2","d=b*2"]}
 修复前   d=b*2 = 2 b          ← 合法单位结果，汇总「成功 2，失败 1」
 修复后   d=b*2 → 失败[unknown_symbol]，汇总「成功 1，失败 2」
```

根因是**两个独立缺陷叠在一起**：

1. **单位判据只看「同级有没有数字」，不看顺序**。
   mathjs 保留书写顺序：`2 b` 是 `[数字, 符号]`（单位），`b*2` 是 `[符号, 数字]`（变量）。
   旧判据一律放过，于是 `b*2` 被当成单位。

2. **赋值语句的右半部分挂在 `value` 上，而 AST 遍历只走 `args/items/content/object/index`**。
   `d=b*2` 的 AST 是 `AssignmentNode(name=d, value=OperatorNode(*))`，
   赋值右侧**整个不被判据看到** —— 所以第 1 条即使修好了也不生效。

这类「下游悄悄变成虚成功」比报错难发现得多：批量汇总里它算成功，
而结果是 `2 b` 这种看着完全正常的量。

新增 `test/multistep.mjs`（26 项）：第 3 节专守这条；第 5 节用 9 种真单位写法
守「修复不能误伤单位」（`5 V`、`9.81 m/s^2`、`s^2`、`(2+3) V`、`1/2 h` 等）。

### 新增（工作区命名变量，默认关闭）

工作区的 `variables` 字段、写入（`workspaceVariables`）、删除（`remove-variable`）、
显示（`show`）**本来都已存在**，唯独**读取路径缺失** —— 存进去的变量在计算里用不到：

```
 {action2:"set", workspaceVariables:{BTU_LB:1260000}}  → 变量 1 个      ✓ 存住了
 {expression:"BTU_LB/1000"}                            → Undefined symbol  ✗ 用不了
```

「能删不能加、加了用不了」是设计不一致，这一版把最后一环接上：

```
 workspace set useWorkspaceVariables:true   → 打开开关（逐工作区）
 evaluate BTU_LB/1000                      → 1260
 evaluate variables:{BTU_LB:999000}        → 本次参数优先，得 999
```

**默认关闭**。打开后同一表达式在不同工作区状态下结果可能不同，
会削弱「同输入同输出」——那是本项目做 hash 复现与回归对比的基础，
所以它是一个显式的、逐工作区的选择，不默认生效。
关闭时行为与未引入该功能时**完全一致**（变量仍存着，能看能删）。

**缓存必须跟着变量走**：缓存键原本只含工作区名与常数指纹，不含变量内容。
若不修，`改变量 → 再算 → 命中旧缓存 → 静默返回改之前的数`——
与文档批评过的「改常数后返回旧值」是同一类。现在变量内容进指纹：

```
 改前 BTU_LB=1260000 → 1260
 改后 BTU_LB=1055000 → 1055    ← 不是命中旧缓存的 1260
```

顺带把 `workspaceVariables` 与 `useWorkspaceVariables` 补进工具 schema：
前者此前代码支持但参数表里没有（模型看不见），属同批「可发现性」问题。

### 修复（按 2026-11-07 实测报告《使用问题与改进建议》）

这份报告的落点是一句话：「工具把安全性放在了错误的位置 —— 它校验「式子能不能算」，
却不校验「结果对不对」。」其中六条已修，另有一条是本轮实测发现、报告未提的回归。

- **单条与批量对「非有限值」的判断不一致**（报告最核心的一条）。

  ```
  {expression:"1/0"}                               → 错误[non_finite]  ✓
  {expressions:["1+1","1/0","sqrt(-1)","log(0)"]}  → 「算式全部求值成功（4 条）」 ✗
  ```

  同一个式子换个调用方式就从「错」变成「对」，而批量恰恰是 AI 最常用的形态。
  现在批量里非有限值归入 `failed`：`ok=false` + `partial=true` + `failed=N`。

  新增 `isNonFiniteValue`（下钻到 `Unit.value`）：`(1/0)*2 kg` 序列化成
  `"Infinity g"`，旧的 `containsNonFinite` 只认恰好 `"Infinity"`，于是带单位的
  非有限值连**单条**都拦不住 —— 而它看起来像个正经结果。
  反向守：`1e400`、`2^1024` 这类**有限的极大数**不误判（转双精度才溢出，
  BigNumber 自己知道自己是有限的）。

- **写出来的目标单位被输出层悄悄撤回**（本轮实测发现，报告未提）。

  ```
  2 m to cm    → mathjs 算出 200 cm  → 工具输出 "2 m"
  1 t to kg    → mathjs 算出 1000 kg → 工具输出 "1 t"
  ```

  根因是单位归位只看 `unit.value`、不看调用方意图，把**显式换算的目标**按阶梯
  重挑了一遍，恰好挑回出发点。数字看着完全合法（`2 m` 是正经长度），所以没人怀疑。
  修法：表达式里有 `to` / `.to()` 时跳过归位。

  顺带补上被它掩盖的另一半：显式换算时小数位没走 `displayPrecision`，
  `5 cm to inch` 会吐 21 位小数。

- **`to` 的报错从 `internal` 降级为可行动的提示**。

  `internal` 在本项目的约定里意思是「工具自己坏了」，会让人去重试；
  而真实原因有四类、修法各不相同。现在分开：
  `unit_name_conflict`（`1 s to min` —— min 在 mathjs 里是函数不是单位，写 minute）、
  `not_a_quantity`（`0.5 to kW` —— 裸数字没有单位可换，该用 operation="units"）。

- **`evaluate` 与 `units` 两套单位表打通**。

  `mph` / `kn` / `rpm` / `inHg` / `cal` / `gauss` / `slug` / `shortton` 等
  在 `units` 里认得、在 `evaluate` 里报 `Undefined symbol`。表不通就逼人**手填系数**
  （`10*745.7`），而手填系数正是报告那四起千倍级事故的共同源头。

  做法是在 `buildMath` 里注入 174 个单位，注入完照旧删掉 `createUnit` ——
  **安全边界一点没动**，只是把「我们自己能定义单位」用上了。三条取舍：
  不覆盖既有单位、不收单字母（否则吃掉变量 `c`/`G`）、不覆盖函数名。

  **踩到一个很隐蔽的连带污染**：注入会把新单位登记进 mathjs 的全局
  `currentUnitSystem`，而 `Unit.toString()` 的 `simplify()` 从那里挑**第一个**
  同维度单位，于是 `1 m^2` 变成 `0.0149 katha`、`1 m^3` 变成 `1086 gantang`。
  最阴的是：注入的用例全绿，坏的是**别的**老用例 —— 只有跑全量回归才看得见。
  修法：注入后把 unitSystem 重置到 `si`（实测两者输出原本一致，且 `si` 是只读的）。

- **文档把「带单位写」提到最前**（报告 P0-1）。

  工具描述加两行（净压到 414/450 字符），`help` 里把 `5 cm to inch`
  从第 4 个例子提到第 1 个，并写明裸数字的风险；补上 `expressions` 元素的
  `{label, expr}` 对象写法，以及「`标签=表达式` 不支持」这条必然踩的坑。

- 新增测试套件 `test/report-1107.mjs`（63 项），每条修复都带反向对照：
  未写单位仍须归位、复数不算非有限、有限大数不误判、既有单位不被改写。

### 变更（帮助系统改成分节目录）

旧的 `help` 是一整块 **5900 字符**的摊平清单，每次调用都付全量成本。分段统计：

```
  世界观推演   3039 字符  ← 占 52%，但算一条 1/3 也要读它
  求值与代数    612
  数据管理      557
  公式库        337
  其余各节合计  700 左右
```

改为三层结构：

```
  operation:"help"                      → 目录（12 节，各带一句话简介）
  operation:"help", helpTopic:"world"   → 该节完整正文
  正文内部再分层                         → 字段表 / 默认值 / 常见坑
```

实测：目录 **1731 字符**，单节 203—1904、平均约 810（全量的 14%）。

**两个互相对抗的要求同时守住** —— 省过头就是「AI 不知道有这个功能」，那比不拆更糟：

1. **目录必须可发现**：每节简介要说清「解决什么问题」（测试断言 ≥15 字），
   并配别名 —— AI 不知道 key 叫 `linalg`，但会说「矩阵」；写「星球」也查得到 `world`。
2. **内容不许因拆而缩水**：旧版为压 6000 字符上限砍掉了 world 的默认值、
   derivation 的子命令参数、错误码表。现在每节按需付费，所以**补全了** ——
   `world` 节 25 个字段带默认值与单位，29 个 derivation 子命令逐个说明，
   并新增错误码对照表。

工具描述改成指引这两步（不写的话 AI 会以为 help 只给目录，或者干脆不查，
那分节就等于把功能藏起来了）。未知节名**不报错** —— 回目录并点名：
「报错会打断探索，而目录能让它自己纠偏」；大小写、空格、换行都容忍。

新增 `test/help-topics.mjs`（63 项）守这两条拉扯。既有 9 处依赖 help 全文的断言
改为按节取用 —— 断言目的没变（说明必须仍能找到），只是找的位置变了。

  上应得 5；球冠 h=r 得半球 2π/3、h=2r 得整球 4π/3；正多边形 n=4,s=2 得正方形面积 4；
  单利与年复利在 t=1 时必须相等。

### 修复

- **检索查不到中文复合词**（比补公式更影响体感）：`findFormulas` 只做整串子串匹配，
  于是 `粮食` 能查到 4 条、`粮食产量` 却是 0 条；`比热` 能查到、`比热容` 查不到。
  用户和 AI 不会总说最短形式。现在加了：
  - 中文 2—4 字滑窗子词匹配（`粮食产量` 能对上关键词「粮食」「产量」）
  - 同义词表（`比热容`→`比热`、`月供`→`贷款`、`粘度`→`黏度` 等 30 组）
  - 词元按长度加权，长词命中排前面，避免「粮食产量」把所有含「量」的公式挤上来
  - 默认返回上限 10 → 20（宽查询不再被截断）

- **`world` 顶层参数静默失效**：此前只认 4 个便捷参数
  （`planetRadius`/`planetMass`/`rotationHours`/`obliquityDeg`），
  于是 `{operation:'world', starMass:10}` 里的 `starMass` 被**静默丢弃** ——
  输出仍是太阳（主序寿命 10 Gyr），一句报错都没有。作者以为算的是 10 倍质量恒星。
  现在改为遍历 `WORLD_PARAMS` 全量白名单派生便捷参数，且 `world` 内同名键优先。

- **频次测试写死绝对值**：`formula-story.mjs` 断言「高频 50—130 条」，
  公式库一扩容就误报失败。它本意是「高频不应占满全库」的比例约束，
  改成占 20%—60% 的比例断言。

### 修复

- **主动提醒命中率归零**（最严重的一条）：`agent/pre-step` 钩子用
  `content.includes('math_execute')` 判断「本会话是否已用过插件」，而我们的系统提示
  每轮都注入、且必然包含这个词 —— 于是 `toolUsedInSession` 恒为 `true`，
  检测器从第一轮之后**永久静默**。

  实测：检测器本身命中率 72%（13/18 条真实作者语句，误报 0/6），但经过钩子后
  实际命中率 **0**。修法是改成**结构化判断**：只看 `role === 'tool'` 消息、
  assistant 的 `tool_calls` 数组、或 content 里的 `type: 'tool_use'` 块。
  「用户问 math_execute 怎么用」也不再被误判成「已用过」。

  修后实测：真实对话历史（含系统提示）下命中率 **90%**（9/10），
  真调过工具后仍正确静默（4/4）。

- **工具描述漏了 3 个 operation**：`TOOL_DESCRIPTION` 里没有 `derivation`、
  `custom`、`feasibility`，模型因此不知道它们存在 —— 而所有测试全绿。
  原因是 `test/awareness.mjs` 里手写了一份 operation 清单，加新 op 时没同步。
  现在清单**从 schema enum 派生**（唯一真相），并加反向断言与长度预算（≤900 字符）。
  描述长度 810 → 718 字符，同时覆盖全部 29 个 operation。

- **检测器缺势力收支类词表**：`balance` 是新增能力，但检测器词表里没有
  「养得起/够不够/军费/粮草」这类说法，导致「这个王国养得起二十万兵吗」评分 0。
  已补两条意图模式，命中率 72% → 83%。

- **`help` 让作者去点一个不存在的面板**：数据管理那段还写着「侧栏『数学工作区』入口
  可图形化管理」，但界面 2026-10-25 已全部移除。AI 照读会把作者引到一个点不开的入口。
  已改成「本插件没有图形界面，全部经工具与 HTTP 路由操作」。
  同时 `test/advanced.mjs` 里那条「help 必须提到侧栏入口」的断言原本把错误行为
  写成了预期，改为反向断言（不许出现「侧栏」，必须说明「没有图形界面」）。

- **世界推演的措辞违反项目铁律**：1.4 g 以上会输出「生物**必须**更矮壮」，
  而铁律要求输出措辞不出现「错误/禁止/必须」（`test/ai-brief.mjs` 守着这条）。
  改成「生物得长成矮壮型才撑得住」。这一条是**实际使用验收**跑出来的，
  原来的世界推演测试只看数值不看措辞。

- **单位清单的伪精度**：`亩` 的系数是 666.6…（无限循环），清单里显示成
  `666.6666666666666`，看着像精确值。系数改用独立格式化，显示 `666.667`。

### 测试

- 新增 `test/real-usage.mjs`（94 项）：**作者视角的实际使用验收**。
  与其它套件不同，它验的是「拿去能不能用」而不是「算得对不对」：
  输出里不许出现已删界面、`Infinity`/`NaN`/`undefined`/`[object Object]`；
  必须有单位与可信度标签；措辞不许反驳作者设定；错误必须给修复方向；
  输出体积有上限（AI 读得下）；并把「1.5 g 星球 → 50 米巨兽站不住 →
  300 米塔能建 → 王国养不养得起兵 → 火箭飞不出去 → 三十里多长」串成一个
  完整场景，检查前后自洽。

### 移除

- **UI 全部移除**（2026-10-25，`14f6ed0`）。做了三版（目录树 18 节点 → 精简 10 节点 →
  单页工作台）效果始终不好，决定砍掉：`src/client.ts`（2497 行）、`lib/client.js`
  （138.8 KB）、9 个客户端测试套件、`tsconfig.client.json`、`package.json` 的

  只经 `math_execute`（27 种 operation）与 HTTP 路由给 AI。见 `docs/ui-removed.md`。

### 新增

- **世界参数校验（三档）**：`world-params.ts` 的 `range` 此前是**纯装饰** ——
  22 处声明没有任何代码读取，实测 `planetMass=-5`、`planetRadius=0`、`albedo=5`
  都 200 OK 存进去了。新增 `src/world-validation.ts` 让范围真正生效：
  - **硬拒绝 400**：`range.hard` 且**低于下界** —— 会算出无穷/非数/负物理量
    （零半径 → 重力 Infinity、零质量 → 离心比 Infinity、零轨道 → 80 处 Infinity）；
  - **软警告 200 + `warnings[]`**：越界但仍照设定算（`planetMass=500`、`albedo=1.5`），
    消息里给出范围与代价。**上界一律走这一档** —— 「质量大得离谱」是设定自由，
    拦了就违反「不反驳用户设定」；
  - **静默接受**：在范围内。

  哪些参数标 `hard` 是**实测**出来的（逐个取极端值跑推演、统计产物里 `Infinity`/`NaN`
  个数），不是拍的。实测还暴露了探针自身的 bug：`planet.surfaceGravity` 其实是
  显示串（`'Infinity'` 字符串），只看 `typeof === 'number'` 会整片漏判。

- **`invalid` 判定档**（`dead-universe.ts`）：检出物理量非有限/为负时判 `invalid`，
  与 `dead` 分开 —— `dead` 是「死寂宇宙」这种合法设定，`invalid` 是「参数本身算不出数」。
  混在一起会让作者以为「世界设得太狠」，实际是把半径写成了 0。渲染措辞仍只讲怎么改，
  不写「错误/禁止/必须」。

- **逐颗卫星 `moons` 可存档**：`world.ts` 早已支持 `MoonSpec[]`（洛希极限/希尔球/
  相邻间距/观感），但 `moons` 不在白名单里，导致「多卫星系统」只能直接调 tool、
  存不进工作区。`ParamSpec.kind` 新增 `'array'` 与 `itemShape`，现在能存能校验。

### 修复

- **`Infinity`/`NaN` 会流到 AI**（最伤可信度的一条）：`/summary` 的
  `derived[].value` 曾是裸 `Infinity`（只有 `text` 被格式化成 `—`），
  `verdict.causes` 里也有 `"表面重力不成立：Infinity m/s²"`。AI 会当成真数字写进结语
  ——「这颗星球重力是 Infinity」。现在 `deriveAll` 用 `finite()` 统一归一化，
  `judgeDead` 的原因描述改成中文（不出现字面量），整个响应不含 `Infinity`。
- **`save-world` 的双白名单事故**：该路由曾自带一份 14 键硬编码白名单，
  而 `WORLD_PARAMS` 有 23 个基础量 —— 于是 `starClass`（「我要 G2V 恒星」）、
  `hasLiquid`、`materialStrength/Density`、`moonCount/Mass/Distance`、
  `lightPollution`、`galaxyBand` 共 9 个键被**静默丢弃**：返回 200 OK，不报错不提示。
  现在白名单只留一个真相。
- **类型静默强转**：`Number(true)===1`、`Number([])===0`、`Number(['7'])===7` ——
  `{planetMass:true}` 曾静默存成 1。现在只接受 `number` 与数字字符串，其余 400。
- **注入给 AI 的 operation 数量是旧的**：`awareness.ts` 的系统提示写「共 25 个」，
  实际 27 个（漏了 `derivation` 与 `custom`）。`integration.mjs` 的断言清单同样只有 25 个，
  现在补齐到 27 并加了**反向断言**（schema 里不许有清单外的名字）。
- **`npm run preflight` 因 UI 移除而崩溃**：它仍在 `readFileSync('lib/client.js')`，
  文件已删 → `ENOENT`，装机前自检直接非零退出。改为反向断言（客户端产物确实不存在、
  无 `dsh.client`、无 `exports["./client"]`、无 `tsconfig.client.json`），
  与 `test/integration.mjs` 第 5 节互为印证。
- **`tsconfig.json` 仍排除 `src/client.ts`**：文件早不存在，排除项清掉。

### 能力

- **计算内核**：BigNumber 64 位高精度求值、符号微积分（求导/积分/化简/展开）、
  解方程与线性系统、矩阵（秩/行列式/迹/奇异值/零空间/逆）、统计与概率分布、
  回归、ODE（RK4）。
- **UI（令牌化）**：左栏「全局管理」与右栏「本工作区工作台」共用同一套宿主设计令牌
  （`--dsw-alias-*` / `--dsw-font-*` / `--dsw-radius-*`），无写死颜色；
  **新建工作区即生成同名数据表**（`<工作区名>.json`，含常数/公式/地点/变量四张子表），
  切换工作区后右栏自动跟随。
- **公式库 342 条**，每条带**三轴标签**：
  `layer`（离最底层规则的远近：基本/数学/导出/经验/工程/约定）、
  `domains`（学科领域，多标签）、`frequency`（**主角视角感知频率**）。
  检索：`freq:` / `layer:` / `domain:` / `symbol:` / `keyword`。
- **两级公式扩展**：全局公式包（`$DSH_HOME/math-calc/formula-packs/global.json`，写盘即生效）
  + 工作区临时公式；新增时校验 id、表达式可解析、**符号必须已定义**（拼错变量当场拒绝）。
- **符号消歧**：同一字母不同含义（`m` = 质量/米）可查 `symbol:m@质量`。
- **常数推演**：无量纲优先（α/μ/α_s/α_G）、尺度阶梯、单位旋钮与物理改动分离、矛盾清单。
- **世界推演**：恒星（质光/寿命/宜居带/α 敏感度）→ 气候 → 天空配色 → 卫星系统 →
  化学窗口与生命硬否决 → 跨模块一致性检查 → 经验系数可信度标注。
- **UI**：左侧入口 = **全局管理**（所有工作区：创建/切换/删除，常数表、公式表、设置）；
  右侧边栏页签 = **本工作区工作台** —— 工作区切换器、本区数据表（常数/公式/地点/变量）、
  **开关**（提示档位、公式启停）、**管理**（变量与地点的增删）。
  左栏切换工作区后右栏**自动跟随**（同一 client bundle 内的订阅 + 宿主 `sidebarRight` store）。

### 修复（相对内部早期版本）

- **客户端注册 id 必须等于包名**：此前用 `<包名>-client`，宿主按包名查找不到模块，
  导致桌面端每次启动都报 `import failed` 并致命退出。
- **客户端入口幂等**：宿主会重放 bundle，重复注册会抛错并升级为致命错误。

- **工作区切换自动落盘**：此前切到不存在的工作区只产生内存对象，`current` 会指向幽灵工作区。
- 工作区创建兼容 `name` 参数（此前只认 `workspace`，误报「不能是 default」）。
