## 一、单位体系（最痛的区，18 条）

### 1.1 中文单位直接映射 SI 基准 → 丢因子

- **现象**：`1 担` 算成 `1 kg`，差 **50 倍**。
- **根因**：`担` 映射到基准 `kg` 时，factor（50）丢了。
- **正确做法**：中文名注册成**合成名**（`cz` + 3 位小写字母）并带 factor。
- **出处**：AGENTS.md:63

### 1.2 短别名拆掉长词

- **现象**：加了 `石` 别名后，`1 石炭 to MJ` 被拆成 `1 cndan炭` → 语法错。
- **根因**：别名替换没判后边界，`石` 在 `石炭` 里被单独匹配走。
- **正确做法**：别名后**紧跟汉字**说明它只是长词的一部分，跳过。
- **出处**：AGENTS.md:60

### 1.3 单位别名表与数据表不同步

- **现象**：units.json 459 条带中文别名，手写别名表只有 172 条 → **实际只有 78 条能通**。
- **根因**：维护了两份数据源。
- **正确做法**：从数据表**自动生成**映射，unit-coverage 守护覆盖率。
- **出处**：AGENTS.md:62

### 1.4 复合单位被显示成冷门内部单位

- **现象**：`1 J/g` 显示成 `1e+5 raddose`（吸收剂量内部代号）；`1 N*m` 显示成 `1e-44 foe`（超新星能量单位）。
- **根因**：mathjs 对复合单位结果会挑**同量纲里最冷门的一个**显示。数值都对，但读者看不懂，写设定时极易误判成「工具算错了」。
- **正确做法**：显示层做 SI 归约，但**判据必须是白名单式的已知代号**。
- **出处**：src/core/format.ts
- **⚠ 第三次复发（2026-11-27）**：`1 kg*m/s^2` → `tonf`、`1 J/s` → `erg_per_s`、
  `1 N/m^2` → `Ba`、`1 m^3/s` → `cfm` 仍然漏。根因升级：**result 与 value 是两条独立
  格式化路径，各维护一套白名单**（evaluate.ts 的 `isObscureUnitText` vs format.ts 的
  `normalizeDisplayedUnit`），修一条另一条不动——就是 1.5 的教训再犯。
- **正确做法（更新）**：两条路径**共用同一个** `normalizeDisplayedUnit`，对着
  `STANDARD_DIMENSION_UNITS` 判断「是否标准 SI 写法」；冷门名单只维护一处。
  用户显式写的单位（`担`、`degC`、`kW`）一律保留，判据不得用否定式。

### 1.5 裸写 m/s 被内部合成名劫持（最严重的一次）

- **现象**：`5 m/s` 算成 `288.018`，`10 m / 2 s` 同样。
- **根因链**：数据表里有 `日行里快`（factor 0.01736，速度维度）→ 注册成 `czxxl` → mathjs 解析「数值+单位」时把 `m/s` 匹配成了 `czxxl` → 5 ÷ 0.01736 = 288。
- **正确做法**：显示层识别 `cz` 合成名与**被代换的中文具名单位**，归约回 SI。
- **⚠ 二次踩坑**：第一次只修了 `value` 字段，`result` 没修——因为测试只看 `value`，误判为已修复。**发布后装机实测才抓出来**。
- **出处**：src/features/numeric/evaluate.ts、CHANGELOG 3.2.1

### 1.6 判据顺序错误导致修复失效

- **现象**：明明加了 `cz` 形态判断，`5 m/s` 还是显示成 `288.018 日行里快`。
- **根因**：先执行 `restoreCjkUnitNames` 把 `czxxl` 还原成中文名「日行里快」，此时判据（只认 `cz` 形态）已经认不出。
- **正确做法**：**判据必须在还原之前**；且判据要同时覆盖 `cz` 形态和中文具名单位。
- **出处**：CHANGELOG 3.2.1

### 1.7 用户写的中文单位不能被「归位」掉

- **现象**：`1 zli`（里）被归位成 `m`，看起来像工具换了单位。
- **根因**：显示归约逻辑没区分「工具内部代号」与「用户明确写的单位」。
- **正确做法**：用户写的中文单位（担、里、时辰）原样保留；只归位 `cz` 合成名与**被代换的**具名单位。
- **出处**：r82-namespace-units 抓出

### 1.8 一律归约到 SI → 把用户要的单位冲掉

- **现象**：`10 hp to kW` 变成 `(kg m^2)/s^3`，`5 cm to inch` 变成 `0.05 m`。
- **根因**：无条件归约会覆盖用户明确指定的目标单位。
- **正确做法**：**只在该单位名是已知冷门代号时才归约**。这条比原 bug 更糟，实测踩到。
- **出处**：src/core/format.ts:436

### 1.9 用「不在常见集里」做判据 → 误伤

- **现象**：`1 kg → 0.02 担` 里的「担」不在常见单位集 → 被判冷门 → 强行改成 `1 kg`。
- **根因**：否定式判据（不在白名单 = 可疑）必然误伤。
- **正确做法**：判据用**白名单式的已知代号**，不要用否定式。
- **出处**：src/features/numeric/evaluate.ts:301

### 1.10 createUnit 用复合基准定义体会污染原符号

- **现象**：注册任意速度单位后，`1 m/s` 被解析成该单位。
- **根因**：`createUnit(safe, '0.01736 m/s')` 会把 `m/s` 本身注册成可前缀匹配的单位。
- **正确做法**：不要用复合符号作定义体；已在显示层兜底。展开成 `m*s^-1` **也会**被 mathjs 化简回去，无效。
- **出处**：实测记录（本轮）

### 1.11 一个 try 包多条注册

- **现象**：`createUnit('AU'…)` 抛了，后面 `tce` 静默消失；单独注册却成功。
- **正确做法**：批量注册**逐条 try**。
- **出处**：AGENTS.md:61

### 1.12 单位名清洗后撞名

- **现象**：`m/s` 清洗成 `ms`，与**毫秒**同名。
- **正确做法**：标准写法（`m/s`、`km/h`）不注册，交给 mathjs 原生处理。
- **出处**：src/core/engine.ts

### 1.13 li 在 mathjs 里是 link（测链）

- **现象**：`1 li` 得到 `0.201168 m`（测链），不是「里」。
- **正确做法**：中文「里」走中文替换路径，不用 ASCII 名。
- **出处**：src/core/engine.ts:114

### 1.14 mathjs 原生缺常用缩写

- **现象**：缺 `kn`（节）、`kcal`、`cal`——只补了 `knot` 却漏了缩写。
- **正确做法**：补注册时要**同时补全称与缩写**；提示词里的每个例子都要有守护测试。
- **出处**：src/core/engine.ts:1036、AGENTS.md:64

### 1.15 年代单位的命名规则

- **现象**：第一版直接 `ERA_ALIAS.set(cjkName, name)`，后注册的覆盖前面的。
- **正确做法**：createUnit 只允许字母数字；用 `cnera` 前缀 + 确定性编码，避免碰撞。
- **出处**：src/core/units-era-registry.ts:466,239

### 1.16 公式参数名被单位替换吃掉

- **现象**：`minutes_per_page` 被换成 `min_per_page`，公式参数名对不上。
- **正确做法**：单位替换要有边界判断，不能贪心匹配参数名。
- **出处**：src/core/engine.ts:580

### 1.17 温度是仿射不是线性

- **现象**：`0 degC to K` 若按纯因子换算会错。
- **正确做法**：温度换算必须按 **offset + factor**（仿射）处理，不能只乘系数。
- **出处**：docs/单位体系-UCUM规格对齐.md

### 1.18 华氏/摄氏的「温差」与「绝对温度」是两个概念

- **现象**：`3 degF to degC` 返回 -16.1（绝对温度换算），但用户要的是温差 1.67。
- **正确做法**：温差换算与绝对温度换算必须区分；输入里只有单位时无法自动判别，需要提示。
- **出处**：本轮真实世界观压测发现

## 二、数值与精度

### 2.1 displayPrecision 是小数位，不是有效数字

- **现象**：语义曾写错过一次，导致显示位数全错。
- **正确做法**：`displayPrecision` = **小数点后几位**；`precision` = 计算精度（默认 64，**不要为好看调低**）。
- **出处**：src/core/format.ts:24

### 2.2 BigNumber 溢出

- **现象**：`(A/B - C/D)/(A/B)*100` 溢出。
- **根因**：作用域里的 JS number 没转 BigNumber。
- **正确做法**：入口处 `coerceScopeToBigNumber`，且必须**原地修改**（不能复制）。
- **⚠ 回归**：第一版复制了 scope，导致 `expressions` 批量的 `u=5 → u*3` 共享失效，27 项测试红。
- **出处**：docs/R48复测解读与修复.md

### 2.3 JSON.stringify(undefined).slice() 让测试自己崩

- **现象**：抛 `Cannot read properties of undefined`，看起来像产品缺陷，实际是**测试自己崩了**。
- **正确做法**：写断言时先判空，用 `String(x ? JSON.stringify(x) : 'ok')`。
- **⚠ 本项目已犯三次**（R49/R52/R53）。
- **出处**：AGENTS.md

### 2.4 超精度静默丢末位

- **现象**：`(10^100+1)-(10^100)` 在 64 位下就是 0——数学正确、工程上丢信息。
- **正确做法**：**必须提示**，不能静默。把末位不可信这件事说出来。
- **出处**：src/features/numeric/evaluate.ts

### 2.5 大整数判定写窄了

- **现象**：第一版只判 `^-?\d{16,}$`，30 位以上的整数全部落到错误分支。
- **出处**：src/features/numeric/evaluate.ts:178

### 2.6 递归解析先撞栈

- **现象**：项数与括号深度会**先于字符数**撞栈——实测 4950 项平铺就炸。
- **正确做法**：限制要看项数/深度，不只看字符串长度。
- **出处**：src/core/engine.ts:48

### 2.7 计算预算系数曾低估 20 倍

- **现象**：系数取 0.02，导致 1000 步时间轴被估成 0.4 秒（实际是秒级）。
- **正确做法**：**宁可高估也不要低估**——低估会让人以为可以随便跑。
- **出处**：src/compute-budget.ts:45

### 2.8 BigNumber 用在积分主循环 → 一次 SIR 要 29 秒

- **现象**：多状态 ODE 修好后，2000 步 SIR 实测 **29.3 秒**；同样的式子放进 `simulate` 只要毫秒级。
- **根因**：`Engine` 走 BigNumber，RK4 每步每状态各调一次 → 2000 × 4 阶 × 3 状态 = 2.4 万次 BigNumber 求值。**RK4 本身就是浮点运算，BigNumber 在这条路径上没有收益，只会把「能算」变成「算不完」。**
- **正确做法**：数值积分/迭代类路径用独立浮点 mathjs 实例 + 预先 `compile` 表达式；实测 **29317ms → 155ms（约 189 倍）**，数值完全一致（RK4 截断误差远大于 15 位）。与 `system-dynamics.ts` 的做法一致。
- **出处**：src/features/numeric/ode.ts、2026-11-27

### 5.10 带单位的除零没被拦，结果一路显示成 Infinity

- **现象**：`1/0` 会报 `non_finite`，但 `1 m / 0 s` 返回 **`Infinity 日行里快`** ——
  数值根本不可用，还带着被代换的中文单位名。
- **根因**：`evaluate` 的非有限检查**漏了 Unit 分支**：裸数字、字符串、BigNumber、复数
  都查了，唯独 `isUnit` 被排除（历史上单位值被认为「走另一条路」）。
- **正确做法**：Unit 也要查 `magnitude`（`toNumber()`）是否有限；单位不是免检通道。
- **出处**：src/features/numeric/evaluate.ts、test-v3/r109-composite-units.mjs、2026-11-27

## 三、架构与分发

### 3.1 参数取值重复 151 次

- **现象**：dispatch.ts 1436 行，`typeof args['x'] === 'number' ? (args['x'] as number) : undefined` 重复 **151 处**；第 428 行一行内联 14 个参数、2588 字符。
- **正确做法**：收敛到 core/args.ts（num/str/bool/rec/strList）。当前已接到 num 52 处、str 21 处、bool 21 处、rec 29 处、strList 5 处。
- **出处**：CHANGELOG 3.53.0 / 3.55.0

### 3.2 造了不用抽象（Speculative Generality）

- **现象**：bool/rec/strList 三个函数写完后**零调用方**。
- **正确做法**：code-review 的坏味道清单里「为不存在的需求加抽象 → 删掉它」；本项目选择接上真实调用方。
- **⚠ 更极端的一次**：给 engine.ts 加了 135 行转译机制，**干净对照实测完全没作用**，整段删除。
- **出处**：CHANGELOG 3.55.0 / 3.54.0 补记

### 3.3 正则批量替换生产代码会引入语义 bug

- **现象**：把 `x ? a : b` 批量替换后，`str(args,'id') ?? a ? b : c` 被解析成 `(x ?? a) ? b : c`，data get 的 id 变成 `note:undefined`。
- **正确做法**：批量替换后**必须跑全量测试**；涉及 `??` 与三目混用处要加括号。
- **出处**：CHANGELOG 3.53.0

### 3.4 一个 operation 一个 case → 58 个 case 在一个 1436 行文件里

- **正确做法**：新 operation 优先走独立模块 + dispatchNew 分发，不要再往 dispatch.ts 里堆。
- **出处**：架构审查（.scratch/reports/arch-review.html）

### 3.5 声明与实现不一致

- **现象**：文档/schema 声明了某个参数或能力，实际没实现。
- **正确做法**：r37/r88 系列测试专门核对「声明了但没做」；新增参数必须同步 schema + skill + help 三处。
- **出处**：docs/项目状态总结、r88-declaration-align

## 四、输出契约与错误语义（9 条）

### 3.1 NaN/Infinity 被当成字符串结果返回 ok=true

- **现象**：`1/0` 在单条被拦，但带单位时 `(1/0)*2 kg` 宣告成功，看起来像个正经结果。
- **根因**：`containsNonFinite` 只认恰好 `"Infinity"`，而 Unit 序列化成 `"Infinity g"`；复数被误判 non_finite。
- **正确做法**：`isNonFiniteValue` 下钻到 `Unit.value` 并在求值点直接判；识别复数（`sqrt(-1)` → `复数：1i`）；`1e400`/`2^1024` 这类有限大数不误判。
- **出处**：8fcc31f / v3.28.0、17a951a / v3.29.0

### 3.2 批量失败时顶层 ok 仍是 true

- **现象**：`result` 里写着「失败[unknown_symbol]」，而 `ok:true`、`error:undefined`。报告原话：「我多次写 `if (!r.ok)` 来判断成败，得到的结果是『永远成功』。」
- **根因**：`ok` 只看整体是否跑完，不看逐条结果。
- **正确做法**：`ok` 按失败数决定，补 `partial`/`failed`/`succeeded` 三个字段；刻意不塞 `error`（那是「批量里某条错」，不是「整个调用错」）。
- **出处**：5c05cbd

### 3.3 单条与批量的判定不一致

- **现象**：单条 `1/0` 报错，批量 `["1+1","1/0","sqrt(-1)","log(0)"]` 却宣告「算式全部求值成功（4 条）」。
- **根因**：两条路径各写了一套成功判定。
- **正确做法**：单条与批量共用同一判定。教训：**同一式子换个调用方式就从错变成对，而批量恰是 AI 最常用的形态**。
- **出处**：0678512

### 3.4 把「算得出来吗」和「符不符合判据」塞进同一个 ok

- **现象**：`{expr:'999999', sanity:{max:1000}}` → `items[0].ok = true`，越界了却说成功。
- **根因**：`ok` 的语义是「算得出来吗」，锚点越界是「算了但不符合判据」。
- **正确做法**：新增独立的 `sanityStatus`（passed/violated/incomparable/skipped）；**没给判据的条目不写该字段**（没检查 ≠ 检查通过）；量纲不可比较时必须给说明。
- **出处**：cef7fc8、18d8f60

### 3.5 读失败伪装成「空的」

- **现象**：`broken.json` 写成非法 JSON 后，`show` 返回 `ok=true` 并显示「物理常数：现实值（未改动）／星球参数：未设定」——用户以为工作区本来就是空的，不会去修。
- **根因**：`loadWorkspace` 的 catch 写着「损坏就当作空工作区，不抛错」。
- **正确做法**：三态 `ok`/`missing`/`corrupt`（ENOENT 是常态不报警），`corrupt` 时显式警告并给修法。**静默降级比报错有害：报错会让人修，伪装成「空的」会让人重建。**
- **出处**：3916ca5

### 3.6 算出来了但没呈现，用户以为没做

- **现象**：`world-map` 的 `climate:true` 数据一直生成，但只放在 `value.climate`、文本里没写 → 用户以为没生成。
- **根因**：`value`（数据通道）与 `result`（给人看的）分工没落实到每条新功能。
- **正确做法**：文本追加【气候层】；同类还有 `mapDistance` 只进 `value`。
- **出处**：d15824a / v3.43.2、5aecbbb / v3.21.0

### 3.7 internal 语义被滥用成「我也不知道为什么」

- **现象**：`to` 换算失败报 `internal`，而 `internal` 在本项目的约定里意思是「工具自己坏了」，会让人去重试。
- **根因**：真实原因有四类（单位名撞内置函数、裸数字无单位可换…），修法各不相同，却共用一个类型。
- **正确做法**：拆成 `unit_name_conflict` / `not_a_quantity` / `syntax` / `invalid_argument` 等，8 类失败全带 `{type,message,hint}`。
- **出处**：0678512、252e4e6 / v3.1.0

### 3.8 失败步骤的下游被当成「单位算式」算出合法结果

- **现象**：`["a=5","b=oops*2","d=b*2"]` → `d` 算出 `2 b`，汇总说「成功 2，失败 1」。
- **根因**：① 单位判据只看「同级有没有数字」不看顺序；② 赋值语句右半挂在 `value` 上，而 AST 遍历只走 `args/items/content/object/index`。
- **正确做法**：判据看顺序；遍历补上 `value` 分支。**「下游悄悄变虚成功」比报错难发现。**
- **出处**：c976158

### 3.9 出口不清理 undefined

- **现象**：`ledger` 出现致命错误，并连带产生 `[object Object]` 显示。
- **正确做法**：出口统一清理 `undefined`，并加「无损性守护」防止清理本身丢信息。
- **出处**：5ec8ea8 / v3.1.1（R48）

## 五、参数解析与声明一致性（5 条）

### 4.1 schema 声明了的键，代码从不读取

- **现象**：`{formula:'oxygen_depletion', overrides:{V:324375}, unitFrom:'L'}` 得到 `11353125 min`——与不传 `unitFrom` 完全相同（应为 `11353.125 min`，**差 1000 倍**）。同类：`customExpression` 是死键、52 个键被静默忽略。
- **根因**：`opFormula` 里根本没读这两个参数；schema 声明与实现是两份互不校验的文本。
- **正确做法**：语义定为「把所有**声明了单位的**数值参数按 `unitFrom→unitTo` 换算」，无量纲参数一律不参与（否则「人数 n=20」会被当成 `20 L`）。
- **出处**：2cdfec7、eb042a3 / v3.1.1、8dcc937 / v3.37.0

### 4.2 全局参数白名单 → 必须按 operation 分片

- **现象**：`world + unitFrom`、`units + planetMass`、`evaluate + diffA` 全部被静默接受。
- **根因**：只有一个全局白名单——只要键名在任何一个 operation 里合法就放行。
- **正确做法**：两段校验——解析前只查拼写，解析后查归属（属于别的 operation 就报 `not_in_operation`）。**分层是必要的**；并豁免 `world`/`expression`/`unitFrom+unitTo`（第一版没豁免，12 个套件红）。
- **出处**：84564c2

### 4.3 数组元素内部的未知键被静默忽略

- **现象**：`expressions` 元素里的未知键被吞掉；顶层严格拦截，元素内部不查。
- **正确做法**：该条失败并点名键名，其余条目不受影响。
- **出处**：5c05cbd

### 4.4 手写清单与实现漂移，功能静默变死功能

- **现象**：未知子命令提示硬编码 21 个名字，而实现有 29 个——`flip`/`trace`/`impact`/`cost`/`graph`/`heatmap`/`whitepaper`/`timeline`/`observer` 从此不可被模型发现。同类：`TOOL_DESCRIPTION` 漏了 `derivation`/`custom`/`feasibility`，而测试全绿。
- **正确做法**：单一来源（`DERIVATION_SUBCOMMANDS`），提示从它生成；测试**双向**比对；工具描述的 op 列表从 schema enum 派生。
- **出处**：9f1f85a、8722daa

### 4.5 宿主对输出做 additionalProperties:false 校验，测试路径绕过了它

- **现象**：v2.1.0 在任何环境安装都会失败——`notice` 与 `cached` 是产出字段却未在 output schema 声明。**77 套测试全绿，工具却根本调不动。**
- **根因**：测试直接调 `runMathTool` 检查返回对象，宿主的 schema 校验在这条路径之外。
- **正确做法**：integration 套件断言「`MathResult` 能产出的每个字段都在 schema 声明」。
- **出处**：dd506c4 / v2.1.1

## 六、测试与验证方法

### 5.1 只测一边——「该拒绝的拒绝了」但「该放行的也拒了」

- **现象**：修复越权/误伤类问题时，只验证了拦截侧，正常输入被一起拦掉。
- **正确做法**：每条断言成对：拒绝 + 放行。`stop-bleed` 79 项里明写「该拒绝的被拒绝（6 条跨 operation + 8 条非法参数）／合法输入不被误伤（17 条正常调用 + 7 条极端但合法）」。
- **出处**：AGENTS.md、84564c2

### 5.2 JSON.stringify(undefined).slice() 让测试自己崩

- **现象**：抛 `Cannot read properties of undefined`，第一反应是产品坏了。
- **正确做法**：用 `String(x ? JSON.stringify(x) : 'ok')`，写断言时先判空。**本项目已犯三次（R49/R52/R53）。**
- **出处**：AGENTS.md、42f68ed、745e7ef、d47ebd8

### 5.3 测试断言编码了旧行为，改对了反而红

- **现象**：修正精度语义与显示判据后，一批断言仍按旧行为写，逼着人想「放宽断言」。
- **根因**：测试写的是实现的当前形态，不是需求。
- **正确做法**：明确「改测试而不是放宽断言」——按新行为改写；并补上「直接断言真值在 1e-6 内」这类面向真值的断言。
- **出处**：faac524、ee9e0fc

### 5.4 随机生成用例与检测器共享词表，等于自证

- **现象**：400 个随机用例 400 个全对，看着很好——**这个数字毫无价值**。
- **根因**：生成器从检测器自己的词表取词，只能证明「词汇表覆盖了自己」。
- **正确做法**：重建批次，**绕开词表用场景描述**（「这堵墙要多厚才挡得住投石机」）。真实准确率只有 5/14，三轮盲测分别抓出「中文数词不识别」「工程词汇缺失」「文学描写被误报」三类缺口。
- **出处**：4eda638

### 5.5 测试共享全局 HOME 目录，套件互相污染

- **现象**：单跑绿、连跑红，或前一晚的数据影响今晚的结果。
- **正确做法**：每个套件独立临时目录；以 `test:report` 为准（旧 `run-all-tests.mjs` 在部分环境撞 `spawn EPERM`）。
- **出处**：AGENTS.md

### 5.6 忘了 npm run build 就跑测试

- **现象**：测试导入 `lib/`，改的是 `src/`，跑出来是旧行为。
- **出处**：AGENTS.md

### 5.7 只测 value 不测 result → 误判修复成功

- **现象**：`5 m/s` 的 `value` 是对的，`result` 仍是 `288.018 日行里快`；只看 `value` 就以为修好了。
- **正确做法**：**用户可见的 `result` 必须单独断言**；发布前必须装机实测。
- **出处**：77e649f / v3.2.1

### 5.8 用造出来的数据测，测不到真实写法

- **正确做法**：用**真实材料**当 fixture（本项目用 1106 万字架空设定），断言写**算术自洽性**而非「原文对不对」。
- **出处**：r100-realworld-fixtures

### 5.9 文档承诺的功能从未实现，测试只覆盖了简单形态

- **现象**：`help` 的 ode 条目写着「一阶方程组（SIR / 捕食模型）与二阶方程都能解」、`at` 精确取点、返回极值；实测**多状态必发散**，`at` 与极值在代码里**零处实现**。而 test-v3 里全部 ode 用例都是单状态（`dy/dt = -y`）。
- **根因**：`parseOde` 的正则带起止锚点，右端贪婪吃掉后面所有方程；`derivFn` 又对每个状态求同一个导数。只测单状态 → 永远绿。这是 AGENTS.md「提示词承诺未验证」的复发，也是本表 2.8 的伴生问题（多状态一修好就撞性能墙）。
- **正确做法**：**help 里出现的每个示例都要有一条守护测试**——SIR 三状态、`x'=y; y'=-x`、`dy/dx`、`at`、极值、缺初值各一条。新增 `test-v3/r102-ode-multistate.mjs` 26 项，用守恒/单调/周期等**定义性质**断言，不背数值。
- **出处**：src/features/numeric/ode.ts、test-v3/r102-ode-multistate.mjs、2026-11-27

## 七、数据一致性与算法

### 6.1 输出「看着合理」掩盖了公式级错误

- **现象**：t 分布 CDF 在 `t=0` 时给出 `0.000086` 而不是 `0.5`；`t=1, df=10` 差 17%。
- **根因**：用了正则化不完全 Gamma 函数，而 t 分布要的是不完全 Beta 函数——**不是精度问题，是用错了数学函数**。一直没被发现，因为 `0.999982` 看起来像个正常的 CDF 值。
- **正确做法**：换 jstat；顺带淘汰 `erf` 的近似式，精度提升 9 个数量级。教训：**要用定义性质验（`t=0` 必须等于 0.5），而不是看数值像不像**。
- **出处**：80f46b7

### 6.2 经验系数不能拍，必须拿真实锚点反算

- **现象**：熔点公式把「每原子结合能与 k_B·T_m 同量级」**记成了等式**，铁算出 32493 K，实际 1811 K——**差 18 倍**，而 3 万度「看着完全合理」。同类：生态承载力用「1% 光合效率」，而全球实际只有约 **0.11%**，高估 42 倍；波阻系数随手写 20，比文献差 3.4 倍。
- **正确做法**：用 12 种金属的实测值反算得 0.036（中位 0.0362）；用「M=0.90 时 C_Dw≈0.02」反算 K=5.93；生态改为按比例缩放地球实测 NPP。测试用**多种真实值反守**（5 种金属落在 8% 容差内）+ 反向断言（「铁不得算出 30 万 K」）。
- **出处**：054b7bd / v2.3.2、c8f38b0、v2.3.16

### 6.3 色带用绝对阈值，而海平面是分位数

- **现象**：SVG 地图渲染出来是噪声图，大片陆地落进「海」色带。
- **根因**：用绝对 0–1 阈值分档，而实际海平面是**分位数**（本例 0.647）。
- **正确做法**：统一换算成「高于海平面多少」再分档。
- **出处**：3818756 / v3.45.0

### 6.4 按 UTC 日切时间窗口，跨时区就取错日子

- **现象**：北京夏至算出「日出 20:46Z 晚于日落 11:46Z」（把次日日出算进来）；lat45 夏至日照 39.62h。
- **根因**：① 窗口按 UTC 24 小时切；② 日照用 `|set − rise|`，跨日/高纬时把次日日出算进来；正午高度用 UTC 12:00，北京夏至算出 −2.1°。
- **正确做法**：按**当地日**切窗口，时区默认由经度推算（每 15° = 1 小时）或 `timezoneMinutes` 指定；日照用当日太阳高度 5 分钟步长扫描；极昼/极夜明确给 24h/0h。
- **出处**：f66d0da / v3.38.0、2a2efb6 / v3.44.0

### 6.5 同一物理量在两个模块有两套口径

- **现象**：ship 排水量用 `t`、公式库用 `kg`，差 99.9%；「一年天数」一处用秒一处用天，**换算方向反了**。
- **根因**：两处实现各自写死单位，数字碰巧在某点上一致，于是没人发现。
- **正确做法**：修正口径，并纳入 `crosscheck`（5 项同一物理量两份实现比对）作为常驻守护。
- **出处**：b00073f / v3.1.0

### 6.6 索引表「后者覆盖前者」且不报错，公式被静默吃掉

- **现象**：`spring_energy`、`lc_resonance`、`thermal_stress`、`city_wall_perimeter` 4 个 id 被覆盖，永不加载。症状只是「按名字查不到」和 `FORMULAS.length` 比预期少 4——**少 4 没人会注意**。
- **正确做法**：删掉 4 条重复副本，新增 `formula-integrity.mjs`（id 唯一、INDEX 与数组一致、字段完整）。
- **出处**：v2.3.23

### 6.7 路径与排序的隐性错误

- **现象**：① 数据层出现重复 `datastore` 子目录；② 归档读取按降序返回，`compare` 取到旧版；③ 所有工作区共用一个 datastore，w2 能查到 w1 的记录；④ `putRecord` 每条全表重读，5000 条写入 52s。
- **正确做法**：修目录拼接、读取改版本升序、每工作区独立目录（旧数据首次访问迁移一次）、`putRecord` 用缓存查重（52s → 9s）。
- **出处**：e676fed、0d09ea9 / v3.1.0、17a951a / v3.29.0、58afbd7 / v3.29.2

## 八、流程与工具链

### 7.1 注释里写字面量「星号紧跟斜杠」会提前闭合块注释

- **现象**：在注释里描述这几个字符，直接把文件写坏，整段编译失败，**报错行号不等于出错位置**。
- **正确做法**：用文字描述，不写字面量。`doccheck` 现在有**块注释提前闭合检测**。
- **⚠ 写这条检查的人自己又踩了三次同一个坑。**
- **出处**：18c41e5 / v3.56.0

### 7.2 core.hooksPath 写成相对路径，钩子静默不执行

- **现象**：装了 pre-commit 却毫无作用，**实测提交直接通过才发现**。
- **根因**：`hooksPath` 相对 git 根解析，而仓库根是 `D:/0cengxu/5`、钩子在 `dsh-math-calculator/.git-hooks`。
- **正确做法**：必须用绝对路径。配套教训：钩子只跑秒级检查，**不含 10 分钟的全量测试**——否则人会习惯性 `--no-verify`。
- **出处**：18c41e5 / v3.56.0

### 7.3 大段插入挤掉相邻的 JSDoc

- **现象**：`doccheck` 红，导出注释被新代码覆盖。
- **正确做法**：改完立刻跑 `doccheck`，它会逐一点名。**本项目第二次犯**（一次连续挤掉 7 处）。
- **出处**：AGENTS.md、v2.3.23

### 7.4 为假想需求造抽象，留下无法验证的死代码

- **现象**：① `chain-runner.ts` 约 400 行自动执行器；② `engine.ts` 135 行复合单位转译机制；③ `suggestOperation` 5 条规则**从未被调用**。
- **根因**：写之前没有先用数据验证需求成不成立。实测：22 条链 / 259 步里只有 9 步声明了依赖（3.5%）——**「链」是主题分组不是依赖链**；135 行转译经**干净对照实测完全不影响行为**。
- **正确做法**：先实测再写；写不出对照实验的抽象就删掉。三者最终都被整段删除。
- **出处**：v2.3.22、4c1f733 / v3.54.0 补记、v3.50.0

### 7.5 git add -A 把私有文件提交进去

- **正确做法**：**永远只用显式文件列表**。
- **出处**：AGENTS.md

### 7.6 git reset --hard 会丢掉未提交的代码

- **现象**：本轮一次 `reset --hard` 把刚写的检查代码一起丢了，重写了一遍。
- **正确做法**：reset 前先 `git stash` 或确认工作区干净。

### 7.7 版本号虚高

- **现象**：npm 只发到 3.1.0，之后 70 条改动全按 minor 递增到 3.56.0，编号与实际改动量脱节。
- **正确做法**：一个版本对外发布一次；未发布的累积改动归并成一条。
- **出处**：6e70a9b / v3.2.0

### 7.8 推送经常失败（网络）

- **正确做法**：用 `bash .scratch/push-retry.sh` 重试；常见 `code 128` + `credential-manager` 提示（可忽略）。

### 7.9 /tmp 在 Windows 下是映射路径

- **现象**：`/tmp/x` 实际是 `C:/Users/<用户>/AppData/Local/Temp/x`；`os.tmpdir()` 还返回过异常值。
- **正确做法**：需要真实路径时用 `process.cwd()` 确认，或直接写绝对路径。

## 附一：本表的维护

- **新增一条的时机**：修完一个 bug，问自己「这个错误以后还会不会再犯？」会 → 加一条。
- **判断标准**：根因有**普遍性**才收；一次性参数调优不收。
- **优先做成检查**：机械性错误（固定语法、禁用 API、文件位置）→ 写进 linter/钩子，不要只写进本表。
- **本表只收判断类**：跨文件一致性、风格匹配这类**没法自动检查**的。

> 原则（借 `/retro`）：**机械错误做自动检查，判断问题写规范**。

## 附二：相关检查工具（都已存在，别重复造）

| 命令 | 检查什么 | 何时跑 |
|---|---|---|
| `npm run typecheck` | 类型 | 每次改 src/ |
| `npm run doccheck` | 注释覆盖 + 块注释提前闭合 | 大段插入后 |
| `npm run preflight` | 版本三处一致、清单声明、peer 依赖 | 提交/发布前 |
| `npm run test:report` | 全量 159 套 | 改完逻辑 |
| `.git-hooks/pre-commit` | 前三项（自动） | 每次 git commit |

> 若 `git commit` 没输出 `[pre-commit]`，说明钩子配置丢了：
> `git config core.hooksPath "$(pwd)/.git-hooks"`
