# 联网联动方案设计与价值验证

> 状态：**方案稿，未实现**。本文回答两个问题：怎么做、值不值得做。
> 背景：实测报告 3.2 提出「缺少量级合理性的外部锚点校验」，建议工具提供
> `sanity: { max: 1e10, note: "帝国星界军总规模" }` 之类的能力。

---

## 一、先厘清：报告要的东西分两种，价值差别很大

报告 3.2 原话：

> 工具能算出 `1e8 * 25000 = 2.5e12`，但**不会提醒「这个数比帝国星界军总人口（1e10）还大 250 倍」**。

这句话里其实藏着两件事：

| # | 能力 | 数据来源 | 价值 |
|---|---|---|---|
| **A** | 调用方**自己给锚点**，工具比对 | 调用方传入 | **高**，且零风险 |
| **B** | 工具**自己去网上查**锚点 | 联网检索 | **低**，且高成本 |

**A 是本地能力，不需要联网。B 才是「联网联动」。**

本项目的立场（历次确立）：**本地执行、不联网、不猜**。
所以下面的方案严格区分这两层，先做 A，B 单独立项。

---

## 二、A 层：锚点校验（不需要联网）

### 2.1 接口设计

```json
{
  "operation": "evaluate",
  "expressions": [
    {
      "label": "日产台数",
      "expr": "1e8*25000",
      "sanity": { "max": 1e10, "note": "帝国星界军总规模" }
    }
  ]
}
```

支持四种边界，都是**可选**：

| 键 | 含义 | 典型用途 |
|---|---|---|
| `max` | 超过则提示 | 「日产台数不该超过总人口」 |
| `min` | 低于则提示 | 「这棵树总不至于一年结 0.001 个果」 |
| `expect` | 期望量级（10 的幂） | 「这个数应该落在 10⁴」 |
| `note` | 提示时引用的依据 | 让警告有出处，不是玄学 |

### 2.2 输出形态

```
日产台数（1e8*25000） = 2500000000000 (~10¹²)
⚠ 超过锚点上限 1e10（帝国星界军总规模）达 250 倍；
  若这个数要写进设定，请先确认口径。
```

### 2.3 为什么这条能成立、而「自动判断量纲」不能

报告 3.1 建议「工具检测 kg/day 与 unit/day 不同量纲就拒绝比较」——那条我做不了，
因为**工具不知道你在做比较**（`expressions` 里每条是独立求值）。

但 `sanity.max` 能成立：**调用方显式声明了「我认为它不该超过这个数」**。
工具只做一件事——比对。判据来自调用方，不来自工具的猜测。

这正好符合本项目一贯的取向：**不猜，只说明代价**。

### 2.4 实现成本

| 项 | 工作量 |
|---|---|
| 参数解析与校验 | 小（约 40 行） |
| 与防呆层的 warning 汇总 | 小（复用既有 `magnitudeWarnings` 通道） |
| 元素级未知键（已修） | 已完成 —— `sanity` 加进去不会静默失效 |
| 测试 | 中（约 25 条断言） |
| **合计** | **半天内** |

### 2.5 价值验证方法

**这一步是本文最重要的部分——先验证，再实现。**

用**历史实测数据回放**，不用虚构案例：

本次报告记录了三类「工具没提醒、人也没发现」的错误，全都可用锚点挡住：

| 案例 | 算出的值 | 应有的锚点 | 能否拦住 |
|---|---|---|---|
| 1 亿棵树日产 2.5×10¹² 台 | 2.5e12 | `max: 1e10`（星界军总规模） | ✅ 拦 |
| 规模 × 密度 × 高度 / 10⁹ | 2133（被当成万吨） | `expect: 10³`（千吨） | ✅ 拦 |
| 「产能表 9 万吨/日」vs「单果 0.25 台/日」 | 36 万倍 | 无锚点可设（**量纲不可比**） | ❌ 拦不住 |

**第 3 行是关键**：它说明锚点能挡住报告里 3 例中的 2 例，
**但挡不住「拿两个不同量纲的数直接比」** —— 而那正是报告 1.2 号错误（也是最严重的自省）。

所以 A 层的诚实定位是：

> **它能挡住「数量级荒谬」，挡不住「量纲不可比」。**

验证方法：把这 3 条写成测试用例，A 层实现前后各跑一次，
看「拦住数」是 2/3 还是更低。**如果低于 2/3，就不值得做。**

## 三、B 层：联网查锚点（本文需要你决策的部分）

### 3.1 三种可能的形态

**形态 1：插件内发起请求**

```ts
// 工具内部直接 fetch 外部 API
const anchor = await fetchWikipedia('帝国星界军总规模')
```

**问题（致命）**：

- 插件是**本地执行、不联网**的定位。开这个口子等于改定位。
- 无网络环境直接报错或超时，破坏「工具永不抛异常」的约定。
- 无法控制成本：每次调用都可能触发一次外网请求。
- **不确定性强**：搜索结果可能变、可能被墙、可能有注入。

**结论：不建议做。**

**形态 2：工具只「建议查什么」，不查**

```json
// 输出里给一行：
// 建议核实：单棵树日产 2.5 万台 —— 可用 web_search 查「帝国编制规模」
```

- 零网络风险，成本为零。
- 但**价值也接近零**：模型本来就知道该查，它不缺这个提示。
- 且容易变成噪音（每条都建议查）。

**结论：价值低，不值得做。**

**形态 3：宿主层联动（DSH 侧）**

插件不联网，但**宿主**把 `web_search` 的结果作为 `variables` 传进来：

```json
{
  "operation": "evaluate",
  "expression": "1e8*25000",
  "variables": { "IMPERIAL_ARMY_TOTAL": 1e10 },
  "sanity": { "max": "IMPERIAL_ARMY_TOTAL" }
}
```

- 联网发生在宿主层，**插件仍是纯本地**。
- 锚点由谁查、查得准不准，责任清晰（在编排层）。
- 与本项目定位**不冲突**。

**结论：这是唯一在定位上站得住的形态。**

### 3.2 形态 3 的必要性判断

但这会引出一个更根本的问题：**形态 3 需要「变量引用」这个能力**，
而 `sanity.max` 目前只接受字面数字。

于是成本链条变成：

```
联网联动（形态 3）
  → 需要 sanity 支持变量引用
    → 需要 sanity.max 接受字符串键名并解析
      → 需要定义「变量找不到时怎么办」（报错？还是放过？）
```

每多一层，出错面就多一块。而收益只有一句：

> 「锚点可以由编排层查好后传进来」

**我的判断：形态 3 可以做，但应该排在 A 层之后，且不做变量引用。**

理由：调用方既然能联网查到 `1e10`，它直接写 `"max": 1e10` 就行 —— 
**多绕一层变量引用，除了让参数更难写，没有增加任何能力。**

## 四、结论与建议

| 层 | 做不做 | 理由 |
|---|---|---|
| **A：锚点校验（`sanity`）** | **建议做** | 零风险、半天成本；能挡住报告 3 例中的 2 例 |
| B-形态1：插件内联网 | **不做** | 改定位、破坏稳定性、不可控成本 |
| B-形态2：只给「建议查什么」 | **不做** | 价值接近零，易成噪音 |
| B-形态3：宿主联动传变量 | **暂不做** | 能力的本质是 A 层；变量引用只是包装，只增加出错面 |

### 一句话

> **联网能让工具「知道更多数」，但不能让它「更会判断」。**
>
> 报告里最严重的错误（拿吨和台直接比）不是**信息不足**，是**判断失衡**。
> 联网补不了这个 —— 补上它的是调用方自己声明锚点，然后工具老实比对。

---

## 五、如果决定做 A 层，验收标准

1. **拦住数 ≥ 2/3**：用上面三个历史案例回放，至少拦住 2 个。
2. **零误报**：`sanity` 不传时不产生任何新警告（与现状完全一致）。
3. **不猜**：警告文本必须引用调用方给的 `note`，不自己编依据。
4. **不破坏不变量**：`sanity` 不进缓存键（它只影响提示，不影响数值）；
   同一表达式传不同 `sanity` 得到不同提示，但**结果数字必须完全一致**。

第 4 条是必须守的——否则「同输入同输出」会被一个纯提示参数破坏。
