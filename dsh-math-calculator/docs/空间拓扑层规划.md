# 空间拓扑层规划（entity_topology）

> 起因：用户指出「拓扑模型」指的是**实体的空间拓扑**（地质地形、建筑、载具、各种实体的几何与连通结构），
> 而几何层（距离/行军/遮蔽）只是它的**自然延伸**，不是独立功能。
>
> 我在第一轮把「拓扑」误当成「依赖传导图」做掉了，**少了这一半**。
> 两者互相独立，**都要做**。

## 一、四个能力的分界（这一节是为了不再搞混）

| 能力 | 回答什么 | 有空间吗 | 现状 |
|---|---|---|---|
| `world` 的 `terrain` | 某个纬度/海拔的**局地气候**（日照、气温） | ❌ 无位置 | ✅ 已有 |
| `hierarchy` | 一个编制**多少人** | ❌ 无位置 | ✅ 已有 |
| `dependency` | 改 X 会**传导到谁**（含环/层深/跨度） | ❌ 无位置 | ✅ 已有（本轮刚做，原名 topology 已改） |
| **`entity_topology`** | **A 到 B 多远、中间隔着什么、能不能过、看不看得见** | ✅ **有** | ❌ **缺** |

**为什么前三个替代不了第四个**：

```
dependency  问「重力变了，山高上限变多少」     → 关系，不关心在哪里
entity_top  问「从帝都调兵到南极煤田要几天」   → 位置、路径、地形阻力
```

## 二、它要覆盖的实体类型

| 类型 | 拓扑内容 | 典型问题 |
|---|---|---|
| **地形** | 区域划分、高程、地貌、相邻关系、可通行性 | 从 A 城到 B 城走哪条路？雨季哪段会断？ |
| **建筑** | 楼层、房间、门窗、楼梯、通道 | 从大门到王座要过几道门？哪层是死路？ |
| **载具** | 舱室、管道、竖井、可达性 | 从货舱到驾驶室要经过哪些舱？ |
| **通用** | 节点 + 空间关系（相邻/包含/连通/阻塞） | 某点被毁，哪些区域失联？ |

## 三、几何层是它的自然延伸（不是独立功能）

用户明确指出：几何层（距离/行军/遮蔽）**只是地形拓扑的自然延伸**。

所以不单独立项，而是 `entity_topology` 的查询项：

```
① 距离      两点间最短路径长度（按地形加权，非直线距离）
② 行军      距离 ÷ 该地形速度系数 → 天数
③ 遮蔽      两点间视线是否被高地阻挡（地形遮蔽）
④ 视域      某点能看到哪些区域（反向：哪些点能看到它）
⑤ 连通      某个节点被毁，哪些区域失联（图的连通分量）
⑥ 通行      这条路径对某类载具是否可走（桥梁/隧道/坡度约束）
```

报告里那条「几何层 3 天 / 数据量仅 16–32 KB」的评估**仍然成立**，
只是它的位置从「第四梯队独立能力」改成「`entity_topology` 的查询项」。

## 四、数据结构草图

```jsonc
{
  "entity_topology": {
    "kind": "terrain",           // terrain | building | vehicle | generic
    "nodes": [
      { "id": "帝都",   "x": 0,   "y": 0,   "elevation": 50,  "terrain": "plain" },
      { "id": "南极煤田", "x": 900, "y": 1200, "elevation": 800, "terrain": "mountain" },
      { "id": "雪岭",   "x": 450, "y": 600,  "elevation": 3000, "terrain": "mountain" }
    ],
    "edges": [
      { "from": "帝都", "to": "雪岭",     "lengthKm": 620, "passable": true, "cost": 2.5 },
      { "from": "雪岭", "to": "南极煤田", "lengthKm": 900, "passable": true, "cost": 2.5 }
    ],
    "query": {
      "from": "帝都",
      "to": "南极煤田",
      "mode": "march",            // march | sight | reach
      "speedKmPerDay": 30,
      "terrainMultiplier": { "plain": 1.1, "mountain": 2.5 }
    }
  }
}
```

**输出**：

```
路线：帝都 → 雪岭 → 南极煤田
  直线距离  1,230 km
  地形加权  3,100 km（山地 ×2.5）
  行军天数  103 天（30 km/日）
  遮蔽：雪岭（海拔 3000m）位于两点连线中点，**视线被阻挡**
  ⚠ 若走直线需翻越雪岭，报告中「14,880 km 直达」的说法需要核实
```

## 五、实现顺序与成本

| 步骤 | 内容 | 成本 | 判据 |
|---|---|---|---|
| **1** | 数据模型 + 路径查询（距离/连通/失联） | 1.5 天 | 能答「从 A 到 B 怎么走」 |
| **2** | 地形速度系数 + 行军天数 | 0.5 天 | 能答「调兵要几天」 |
| **3** | 遮蔽与视域 | 1 天 | 能答「那里看不看得见」 |
| **4** | 建筑/载具的层与舱室语义 | 1 天 | 能答「从大门到王座几道门」 |
| **合计** | | **4 天** | |

## 六、明确不做的部分

```
✗ 真实地理数据（经纬度/真实高程）  —— 那是外部数据源的事，本工具只算给它的结构
✗ 3D 渲染与坐标可视化           —— 用户已砍 UI
✗ 自动生成地形                   —— 那是叙事选择，不是计算
✗ 与 world 的 planet 参数耦合     —— 保持独立：拓扑是结构，world 是物理
```

## 七、一处需要先确认的判断

**路径数据从哪来？** 三种可能：

1. **用户手写**（最现实）：给节点与边，工具只算路径与行军
2. **从设定文本抽**（依赖 `extract_numbers` 的思路）：从「帝都到南极煤田 14,880 km」抽出边
3. **规则生成**：给区域格点与高程函数，自动连边

我建议**先做 1**，因为 2 与 3 都要依赖 1 的数据结构。而且在 99层、蒸汽朋克
这些项目里，作者本来就写有距离表（报告里引过「帝都→南极煤田 14,880 km」），
只是没有工具能拿它算路径。

## 八、与现有能力的关系

```
extract_numbers   从设定文本抽出「帝都到南极煤田 14,880 km」
       ↓
entity_topology   把这些数字变成图，算路径/行军/遮蔽
       ↓
dependency        若某段路被毁，影响哪些下游设定（抽象传导）
       ↓
consistency       检查同一段距离在多处是否一致
```

**四者串起来才是完整的空间推演**，缺任何一环都只能得到片段。
