# 空间拓扑层规划（entity_topology）

> 起因：用户指出「拓扑模型」指的是**实体的空间拓扑**（地质地形、建筑、载具、各种实体的几何与连通结构），
> 而几何层（距离/行军/遮蔽）只是它的**自然延伸**，不是独立功能。
>
> 我在第一轮把「拓扑」误当成「依赖传导图」做掉了，**少了这一半**。
> 两者互相独立，**都要做**。

## 一、四个能力的分界（这一节是为了不再搞混）

| 能力 | 回答什么 | 有空间吗 | 现状 |
|---|---|---|---|
| `world` 的 `terrain` | 某个纬度/海拔的**局地气候**（日照、气温） | ❌ 无位置 | ✅ 已有 |
| `hierarchy` | 一个编制**多少人** | ❌ 无位置 | ✅ 已有 |
| `dependency` | 改 X 会**传导到谁**（含环/层深/跨度） | ❌ 无位置 | ✅ 已有（本轮刚做，原名 topology 已改） |
| **`entity_topology`** | **A 到 B 多远、中间隔着什么、能不能过、看不看得见** | ✅ **有** | ❌ **缺** |

**为什么前三个替代不了第四个**：

```
dependency  问「重力变了，山高上限变多少」     → 关系，不关心在哪里
entity_top  问「从帝都调兵到南极煤田要几天」   → 位置、路径、地形阻力
```

## 二、它要覆盖的实体类型

| 类型 | 拓扑内容 | 典型问题 |
|---|---|---|
| **地形** | 区域划分、高程、地貌、相邻关系、可通行性 | 从 A 城到 B 城走哪条路？雨季哪段会断？ |
| **建筑** | 楼层、房间、门窗、楼梯、通道 | 从大门到王座要过几道门？哪层是死路？ |
| **载具** | 舱室、管道、竖井、可达性 | 从货舱到驾驶室要经过哪些舱？ |
| **通用** | 节点 + 空间关系（相邻/包含/连通/阻塞） | 某点被毁，哪些区域失联？ |

## 三、几何层是它的自然延伸（不是独立功能）

用户明确指出：几何层（距离/行军/遮蔽）**只是地形拓扑的自然延伸**。

所以不单独立项，而是 `entity_topology` 的查询项：

```
① 距离      两点间最短路径长度（按地形加权，非直线距离）
② 行军      距离 ÷ 该地形速度系数 → 天数
③ 遮蔽      两点间视线是否被高地阻挡（地形遮蔽）
④ 视域      某点能看到哪些区域（反向：哪些点能看到它）
⑤ 连通      某个节点被毁，哪些区域失联（图的连通分量）
⑥ 通行      这条路径对某类载具是否可走（桥梁/隧道/坡度约束）
```

报告里那条「几何层 3 天 / 数据量仅 16–32 KB」的评估**仍然成立**，
只是它的位置从「第四梯队独立能力」改成「`entity_topology` 的查询项」。

## 四点五、开源调研结果（2026-11-12 实地核查）

> 用户要求：检索拓扑模型有没有现成的代码。
> 结论：**图算法有成熟库可用，空间语义要自己写。**

### 4.5.1 三个层次的候选

| 层次 | 候选 | 版本/更新 | 周下载 | 许可 | 判断 |
|---|---|---|---|---|---|
| **图算法** | `graphology` | 0.26.0 / **2 年前** | **2,212,654** | **MIT** | ✅ 可用，但需注意停更风险 |
| 图算法 | `graphology-library` | 聚合包 | — | MIT | ✅ 一次性拿到全部算法 |
| **地理几何** | `@turf/turf` | 7.4.0 / 3 个月前 | **2,313,537** | **MIT** | ✅ 地理坐标场景首选 |
| 路径 | `node-dijkstra` | 2.5.1 | — | MIT | ✅ 任意加权边，不限坐标系 |
| 三角/多边形 | `d3-polygon` / `point-in-polygon` | — | — | ISC/MIT | ⚠️ 太底层，只有在做视域时用得上 |

### 4.5.2 `graphology` 覆盖了我要的全部算法

它的标准库模块清单（实地读自 graphology.github.io）：

```
components      连通分量（strong/weak）        → 我要的「某节点被毁，哪些区域失联」
dag             环检测 + 拓扑排序              → 我要的「依赖成环」
shortest-path   Dijkstra / A*                 → 我要的「A 到 B 最短路径」
traversal       BFS / DFS                     → 我要的水平扩散
metrics         density / centrality / modularity → 结构体检（关键节点识别）
simple-path     所有路径                      → 「有几条路可走」
```

**这意味着「图的骨架」完全不用自己写。** 我本轮手写的
`traverse`／`findCycles`（约 80 行）都是在重新发明这些。

### 4.5.3 `@turf/turf` 覆盖了地理几何，且有一个关键函数

实地读 Turf 7.4.0 的 API 清单，与我们需求对应的：

| Turf 函数 | 对应我们的查询 |
|---|---|
| `distance` | 球面/平面距离（两点直线） |
| `length` | 折线总长（路径长度） |
| **`shortestPath`** | **避开障碍物的最短路径**（栅格矩阵，`resolution` 控制精度） |
| `booleanPointInPolygon` | 某点在哪个区域内 |
| `pointToPolygonDistance` | 点到区域边界的距离（「离边境多远」） |
| `lineIntersect` | 两条路径是否相交（「这条路会不会被截断」） |
| `along` / `midpoint` | 沿路径取点（「行军到第 3 天在哪」） |
| `isolines` / `isobands` | 等值线（「等温线/等高线」） |
| `voronoi` | 泰森多边形（「最近的城市是哪个」） |
| `hexGrid` / `squareGrid` | 栅格化（把区域切成格点） |

**`shortestPath` 是意外收获** —— 我原计划自己写栅格寻路，而 Turf 直接提供了
「绕开障碍物的最短路径」，正是地形绕行需要的。

### 4.5.4 但有两件关键的事没有现成库

#### ① 视线/遮蔽（viewshed / isovist）

我搜了 npm 的 `isovist` / `visibility polygon` / `viewshed`，
**没有找到成熟的 JS 库**。找到的都只是底层几何（`d3-polygon`、`point-in-polygon`），
需要自己实现视域算法。

**结论：遮蔽与视域必须自己写**（约 150 行：射线投射 + 分段求交）。

#### ② 地形语义（什么地形多快、能不能过）

没有任何库知道「山地行军 ×2.5」「沼泽 ×3」「骑兵不能过密林」——
这是**领域知识**，不是几何。

**结论：地形系数表要本项目自己定**（这也是它作为世界观工具的价值所在）。

### 4.5.5 我的选型判断

```
┌─ 局部坐标（建筑/载具/单块大陆）────────────────────┐
│  graphology + graphology-library                  │
│  理由：任意节点属性、任意加权边，不假设地理坐标     │
│  风险：2 年未更新（但 MIT，可 fork）               │
└───────────────────────────────────────────────────┘

┌─ 地理坐标（整颗行星/大洲）────────────────────────┐
│  @turf/turf                                       │
│  理由：球面距离、绕障路径、多边形关系全都现成       │
│  优势：231 万周下载，活跃维护                       │
└───────────────────────────────────────────────────┘

┌─ 视线与遮蔽（两种情况都要）──────────────────────┐
│  自己写（约 150 行射线投射）                       │
│  理由：npm 上没有成熟实现                          │
└───────────────────────────────────────────────────┘

┌─ 地形系数与通行规则 ──────────────────────────────┐
│  自己定（这是领域知识，也是本工具的差异化价值）     │
└───────────────────────────────────────────────────┘
```

### 4.5.6 引进外部依赖的代价（必须说清）

本项目目前**零依赖**（除 mathjs）。引入图库与几何库会带来：

| 代价 | 说明 | 缓解 |
|---|---|---|
| 包体积 | `@turf/turf` 全家桶很大（117 个依赖） | 用**子包**：只装 `@turf/shortest-path`、`@turf/distance` 等 |
| 依赖链风险 | Turf 117 个依赖；graphology 1 个 | Turf 用子包可大幅降低 |
| 停更风险 | graphology 2 年未更新 | MIT，必要时 fork 或自己写（算法本身约 300 行） |
| 「假关系」风险 | 外部库不理解世界观语义 | 库只做算法，语义层永远在本项目 |

**建议**：先只引 `graphology`（1 个依赖、纯算法、体积小）。
Turf 只在真需要球面地理计算时再引，且只引子包。

## 六、明确不做的部分

```
✗ 真实地理数据（经纬度/真实高程）  —— 那是外部数据源的事，本工具只算给它的结构
✗ 3D 渲染与坐标可视化           —— 用户已砍 UI
✗ 自动生成地形                   —— 那是叙事选择，不是计算
✗ 与 world 的 planet 参数耦合     —— 保持独立：拓扑是结构，world 是物理
```

## 七、一处需要先确认的判断

**路径数据从哪来？** 三种可能：

1. **用户手写**（最现实）：给节点与边，工具只算路径与行军
2. **从设定文本抽**（依赖 `extract_numbers` 的思路）：从「帝都到南极煤田 14,880 km」抽出边
3. **规则生成**：给区域格点与高程函数，自动连边

我建议**先做 1**，因为 2 与 3 都要依赖 1 的数据结构。而且在 99层、蒸汽朋克
这些项目里，作者本来就写有距离表（报告里引过「帝都→南极煤田 14,880 km」），
只是没有工具能拿它算路径。

## 八、与现有能力的关系

```
extract_numbers   从设定文本抽出「帝都到南极煤田 14,880 km」
       ↓
entity_topology   把这些数字变成图，算路径/行军/遮蔽
       ↓
dependency        若某段路被毁，影响哪些下游设定（抽象传导）
       ↓
consistency       检查同一段距离在多处是否一致
```

**四者串起来才是完整的空间推演**，缺任何一环都只能得到片段。
