# 数据管理：开源学习与改造（2026-11-16）

> 用户：「数据管理比较粗糙，学学成熟的开源」。先评估候选，再说明学到了什么、改了什么。

## 一、候选评估

| 库 | 版本/许可/体积 | 能力 | 判断 |
|---|---|---|---|
| **@seald-io/nedb** | 4.1.2 / MIT / 715KB | 嵌入式文档库：查询（$in/$regex）、索引、**append-only 日志 + 自动压缩**、崩溃恢复 | ✅ **主要学习对象**（形态与我们最像） |
| lowdb | 7.0.1 / MIT / 23KB | JSON 文件 + 适配器 + 极简 CRUD | ⚪ 太薄（无查询/索引/压缩） |
| pouchdb | 9.0.0 / Apache / 5.5MB | 离线同步文档库 | ❌ 重量级，同步能力我们不需要 |
| sql.js | 1.16.0 / MIT / **31MB** | WASM SQLite | ❌ 体积不可接受 |
| alasql | 4.22.2 / MIT / 10MB | JS 里的 SQL | ❌ 体积 + 解析开销 |

**结论：不引依赖**（715KB 对插件的「零依赖倾向」偏重），**学它的三项机制自己实现**。

## 二、学到了什么（具体）

| nedb 的机制 | 我们原来的做法 | 改造后 |
|---|---|---|
| **append-only 日志 + compaction** | 纯追加，文件无限增长 | 加 `compact(threshold)`：超阈值只留最新版，旧档存 `.bak` |
| **索引缓存** | 每次查询全文件解析 | `readRecordsCached`：按文件 mtime 复用解析结果 |
| **按版本回放**（文档库的多版本思路） | 只能取最新版 | `getRecordVersion(id, version)`：从日志回放历史 |
| 查询语言（$in/$regex） | 只有 kind/tag/name 精确过滤 | 暂不引入（我们的场景够用；引入反而增加学习成本） |

## 三、为什么不全盘照搬

1. **体积**：nedb 715KB，而我们的整个数据层不到 300 行——引依赖不如借机制；
2. **查询语法**：Mongo 风格 `$in/$regex` 对「记录少、结构固定」的场景是负担；
3. **崩溃恢复**：nedb 有 fsync 与 WAL；我们接受「手工编辑容错 + 坏行跳过」的轻量策略（文件本身是人类可读的）。

## 四、改完后的数据层

```
<workspace>.artifacts/datastore/
  records.jsonl       ← append-only 日志（每行一条记录）
  records.jsonl.bak   ← 压缩前的旧档
```

| 能力 | 说明 |
|---|---|
| 版本 | 同名再写递增 version；可取任意历史版本 |
| 血缘 | refs 上下游查询 |
| 查询 | kind / tag / 名称子串 / 引用谁（带缓存） |
| 压缩 | 超阈值 compaction，避免文件膨胀 |
| 导入导出 | JSON 数组，同 id 按版本高者胜 |

## 五、三件「还需要的功能」：有没有现成开源方案？

| 需求 | 现成方案 | 判断 |
|---|---|---|
| **全文检索** | **minisearch**（MIT，5KB，已装）配 **segmentit**（中文分词）；备选 flexsearch（2.3MB）、orama（2.2MB）、fuse.js（417KB 模糊）、lunr（976KB） | ✅ **已有且已在用**（公式检索 `features/formulas/query.ts` 就用这一套）——数据层直接复用，不新引 |
| **自动入库（saveAs）** | 无「业务无关」的现成库；最接近的是持久化中间件 **redux-persist** / **zustand persist**（状态变更自动落盘） | ⚠️ 学其「写操作统一走持久化层」的形态；工具侧实现为 `saveAs` 参数（30 行） |
| **迁移旧数据** | **umzug**（MIT，139KB，通用迁移引擎：版本化迁移脚本 + executed 记录 + 幂等）；备选 db-migrate / knex migrations | ⚠️ 学其「幂等 + 已执行记录」；我们的迁移是一次性 JSON 合并，写 60 行即可，不引 139KB |

**结论**：只有「全文检索」有值得直接用的成熟库（且已装）；另两项没有通用库、只有可借鉴的形态。
