# 把公式库与世界观推导深度耦合 —— 现状核查与方案

> 本文回答一个问题：**「成体系化的数据库才是世界观推导的本体」这句话，具体到代码上要改什么。**
> 所有数字都来自实测对账，不是推测。

---

## 一、先看现状：两边各算一套，数字碰巧一致

### 1.1 实测对账

我用 `world` 操作与公式库分别算同一批物理量（地球参数）：

| 量 | `world` 输出 | 公式库复算 | 一致？ |
|---|---|---|---|
| 表面重力 | 9.82 m/s² | 9.8203 | ✓ |
| 逃逸速度 | 11.19 km/s | 11.186 | ✓ |
| 地平线距离 | 4.65 km | 4.654 | ✓ |
| 最大山高 | 4.9 km | 4.90 | ✓ |

**数字全部一致。** 这说明两边的物理是**同一套**，没有算错。

### 1.2 但代码上是两套独立实现

```
src/world.ts          → 自己算（511 行 surfaceGravity、513 行 escapeVelocity、641 行 maxMountainHeight…）
src/formula-library.ts → 也算（surface_gravity、escape_velocity、building_height_limit…）
```

实测确认：

```
grep -c "formulas" src/world.ts   →  0
```

**`world.ts` 完全不 import 公式库。** 它对 `formula-library.js` 的引用只有 `CONSTANTS`（常量表），没有公式。

### 1.3 这意味着什么

目前**没有出 bug**，但存在一个结构性风险：

```
改一处，另一处不会跟着改。
今天它们一致，是因为「当初抄对了」，不是因为「结构上保证一致」。
```

本项目历史上已经吃过一次同类的亏（README 写 404 条而代码 442 条）——
**手抄的数字对不齐，只是时间问题。**

## 二、你说的「本体」是什么意思 —— 我的理解

你说「成体系化的数据库才是世界观推导的本体」。我理解这句话有三层含义，
**而现有实现只做到了第一层的一半**：

| 层 | 含义 | 现状 |
|---|---|---|
| **① 单一数据源** | 同一个物理量只在一个地方定义，其他地方引用 | ❌ **没做到**（world 与公式库各一套） |
| **② 推导可追溯** | 每个推导结果能回答「我用了哪几个公式、输入是什么」 | ❌ 没做到（world 只给结果，不给推导链） |
| **③ 关系即知识** | 公式之间的连线（体系链/复合路径）本身就是可查询的知识 | ✅ **已做到**（22 链 / 45 接点 / 7 复合路径） |

也就是说：**第三层（关系网）已经建好了，但第一层（单一数据源）还没接上。**

这正好解释了一种别扭感：体系图很漂亮，但用它推演世界时，
**推演过程根本不经过那张图** —— 图是「地图」，推演却在走另一条路。

---

## 三、为什么不建议「让 world 内部调用公式」

直觉上最简单的做法是：让 `world.ts` import 公式库，逐个替换自算。

**但这个方向有一个致命的坑，实测已经埋着：**

### 3.1 `world` 需要的是**带上下文的计算**，公式库给的是**裸计算**

举例：最大山高。

```
公式库：building_height_limit = strength / (rho * g)
        参数：strength = 2e8（默认）

world：  strength = 1.3e8  ← 这个值不是常数，是**由 α 推出来的**
         （ADR-0001 S2：deriveScaleLadder 从精细结构常数推出材料强度）
```

我第一次复算时用了 `strength=2e8`（公式库默认），得到 **7.54 km**，
而 world 给 **4.9 km** —— 差了 54%。

**不是谁算错了，是「输入从哪来」不同。**

如果直接把 world 改成调用公式库，就必须把「α → 材料强度」这条链也搬进去 ——
而那条链依赖 `provenance.ts` 与 `constants-graph.ts`。

**这会让 world 与公式库形成双向依赖，最终变成一团。**

### 3.2 更根本的问题：**方向应该反过来**

```
现在：world（有上下文）  →  自己算，不告诉别人
理想：world（有上下文）  →  把「输入值」注册给公式库  →  公式库算并记录推导链
```

也就是说：**不是让 world 去调公式，而是让 world 成为「公式库的一次求值」。**

这是本方案的核心主张。

---

## 四、方案：三层，从最稳到最激进

### 层一：单一数据源（推荐先做，风险最低）

**做法**：把 world 里的自算项，改为「调用公式库的同一份实现」，
但**保留 world 的上下文注入**。

```ts
// 之前
const surfaceGravity = (K.G * planetMassKg) / planetRadiusM ** 2

// 之后
const surfaceGravity = evalFormula('surface_gravity', { M: planetMassKg, R: planetRadiusM })
```

**关键设计：只替换「纯函数」部分，不动「值从哪来」。**

这样：
- 物理实现只有一份（改公式库，world 跟着变）
- α → 强度的链条仍留在 world（它的职责）
- 依赖方向保持单向（world → formulas，不反向）

**代价**：需要把 12 个重复项逐个替换，每换一个都要跑对账测试。
**收益**：从此不会再出现「改一处忘另一处」。

### 层二：推导可追溯（中等价值）

**做法**：`world` 输出里加一节「本画像用到的公式与输入值」。

```
【推导链】
  表面重力 ← surface_gravity(M=5.972e24, R=6.371e6) = 9.8203
  逃逸速度 ← escape_velocity(M=5.972e24, r=6.371e6) = 11186
  最大山高 ← building_height_limit(strength=1.3e8←由α=0.007297推出, rho=2700, g=9.82)
```

**为什么有价值**：现在用户看到「最大山高 4.9 km」，无法知道这个数**从哪来**。
而本项目一直强调「可复核」——**推导链正是可复核的形式**。

### 层三：world 变成「复合路径的一次执行」（最激进）

**做法**：把「世界画像」本身登记成一条复合路径。

```
compound: world-profile
  via: [sys-astronomy, sys-climate, sys-food, sys-physics]
  每步用哪个公式、哪个参数，全部登记
```

然后 `world` 就是「按这条路径跑一遍」。

**这个方向的问题**：它会把 world 变成一个**僵化的流水线**，
而现在 world 的灵活性（按需算、跳过无关项）会失去。

**我的判断：层三不该做。** 理由是——
复合路径的定位是「给人看的路线」，不是「给机器执行的程序」。

## 五、我的建议

**做层一 + 层二，不做层三。**

具体：

| 步骤 | 内容 | 成本 | 风险 |
|---|---|---|---|
| 1 | 把 12 个重复项改为调用公式库（保留上下文注入） | 中 | 低（每项都有对账测试） |
| 2 | 加「推导链」输出段 | 低 | 极低（纯新增） |
| 3 | 加一条守卫测试：**world 的每个物理量与公式库复算一致** | 低 | 无（这是保险） |

**第 3 步是重点** —— 它把「碰巧一致」变成「结构上保证一致」。

测试写法（草案）：

```js
// 对每个 world 会输出的物理量，用公式库独立复算，断言相等
const cases = [
  { param: {starMass:1, orbitAU:1}, field: '表面重力', formula: 'surface_gravity',
    overrides: { M: 5.9722e24, R: 6.371e6 }, tol: 0.01 },
  ...
]
```

一旦有人改了公式库而忘了 world（或反过来），这条会立刻红。

## 六、一个必须说清的边界

**「数据库是本体」不等于「所有东西都要进公式库」。**

有些东西**不该**进：

```
✗ 上下文推导     「α → 材料强度」依赖 constants-graph，那是另一套体系
✗ 叙事选择       「这颗星该不该有生命」是判断，不是公式
✗ 复合路径执行   见上文层三
```

**公式库的定位是「物理量的计算与关系」，不是「世界的全部逻辑」。**

把它扩成「什么都在里面」，会得到一个巨大但不可用的东西 ——
而那正是本项目一直在避免的（「假关系比孤立更糟」的同一条原则）。

---

## 七、如果你要开工，我建议的顺序

```
① 先建那条守卫测试（不改任何实现）        ← 立刻有保险，且能量出差距
② 按守卫测试报出的差异，逐个替换实现      ← 每替换一个，测试从红变绿
③ 最后加「推导链」输出                    ← 纯新增，风险最低
```

**第 ① 步的价值被低估了**：它不改代码，但立刻能回答
「world 与公式库到底有多少项不一致」——**而这个数字现在没人知道**。
