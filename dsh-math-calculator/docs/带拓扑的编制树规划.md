# 带拓扑的编制树规划（插件内功能是否都有拓扑结构）

> 用户指示（2026-11-12）：
> 1. **编制树需要做成带拓扑的编制树**
> 2. **插件内绝大部分功能可能都有拓扑结构**
> 3. 写进规划报告，**不要开工**

## 一、先回答那个更根本的问题：是不是「绝大部分功能都有拓扑结构」

我把现有 40 个 operation 逐个摆出来，判断它们的**运算形状**：

| 形状 | 定义 | 现有 operation | 数量 |
|---|---|---|---|
| **点值** | 输入 → 输出一个数 | `evaluate`/`solve`/`derivative`/`integral`/`units`/`formula`/`stats`/`dist`/`regression` | 多数 |
| **表** | 输入 → 输出一张表 | `matrix`/`eigen`/`hierarchy`/`compare`/`ledger`/`extract_numbers` | 6 |
| **链** | 输入 → 沿依赖逐级传导 | `derivation`（部分）/ `dependency` | 2 |
| **结构** | 输入 → **节点+边+属性**，且结构本身要自洽 | **无完整的** | **0** |

**结论：用户的判断是对的，但缺的不是「所有功能都要加拓扑」，
而是「有一类功能本质上就是结构化数据，现在被压成了表」。**

具体看这四类：

### 1.1 已经是结构化、但只用了「层级」这一种拓扑的

| 功能 | 现在只支持 | 真实世界形态 |
|---|---|---|
| `hierarchy` | 等比层级链（每级同一倍数） | **不等比 + 跨级 + 加强单位**（见第二节） |
| `ledger` | 分项 vs 总量两栏 | 分项之间还有**子分项、跨账目转移** |
| `balance` | 七类固定收支 | 类之间有**调入/调出**（不是只看合计） |

### 1.2 本质是结构、现在是「一堆散参数」的

| 功能 | 现在 | 真实形态 |
|---|---|---|
| `world` + `terrain` | 单点：给一个 kind 出局地气候 | 多点 + **相邻关系**（气候要连续，不能山这边温带山那边热带） |
| `feasibility` | 11 条独立上限 | 上限之间有**耦合**（山高受限重力，重力受半径，半径受材料…） |
| `formula` 体系 | 22 条链各自独立 | **链之间靠接点连接**（已有 45 接点，但只能查不能算传导） |

### 1.3 已经是拓扑的

| 功能 | 拓扑形态 | 已做 |
|---|---|---|
| `dependency` | 节点+边（传导/环/层深/跨度） | ✅ 本轮 |
| `derivation graph` | 常数依赖图（有坐标） | ✅ 早已有 |

### 1.4 不是拓扑、也不该是

```
✗ evaluate / solve / derivative    —— 纯运算，无结构
✗ units / formula（单条）          —— 点值换算
✗ interval / quick_feasible        —— 区间与判定
```

**所以精确的结论是：**

> 40 个 operation 里，**约 10 个**本质是结构化数据（表或结构），
> 其中 6 个已被压成「表」，**只有 `dependency` 一个是真正的图**。
> **「绝大部分」不成立，但「关键的那部分」成立**——它们是推演的主体。

## 二、带拓扑的编制树：具体差什么

### 2.1 现在的 `hierarchy` 只能算等比链

```
{levels:["师","团","营"], tree:[3,3], base:10}
→ 师 90 人（10 × 3 × 3）

它的前提是：每一级的下辖倍数**相同**，且**每级只有一种单位**
```

### 2.2 真实编制有四种它表达不了的形态

| 形态 | 例子 | 现在的表现 |
|---|---|---|
| **不等比** | 师辖 3 个普通团 + 1 个加强团（加强团辖 5 营） | ❌ 只能全用 3 |
| **跨级** | 师直属 1 个独立营（不归任何团） | ❌ 层级链是纯线性的 |
| **兵种混合** | 一个师里有步兵团、炮兵团、工兵营（编成不同） | ❌ 只有「人」一个维度 |
| **缺编** | 某团实有 2 营（战损） | ❌ 只算满编 |

### 2.3 带拓扑的编制树该长什么样

**节点 = 编制单位，边 = 辖属关系，属性 = 编成与实力**：

```jsonc
{
  "hierarchy": {
    "nodes": [
      { "id": "1st-div", "name": "第一师", "kind": "division", "strength": 12000,
        "props": { "arms": "步兵", "fullStrength": 12000 } },
      { "id": "1st-rgt-a", "name": "第1团", "kind": "regiment", "strength": 3200 },
      { "id": "1st-rgt-b", "name": "第2团", "kind": "regiment", "strength": 3200 },
      { "id": "1st-rgt-c", "name": "第3团", "kind": "regiment", "strength": 3200 },
      { "id": "reinforced", "name": "加强团", "kind": "regiment", "strength": 5000 },
      { "id": "indep-bn",  "name": "独立营", "kind": "battalion", "strength": 800,
        "note": "师直属，跨级" }
    ],
    "edges": [
      { "from": "1st-div", "to": "1st-rgt-a", "weight": 1 },
      { "from": "1st-div", "to": "1st-rgt-b", "weight": 1 },
      { "from": "1st-div", "to": "1st-rgt-c", "weight": 1 },
      { "from": "1st-div", "to": "reinforced", "weight": 1 },
      { "from": "1st-div", "to": "indep-bn",  "weight": 1, "label": "直属" }
    ]
  }
}
```

### 2.4 它能回答的六类问题（`hierarchy` 现在都答不了）

```
① 实有 vs 满编    这个师实有 11,400 / 满编 12,000 → 缺编 5%
② 跨级识别        「独立营」直属于师，绕过了团这一级 → 需要标出
③ 不等比传导      加强团多出的 1,800 人是谁给的？
④ 某节点被毁      第2团被歼灭 → 师战力降 3,200（不是按等比算）
⑤ 兵种构成        这个师步兵 : 炮兵 : 工兵 的比例
⑥ 指挥链深度      从师到班几级、跨度是否超限（← 这是 dependency 已做的）
```

### 2.5 与 `dependency` 的合并判断

**不该合并，但该共用一套数据结构。**

```
hierarchy（带拓扑）  关心「编成与实力」：有多少人、什么兵种、缺不缺编
dependency           关心「结构与传导」：几级、多深、断在哪、有没有环
```

两者的**输入是同一张图**，但**查询意图不同**。所以：

```
共享：数据结构（nodes + edges + props）
分用：各自的查询与校验规则
```

**建议实现方式**：把「图的数据结构 + 基础遍历」抽成一个内部模块，
`hierarchy` 与 `dependency` 都调它，各自加自己的规则层。
这与本项目已有的做法一致（`core-physics.ts` 就是 world 与公式库的共享底层）。

## 三、其余「本质是结构」的功能改造清单

| # | 功能 | 现在 | 改造成 | 成本 |
|---|---|---|---|---|
| 1 | `hierarchy` | 等比层级链 | **节点+边+属性**，支持不等比/跨级/缺编 | 2 天 |
| 2 | `ledger` | 两层（分项 vs 总量） | **多层账本**（分项可有子分项），支持跨账转移 | 1.5 天 |
| 3 | `balance` | 七类固定合计 | **收支网络**（类间调入/调出，看流向而非只合计） | 1.5 天 |
| 4 | `terrain` | 单点气候 | **区域图**（相邻关系 + 气候连续性校验） | 2 天（与空间拓扑合并做） |
| 5 | `feasibility` | 11 条独立上限 | **约束图**（上限之间耦合，改一个看联动） | 1.5 天 |
| 6 | `formula` 体系 | 链各自独立 | **可算的传导**（不只查，能算「A 变 X% → 末端变多少」） | 2 天 |

**合计约 10.5 天**，其中第 4 项与《空间拓扑层规划》重叠，可合并。

## 四、实施顺序建议

```
第一步（打地基）      抽出「图数据结构 + 基础遍历」内部模块        1 天
第二步（最痛的一个）  改造 hierarchy 为带拓扑的编制树             2 天
第三步（验证地基）    改造 dependency 也用它（不改变行为）        0.5 天
第四步（推广）        按第三节清单逐个改造                        7 天
```

**为什么先做 `hierarchy`**：它是 99层项目 7 轮返工里 5 轮的那一项，
而且「不等比/跨级」是真实编制的常态 —— 现在只能等比，等于把真实编制
压缩成一个不成立的假设。

## 五、一处必须说清的边界

**「有拓扑结构」不等于「该建图」。**

判据是三条同时成立：

```
① 可分解      整体 = 部分之和（人、面积、能量）
② 有内部关系  部分之间相邻/包含/依赖/隶属
③ 有可校验约束 数量要闭合、属性要连续、链要可达
```

反例（不该建图）：

```
✗ quick_feasible   一句话判定，无内部结构
✗ interval         区间是单值对，没有「部分」
✗ units 单次换算   点值运算
✗ 人物性格/氛围    不满足①可分解
```

**这与反馈包 17 号的判断一致**：「凡是同时满足这三点的，就能用这套模型。
纯粹的『氛围描写』『人物性格』不满足①，不该用这套。」
