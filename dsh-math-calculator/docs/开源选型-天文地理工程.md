**探针实测**（astronomy-engine，2026-06-21 夏至）：

```
太阳 ra/dec       6.010 / 23.436°   ← 夏至太阳赤纬 23.44°，正确
太阳高度角         -2.40°（北京 20:00 已日落）

```

**能补什么**：`world` 目前只给「行星级气候」（均温/昼夜），没有真实天文历表。
接入后可以：给某个世界算真实日出日落、太阳高度、月相；用「同一纬度地球实测」对照校准气候。

**集成代价**：1.8 MB + 零依赖；按需懒加载（只在 world 的 `brief:false` 或新的 `astro` 子命令里用）。

## 三、建筑 / 舰船（npm 没有成熟实现）

检索 `opensees-node`、`pynite`、`structure-beam`、`beam-sections`、`naval-architecture`、`shipcalc` —— **全部 404 或无人维护**。

领域现状：

| 领域 | 成熟实现 | 语言 | 能否进 Node 插件 |
|---|---|---|---|
| 结构有限元 | OpenSees / PyNite / CalculiX | C++/Python | ❌ 需原生编译或外部进程 |
| 船舶设计 | FreeCAD Ship / OpenFOAM | Python/C++ | ❌ 同上 |
| 建筑能耗 | EnergyPlus / OpenStudio | C++ | ❌ 同上 |

**结论：不集成，保留现有简化模型。**

理由：
1. 本插件的 `structure` / `feasibility` 是**面积/层数/材料强度的量级模型**，不是有限元——定位是「这个世界能不能立住」，不是「这根梁配筋多少」；
2. 引入 OpenSees 级有限元会让依赖与体积爆炸，且对「世界观推演」是过度精度；
3. 边界已写进 skill：`structure` 只算容量与限高，不算疏散/采光/供水。

若将来要做「真实结构校验」，正确路径是**外部进程**（Python + PyNite），插件只负责导出输入与读回结果。

## 四、物理推导（无现成库，自建正确）

没有「架空世界物理推演」的成熟库（这是领域专属）。可用的是基础件，均已在此：

- `mathjs`（符号/数值/单位）
- `ml-matrix`（线代）
- `jstat`（分布）

公式库 757 条、常数依赖、推导栈属于**数据与领域逻辑**，没有开源替代。

## 六、astronomia 补充评估（2026-11-16）

"挑需要的部分"实测（下载 tarball 5.45 MB，解包 19 MB）：

```
data/elpMppDeFull.js      4.8 MB   月球 ELP 全表（最高精度）
data/elpMppDe.js          644 KB   月球 ELP 简化
data/vsop87Bmercury.js    348 KB   水星（每颗行星 264–348 KB）
data/vsop87D*.js          每颗行星 264–332 KB
lib/                      算法实现（体积小）
```

**结论：不整包集成。** 原因：
1. 19 MB 体积（npm tarball 从 2.2 MB 涨到 ~20 MB），而它的能力与已选的 astronomy-engine 重叠；
2. 按需 import 只能减少**内存**，减不了 **tarball**（整包下载）；
3. 真正更高精度的部分（ELP 全表 4.8 MB）对本项目的「架空世界」场景是过度精度。

**若要"挑"**：只提取单个 `data/vsop87B*.js`（264–348 KB）到 `src/data/`，自写 30 行级数解析（MIT 许可，保留版权声明），**不装包**。这条路径留给「需要真实行星高精度位置」时再说——当前 astronomy-engine 已够（赤纬误差 <0.01°）。

## 七、更大范围天文模拟（2026-11-16 检索）

### 找不到的：程序化行星系统生成器

npm 上没有「任意恒星 + 多行星 + 各自卫星」的生成器：

| 包 | 能力 | 判断 |
|---|---|---|
| orbital-mechanics-kit 1.2.0（MIT，9KB） | 两体轨道（开普勒解/根数/活力公式） | 与 orbit.ts 重叠，不装 |
| pious-squid 2.3.0（MIT，528KB） | **地球轨道卫星**传播（J2/Sun/Moon 摄动） | 地球专用，不生成行星系统 |
| orbjs 0.2.2（MIT） | 简单轨道问题；依赖 core-js 0.9（2014 年） | 陈旧，不装 |
| keplerian-core 0.1.1（MIT，164KB） | KeplerianLab 引擎，0.1 新 | 等成熟再说 |

**astronomy-engine 的边界**：它能定位太阳系已有天体（VSOP），但**不能配置**「不同质量/不同轨道/不同卫星」——它的行星表是固定的。所以「类太阳系但配置不同」必须用通用模型。

### 自建：行星系统生成（system.ts）

物理规则都有明确出处：

```
希尔球        r_H = a·(m/3M)^(1/3)          卫星/行星的引力支配范围
洛希极限      a_R = 2.44·R_p·(ρ_p/ρ_s)^(1/3)  卫星不被潮汐撕碎
卫星外限      r_H / 3                       超出被恒星摄动剥离
行星间距      a_{i+1} − a_i > r_H,i          避免轨道交叉
```

实测（类太阳系）：
- 地球：周期 1.000 年，希尔球 0.01000 AU，月球周期 0.075 年（真实 0.0748）；
- 木星：周期 11.852 年，希尔球 0.355 AU（真实 0.322，同量级）；
- 行星间距 < 希尔球 → 警告「轨道可能交叉」；
- 卫星 < 洛希 → 警告「会被潮汐撕碎」；> 希尔/3 → 警告「会被剥离」。

接入 `astro` 的 `action:"system"`。

### 结论

- **astronomy-engine 用于真实太阳系**（固定配置，高精度）；
- **orbit.ts / system.ts 用于任意星系**（可配置质量/轨道/卫星，二体 + 稳定性判据）；
- 两者互补，不存在「一个库覆盖全部」的开源实现。
