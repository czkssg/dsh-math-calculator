# 开工前先查开源社区（项目铁律）

> 用户指令（2026-11-12）：
> **以后编写或者开工前，无论是什么功能，任何一个功能开工前，先查开源社区。**
>
> 本文是这条规则的执行细则。它约束**所有功能开发**，不区分大小。

## 一、为什么这条规则是必需的

不是「省钱」或「省事」，而是**本项目已经反复用事实证明了自己手写是错的**：

| 我们手写的 | 开源早有的 | 代价 |
|---|---|---|
| `traverse` + `findCycles`（约 80 行，还有上游方向 bug） | `graphology` 的 `components` / `dag` / `shortest-path`（221 万周下载，MIT） | 写了 bug，还要再改 |
| 地形绕障寻路（原计划自己写） | `@turf/turf` 的 `shortestPath`（231 万周下载，MIT） | 计划还没开工就已作废 |
| 复合单位反复补丁（第三次仍在修） | `@lhncbc/ucum-lhc`（NLM 维护，通过 UCUM 官方功能测试） | 修了三次，一共只覆盖了三种写法中的两种 |

**这三条都是自己写到一半才发现开源有成熟实现。**
所以规则不是「先查更优雅」，是**「不查就会重复付学费」**。

## 二、流程（四步，缺一不可）

### 第 1 步：查（开工前的硬门槛）

至少查三个地方：

```
① npm registry   —— JS/TS 生态的标准入口
② GitHub         —— 搜实现的源码仓库（含未发布到 npm 的）
③ 领域标准        —— 有些领域有官方标准与参考实现（如 UCUM、QUDT、GeoJSON）
```

**检索词的写法**（这决定能不能查到）：

```
✗ 太窄：「kg/m3 复合单位解析器」
✓ 分层：
    领域词  units conversion / dimensional analysis
    标准名  UCUM / QUDT / SI derived units
    问题词  compound unit parser / unit expression evaluation
```

**判定「有没有」的四条标准**：

| 标准 | 要求 |
|---|---|
| 维护活跃度 | 最近更新 ≤ 6 个月（超过则记为风险，不是否决） |
| 下载量 | 周下载 ≥ 1 万（低于此说明没人用，风险高） |
| 许可兼容 | 必须能用于 MIT 项目；「SEE LICENSE」这类必须实地读 |
| 能力匹配 | 明确列出**它有什么、没有什么**（见第三节反例） |

### 第 2 步：评估集成代价

不能只看「有没有」，要看「值不值得引」：

| 维度 | 要查什么 | 本项目现状 |
|---|---|---|
| 依赖数 | `npm view <pkg> dependencies` | 本项目目前零依赖（除 mathjs） |
| 包体积 | bundlephobia / 实际安装后看 | 每加一个依赖都要能说清理由 |
| 停更风险 | 最后发布时间 | `graphology` 2 年未更新 = 需标注风险 |
| 是否可只用一部分 | 是否有子包 | `@turf/shortest-path` 可单独装，不必装全家桶 |

### 第 3 步：记录选型理由（写进文档，不只在对话里说）

**必须写清「为什么用」或「为什么不用」**，否则下次有人会重新纠结一遍。

格式（写进对应规划文档）：

```markdown
## 开源调研（<日期>）

| 候选 | 版本/更新 | 周下载 | 许可 | 判断 |
|---|---|---|---|---|
| A | ... | ... | ... | ✅ 推荐：原因 |
| B | ... | ... | ... | ⚠️ 备选：原因 |
| C | ... | ... | ... | ❌ 不用：原因 |

### 它有什么 / 没有什么
（明确列出覆盖范围与空白，空白那部分才自己写）

### 选型结论
（分场景给结论，不要说「用 A」这种没有条件的话）
```

### 第 4 步：才开始写代码

**只有前三步都做完，才允许动 `src/`。**

若结论是「自己写」，也必须先写清「查过了，没有合适的」，并说明理由。

## 三、一个反面教材：不能只看「有没有库」

`@turf/turf` 有 231 万周下载、MIT、活跃维护——但它**不能解决复合单位问题**，
因为它是地理空间库（经纬度、多边形），与「kg/m³ 换算」无关。

**所以第 1 步的判定必须包含「能力边界」**：

```markdown
它有什么：距离、面积、路径、多边形关系、视线相关的底层几何
它没有什么：
  ✗ 单位换算与量纲分析（那是 UCUM 的事）
  ✗ 视线/视域算法（npm 上无成熟实现，须自写）
  ✗ 地形语义（「山地行军 ×2.5」是领域知识，不是几何）
```

**「有个大库」不等于「问题解决了」。**

## 四、三类特殊情况怎么处理

### ① 查到了，但许可不兼容

```
处理：找替代实现（如 @lhncbc/ucum-lhc 许可不明 → 备选 @atomic-ehr/ucum 的 MIT 解析器）
     或只借鉴算法思想，不引代码（算法本身不受版权保护）
绝不：先用了再说
```

### ② 查到了，但不再维护

```
处理：评估「算法是否稳定」
     · 图算法/排序/寻路是几十年不变的经典算法 → 可 fork
     · 与外部格式/标准绑定的（解析器、协议） → 停更即淘汰
```

### ③ 查过了，确实没有

```
处理：① 在规划文档里写明「查过 X/Y/Z，无合适实现」
     ② 说明自己写的估算成本
     ③ 才开始写
```

## 五、这条规则的检查点

| 时机 | 检查什么 |
|---|---|
| 写规划文档时 | 必须有「开源调研」一节，含候选表与选型结论 |
| 开工前 | 能用一句话说清「为什么用这个 / 为什么自己写」 |
| 代码 review | 新增依赖必须能在文档里找到选型理由 |
| 复盘时 | 若发现「手写后发现开源有」→ 记入本文第一节的表 |
