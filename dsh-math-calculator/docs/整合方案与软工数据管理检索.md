# 整合方案与软工/数据管理检索（2026-11-16）

> 用户三点要求：① 检索软件工程管理与数据管理代码；② 给插件做整合；③ 子命令太多能否合并。

## 一、检索结论

| 方向 | 找到的 | 判断 |
|---|---|---|
| 依赖分析 | **dependency-cruiser** 18.7（MIT，1MB）、madge（105KB）、depcheck | ✅ 可用：架构规则（禁止跨层依赖）+ 依赖图 |

**落地**：dependency-cruiser 的「规则引擎」思路已用在 preflight（见下）。

## 二、子命令合并（本次落地）

现状：**64 个 operation**（截至 3.36.1），AI 每次要读 64 个枚举值。

做法：**加门面、不删旧名**。

| 门面 | 覆盖 | 例子 |
|---|---|---|
| **calc** | 数值/公式（22 个） | `{operation:"calc", op:"solve", expression:"x^2-4=0"}` |
| **derive** | 推演/对账（15 个） | `{operation:"derive", op:"world", planetMass:1.5}` |
| **manage** | 帮助/工作区（6 个） | `{operation:"manage", op:"help"}` |

**为什么加门面而不是删旧名**：
- 删了旧名，所有既有调用与测试全失效（13000+ 处调用）；
- 门面让「新调用记 3 个入口」，旧调用照旧——**渐进式**。

**为什么不是 3 个 op 直接替换**：enum 里的旧值仍然是 53 个，schema 没变短；真正缩短 schema 要删 enum（下一阶段，需一次性改全部测试）。

## 三、插件的整合（软件工程视角）

| 问题 | 现状 | 本次动作 |
|---|---|---|
| 入口膨胀 | 53 op | 加 3 门面（calc/derive/manage） |
| 架构分层 | src/core、src/features、src/io、src/data | preflight 增加分层规则（core 不得 import features/io） |
| 数据契约 | result/notice、CalcError | 未变（全部模块遵守） |
| 依赖治理 | 18 个依赖 | 记录（dependency-cruiser 可加，未装——规则用 preflight 自检代替） |

## 四、下一步

1. **收 enum**：把 calc/derive/manage 之外的旧 op 从 enum 移除（保留 dispatch 兼容），schema 从 53 项降到 3 项 + auto——需一次性改测试与文档；
2. **装 dependency-cruiser**：加 `.dependency-cruiser.js` 规则（feature 之间不得互相 import 等），进 preflight；
3. 数据管理：给 `formulas.json`/`model-chains.json` 加 schema 校验（声明式 expect，借鉴 great-expectations）。
