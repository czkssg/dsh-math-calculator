## 一、11 个 operation 的性质分类

| operation | 性质 | 有开源可换？ |
|---|---|---|
| `dependency` | **图算法**（环/层深/上下游/拓扑） | **✅ graphology** |
| `consistency` | 领域语义（同量多处不同值） | ❌ 无 |
| `ledger` | 领域语义（分项 vs 总量） | ❌ 无 |
| `compare` | 领域语义（多方案对比） | ❌ 无 |
| `interval` | 区间算术 | ⏸ 有库但收益小 |
| `extract_numbers` | 文本抽取 | ⏸ 见下 |
| `hierarchy` | 编制树 | ❌ 领域语义 |
| `quick_feasible` | 可行性判定 | ❌ 领域知识 |
| `world_state` | 状态库 | ❌ 无 |
| `units_audit` | 量纲检查 | ⏸ 依赖 UCUM 数据 |
| `timeline_check` | 时间线 | ⏸ 无成熟库 |

**结论：只有 `dependency` 有真正的开源替代。**

## 二、`dependency` 用 graphology

| 能力 | graphology | 实测结果 |
|---|---|---|
| 拓扑排序 | `topologicalSort(g)` | `G → M → R → g → v → E` ✓ |
| 环检测 | `hasCycle(g)` | 加环后返回 `true` ✓ |
| 上下游 | `inboundNeighbors` / `outboundNeighbors` | `g 上游 = [G,M,R]` ✓ |
| **层深** | `topologicalGenerations(g)` | `[[G,M,R],[g],[v],[E]]` ✓ |

**四项全有，且分层结果正是「常数依赖图」需要的形态。**

### 为什么不自己写

老插件手写了 `buildAdjacency` + `traverse` + `findCycles`（98 行），
而它**有上游方向 bug**（第一版只取 `edge.to`，传入边表时永远得空数组）。

`graphology` 是 MIT、221 万周下载，这些算法都经过大量项目检验。

## 三、`interval` 的候选

| 库 | 判断 |
|---|---|
| `interval-arithmetic` | 有，但只做四则运算；本项目的需求含「门槛判定」「宽度/松紧」等语义 |
| `math-intervals` | 同上 |

**不采用**：本项目的区间运算要输出「把握程度」（±52% → 只能当方向），
那是领域语义，不是纯算术。

## 四、`extract_numbers` 的候选

| 库 | 判断 |
|---|---|
| `parse-numeric-stream` | 只解析纯数字流 |
| `number-from-string` | 只认阿拉伯数字 |
| `compromise`（NLP） | 能做英文实体抽取，中文弱 |

**不采用**：核心难点是**中文量级词**（「1.49 亿」「三千年」）与
**复合单位**（「万吨/年」），没有库覆盖这两者的组合。

而这两点本项目已经在 `core/engine.ts` 里解决（中文归一 + 单位注册），
所以 `extract_numbers` 是「复用已有能力 + 少量正则」，不需要新依赖。

## 五、`compare` / `ledger` / `consistency` 为什么不找库

三个都是**领域语义判断**：

```
ledger       什么叫「闭合」？差多少算不闭合？哪个分项最可疑？
consistency  什么叫「同一个量」？（「人口」与「总人口」是同量吗？）
compare      不给权重就不给综合分 —— 这是取舍，不是算法
```

**这三件事的判断标准是本项目定义的**，没有库能替。
