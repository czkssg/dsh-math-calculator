# 泊松比与体积模量：能否用现有功能计算 — 实测结论

> 上一份《材料本构层公式检索报告》里我把这两项判为「不建议做公式」，
> 理由是「定义式非计算式」「三向应力要用 6×6 广义胡克，超出单值求值」。
> **经实测，后一条判断是错的。** 本文记录实测与修正后的方案。

---

## 一、实测：广义胡克用 evaluate 完全能算

### 三向应力下的应变分量（最常用形态）

```
{operation:"evaluate", expression:
  "[(100e6-0.3*(50e6+20e6))/2e11, (50e6-0.3*(100e6+20e6))/2e11, (20e6-0.3*(100e6+50e6))/2e11]"}
```

实测输出：`[3.95e-4, 7e-5, -1.25e-4]`

**手算核对全中**：

```
  εx = (100 − 0.3×(50+20))/2e11 = 3.95e-4   ✓
  εy = (50  − 0.3×(100+20))/2e11 = 7e-5     ✓
  εz = (20  − 0.3×(100+50))/2e11 = −1.25e-4 ✓
```

### 完整的矩阵形式也支持

```
{operation:"evaluate", expression:
  "[[1/2e11, -0.3/2e11, -0.3/2e11],[-0.3/2e11, 1/2e11, -0.3/2e11],[-0.3/2e11, -0.3/2e11, 1/2e11]] * [[1e6],[2e6],[3e6]]"}
→ [[-2.5e-6], [4e-6], [1.05e-5]]
```

柔度矩阵 × 应力向量，**这正是 6×6 广义胡克去掉剪切项的 3×3 主轴形式**。

### 主应力：eigen 直接给

```
{operation:"eigen", matrix:[[100,30,0],[30,50,0],[0,0,20]]}
→ 特征值：20, 35.94875162, 114.05124838
```

手算核对：(100+50)/2 ± √(25²+30²) = 75 ± 39.05 → 35.95 / 114.05 ✓

**所以「三向应力超出单值求值」这个判断是错的** —— 它能算，而且算得准。

## 二、但实测暴露了三个真实限制

### 限制 1：矩阵里不能带单位

```
[[1 MPa, 0, 0],[0, 2 MPa, 0]] * [[1],[1],[1]]
→ internal: Unexpected type of argument in function addScalar
```

原因：矩阵元素的加法走到了 `addScalar`，它不接受 Unit。
**这意味着三向应力必须用纯数字（SI 单位）写**，单位只能靠参数说明交代。

### 限制 2：`variables` 不接受矩阵字符串

```
{expression:"S * sg", variables:{S:"[[1,0],[0,1]]", sg:"[[1],[2]]"}}
→ unknown_symbol: Undefined symbol sg
```

这是**真实缺陷**：`variables` 的字符串回退路径我上一轮只做了「标量」与「带单位的量」两种，
**没有矩阵**。所以想用变量存柔度矩阵这条路走不通。

影响：广义胡克无法写成「公式 + 材料卡片」的形态，只能每次把矩阵原文抄进 expression。
而这正是「材料属性靠硬设定」最难受的地方 —— 柔度矩阵里含 E 和 ν 两个设定值，
每次改一个 ν 就要重抄整个矩阵。

### 限制 3：`(a, b, c)` 这种逗号三元组不是数组

```
(a, b, c)  → syntax: Parenthesis ) expected
[a, b, c]  → ✓ 正常
```

必须用方括号。这不是缺陷（是 mathjs 语法），但容易踩，值得写进 help。

## 三、修正后的判定

| 项 | 原判定 | 修正后 |
|---|---|---|
| **泊松比** | 不做公式（定义式，三向超范围） | **不做公式，但做一条「泊松比效应」换算**：`ε_trans = −ν·ε_axial`。它是**计算式**（给定轴向应变求横向收缩），不是纯定义。单轴场景极常用 |
| **体积模量** | 并入换算 | **按建议照做，做成一族换算**：`K = E/(3(1−2ν))`、`ν = (3K−2G)/(2(3K+G))` 等，每条都是独立可调用的公式 |

### 为什么泊松比仍不做「完整计算式」

完整的广义胡克确实是 6×6，但**它能用 evaluate 算**（见第一节）。
所以不做成公式的真正理由不是「算不了」，而是：

**它需要输入 6 个应力分量（含 3 个剪应力），而绝大多数场景只用 3 个正应力。**
做成一个「吃 6 个参数」的公式，用户会用不上；做成「吃 3 个参数」的，
又要明确说「这是主轴形式，剪应力为零」。

**结论**：三向应力交给 `evaluate` + 矩阵（灵活、能带剪应力）；
公式库只收**单轴那一档**（`ε_trans = −ν·ε_axial`），因为那是 90% 的用法。

## 四、体积模量族：建议做的换算清单

E、ν、K、G 四个量任意两个可定另外两个，做成一族**单向换算**（不做一个四选二的多路公式）：

| id | 公式 | 由什么算什么 | 来源 |
|---|---|---|---|
| `bulk_modulus_from_E_nu` | K = E / (3(1−2ν)) | E,ν → K | 弹性力学标准式 |
| `shear_modulus_from_E_nu` | G = E / (2(1+ν)) | E,ν → G | 同上 |
| `young_from_bulk_shear` | E = 9KG / (3K+G) | K,G → E | 同上 |
| `poisson_from_bulk_shear` | ν = (3K−2G) / (2(3K+G)) | K,G → ν | 同上 |
| `lame_lambda` | λ = νE / ((1+ν)(1−2ν)) | E,ν → λ | 广义胡克的 λ |

实测这几条现在用 `evaluate` 就能算，且 `solve` 能反解：

```
evaluate  "2e11/(3*(1-2*0.3))"                → 1.6667e11   （K）
evaluate  "2e11/(2*(1+0.3))"                  → 7.6923e10   （G）
solve     "166666666666.67 = 2e11/(3*(1-2*x))" → x = 0.3    （反解 ν）
```

**所以问题的关键不是「能不能算」，而是「要不要一个记住名字的入口」**。

这三条换算的公式本身都是一行四则运算，理论上用户自己写也行。
但：

- `E = 9KG/(3K+G)` 这种式子**没人记得住**（我写这份文档时也查了一次）
- 写错了不会报错，会给出一个**量级正确但数值错的数**
- 而它出现在每一条有限元/材料设计推导里

所以值得收 —— 判据是「**非平凡、易记错、且高频**」，而不是「能不能手算」。

## 五、连带建议：修 `variables` 的矩阵支持

这是本次实测暴露的唯一**真实缺陷**，也是让「材料卡片」成立的关键一环。

现状：

```
variables:{S:"[[1,0],[0,1]]"}  → 被静默丢弃（skippedVariableKeys）
```

期望：

```
// 材料卡片成立后，广义胡克可以这样写
workspace set vars {
  STEEL_E: 2e11, STEEL_NU: 0.3,
  STEEL_S: "[[1/2e11,-0.3/2e11,-0.3/2e11],[-0.3/2e11,1/2e11,-0.3/2e11],[-0.3/2e11,-0.3/2e11,1/2e11]]"
}
evaluate  "STEEL_S * [[100e6],[50e6],[20e6]]"   → 三主应变
```

修法很简单：`variables` 的字符串回退路径里，把「解析成矩阵」也列进去
（与已有的「带单位的量」同一处回退，只是多认一种结果形态）。

**优先级**：与上一轮 DIY 方案的 P2（工作区变量可用于 overrides）属于同一族问题，
都是「让用户存下来的东西能用起来」。建议一起做。

## 六、结论摘要

| 问题 | 答案 |
|---|---|
| 三向应力能不能用现有功能算？ | **能。** `evaluate` + 矩阵，实测 3×3 柔度×应力、`eigen` 求主应力都正确 |
| 泊松比要不要做公式？ | 不做完整广义胡克，但**做单轴版** `ε_trans = −ν·ε_axial` |
| 体积模量怎么处理？ | **做一族 5 条换算**（E/ν/K/G/λ 互算），按你的想法办 |
| 有什么要先修？ | `variables` 不支持矩阵字符串 —— **真实缺陷**，影响「材料卡片」成立 |
| 有什么要写进 help？ | 矩阵写法用 `[...]` 不是 `(...)`；矩阵元素不能带单位 |

上一轮我判断「超出单值求值范围」是错的，已在本文更正。
**判据应当改成：能不能算 → 能算；值不值得公式化 → 看「是否非平凡、易记错、高频」。**
