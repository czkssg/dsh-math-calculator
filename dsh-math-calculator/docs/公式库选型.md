# 公式库选型：检索与依赖链（2026-11-13）

> 按铁律「开工前先查开源社区」执行。

## 一、要解决的两个问题

```
① 检索     从 665 条公式里按中文查询找到相关的（「山能长多高」→ 山高上限公式）
② 依赖链   22 条推演链的拓扑求值（A 变了 → 沿 DAG 传导到末端）
```

## 二、检索：四个候选

| 库 | 版本 | 许可 | 中文 | 判断 |
|---|---|---|---|---|
| **`minisearch`** | 7.2.0 | MIT | **需自定义分词器** | **采用** |
| `fuse.js` | 7.5.0 | Apache-2.0 | 模糊匹配可用 | 备选 |
| `flexsearch` | 0.8.212 | Apache-2.0 | 支持 | 不用（API 复杂） |
| `lunr` | 2.3.9 | MIT | 差（英文优先） | 不用 |

### 为什么选 `minisearch`

```
① 支持自定义 tokenizer  → 可接中文分词
② 支持 prefix + fuzzy   → 「逃逸」能命中「逃逸速度」
③ 零依赖、纯 JS         → 插件体积友好
④ 有 storeFields        → 检索结果直接带公式元数据
```

实测（3 条样例）：

```
query      结果
逃逸       逃逸速度(1.91)
黑体       黑体辐射(1.91)
```

### ★ 中文必须自己接分词器

`minisearch` 默认按**空格**分词。而中文没有空格：

```
默认 tokenize('逃逸速度')  →  ['逃逸速度']    整串一个词
→ 「逃逸」检索不到「逃逸速度」
```

所以必须接中文分词。查到的候选：

| 库 | 版本 | 判断 |
|---|---|---|
| **`segmentit`** | 2.0.3 | **采用**（纯 JS，无需编译） |
| `nodejieba` | 3.5.8 | 不用（需原生编译，插件安装成本高） |
| `@node-rs/jieba` | 2.0.4 | 同上（Rust 原生） |

`segmentit` 实测分词质量：

```
山能长多高      →  山 / 能 / 长 / 多 / 高
逃逸速度是多少  →  逃逸速度 / 是多少
黑体辐射强度    →  黑体 / 辐射强度
船的航速上限    →  船 / 的 / 航速 / 上限
```

**「辐射强度」「航速」「上限」都切对了** —— 这正是检索需要的粒度。

## 三、依赖链：三个候选

| 库 | 版本 | 许可 | 判断 |
|---|---|---|---|
| **`graphology`** + **`graphology-dag`** | 0.26.0 / 0.4.1 | MIT | **采用** |
| `toposort` | 2.0.2 | MIT | 备选（极简，无环检测的详细报错） |

### 为什么选 graphology

```
① topologicalSort()     拓扑排序
② 有环时抛出明确错误     不静默返回错误顺序
③ 与将来要做的 entity_topology 共用同一套图库
```

实测：

```
A→B, B→C, A→C, C→D  →  拓扑序 A → B → C → D
再加 D→A             →  检出环（报错而非静默）
```

**与 `entity_topology` 共用 `graphology`** 是关键理由 —— 第五类功能
（实体拓扑）本来就要引它，一次引入两处受益。

## 四、最终依赖清单

| 依赖 | 用途 | 许可 | 依赖数 |
|---|---|---|---|
| `minisearch` | 公式检索 | MIT | 0 |
| `segmentit` | 中文分词 | — | 0 |
| `graphology` | 图（依赖链 + 将来的实体拓扑） | MIT | 0 |
| `graphology-dag` | 拓扑排序 + 环检测 | MIT | 0 |

**四个包、零传递依赖。**

## 五、不采用的

| 方案 | 理由 |
|---|---|
| 自己做倒排索引 | `minisearch` 已经成熟，且支持中文接入 |
| 自己做中文分词 | 分词是 NLP 难题，`segmentit` 是现成的 |
| 自己做拓扑排序 | `graphology-dag` 已提供，且带环检测 |
| `flexsearch` | API 比 minisearch 复杂，收益不明显 |
| `nodejieba` / `@node-rs/jieba` | 需原生编译，插件安装失败率上升 |

**结论：没有可直接替代 665 条领域公式库的开源实现。**
可借力的是三层能力：CAS（nerdamer）、结构化表达式（MathJSON/OpenMath）、
以及 Modelica 的「方程」范式（我们的公式是赋值式，只能正向算）。

### 二、实测诊断（2026-11-13）

```
公式 665 条 · 参数 1720 个 · 唯一参数名 735 个
参数有描述 1720 / 1720 · 参数有默认值 365
公式 unit 非空 600 / 665（65 条无单位）
公式 keys 非空 665 / 665 · 体系链 22 条 / 259 步
全默认参数可直接求值 17 条 · 需必填参数 647 条 · 求值报错 1 条（leontief_inverse 返回矩阵）
```

**静态校验（mathjs parse）抓到的真实问题**：

| 问题 | 数量 | 例子 |
|---|---|---|
| 公式不可解析（展示式混进可执行字段） | **4** | `gini`、`hhi`、`shannon_entropy`、`simpson_diversity`（含 `Σᵢ` 下标、`log_base`） |
| 表达式引用未声明符号 | 5 个名字 | `h` `me` `c` `hbar` `NA`（常数注入，需确认是否应显式声明） |
| 参数无量纲 | 735 个参数名 | 全靠 `desc` 文字，调用方给错单位不会被拦 |
| 无反解 | — | 仅 `backSolve` 的 4 个锚点 |
| 公式与链分离 | — | 22 条链的 259 步未与公式 id 连成图 |

「粗糙」的实质不是「文本 vs 代码」，而是**结构缺位**：
参数没有量纲、公式没有可执行/展示之分、链与公式没有图、反解得逐条写。

### 三、升级方案（按成本/收益排序）

**阶段 1（1–2 天，低风险）**
1. 区分「可执行式」与「展示式」：给 4 条不可解析公式加 `executable:false`（或补 `numericExpr`），调用时明确报「这是展示式，不可求值」而不是语法错。
2. 665 条静态校验测试：可执行式必须 parse 通过、符号必须在 params/常数里；展示式必须有标记。
3. 补 65 条缺单位（无量纲的写明「无量纲」）。
4. 735 个参数名的量纲词典（7 基量向量），给参数级单位检查打底。

**阶段 2（1–2 天）**
5. 反解：给任意公式做「给定目标求某参数」（数值求根 + nerdamer/符号变形），替代仅 4 锚点的 backSolve。
6. 公式-链合图：`systems.json` 的 259 步与公式 id 用 graphology 连成图，支持「改某公式参数 → 末端变多少」。

**阶段 3（可选）**
7. 结构化表达式（MathJSON/OpenMath）用于变形与 LaTeX 渲染（构建期用 compute-engine 编译，运行期不引重依赖）。
8. 调用方给「5 米」时自动换算到公式单位（参数级单位）。

### 四、结论

公式库不缺「可执行性」（mathjs 一直在算），缺的是**结构化**：
量纲、可执行标记、反解、公式-链图。这些都不需要引入新的公式库，
只需要给现有 665 条补字段 + 加一层校验与反解。
