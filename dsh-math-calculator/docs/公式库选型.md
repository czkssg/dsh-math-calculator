## 一、要解决的两个问题

```
① 检索     从 665 条公式里按中文查询找到相关的（「山能长多高」→ 山高上限公式）
② 依赖链   22 条推演链的拓扑求值（A 变了 → 沿 DAG 传导到末端）
```

## 二、检索：四个候选

| 库 | 版本 | 许可 | 中文 | 判断 |
|---|---|---|---|---|
| **`minisearch`** | 7.2.0 | MIT | **需自定义分词器** | **采用** |
| `fuse.js` | 7.5.0 | Apache-2.0 | 模糊匹配可用 | 备选 |
| `flexsearch` | 0.8.212 | Apache-2.0 | 支持 | 不用（API 复杂） |
| `lunr` | 2.3.9 | MIT | 差（英文优先） | 不用 |

### 为什么选 `minisearch`

```
① 支持自定义 tokenizer  → 可接中文分词
② 支持 prefix + fuzzy   → 「逃逸」能命中「逃逸速度」
③ 零依赖、纯 JS         → 插件体积友好
④ 有 storeFields        → 检索结果直接带公式元数据
```

实测（3 条样例）：

```
query      结果
逃逸       逃逸速度(1.91)
黑体       黑体辐射(1.91)
```

### ★ 中文必须自己接分词器

`minisearch` 默认按**空格**分词。而中文没有空格：

```
默认 tokenize('逃逸速度')  →  ['逃逸速度']    整串一个词
→ 「逃逸」检索不到「逃逸速度」
```

所以必须接中文分词。查到的候选：

| 库 | 版本 | 判断 |
|---|---|---|
| **`segmentit`** | 2.0.3 | **采用**（纯 JS，无需编译） |
| `nodejieba` | 3.5.8 | 不用（需原生编译，插件安装成本高） |
| `@node-rs/jieba` | 2.0.4 | 同上（Rust 原生） |

`segmentit` 实测分词质量：

```
山能长多高      →  山 / 能 / 长 / 多 / 高
逃逸速度是多少  →  逃逸速度 / 是多少
黑体辐射强度    →  黑体 / 辐射强度
船的航速上限    →  船 / 的 / 航速 / 上限
```

**「辐射强度」「航速」「上限」都切对了** —— 这正是检索需要的粒度。

## 三、依赖链：三个候选

| 库 | 版本 | 许可 | 判断 |
|---|---|---|---|
| **`graphology`** + **`graphology-dag`** | 0.26.0 / 0.4.1 | MIT | **采用** |
| `toposort` | 2.0.2 | MIT | 备选（极简，无环检测的详细报错） |

### 为什么选 graphology

```
① topologicalSort()     拓扑排序
② 有环时抛出明确错误     不静默返回错误顺序
③ 与将来要做的 entity_topology 共用同一套图库
```

实测：

```
A→B, B→C, A→C, C→D  →  拓扑序 A → B → C → D
再加 D→A             →  检出环（报错而非静默）
```

**与 `entity_topology` 共用 `graphology`** 是关键理由 —— 第五类功能
（实体拓扑）本来就要引它，一次引入两处受益。

## 四、最终依赖清单

| 依赖 | 用途 | 许可 | 依赖数 |
|---|---|---|---|
| `minisearch` | 公式检索 | MIT | 0 |
| `segmentit` | 中文分词 | — | 0 |
| `graphology` | 图（依赖链 + 将来的实体拓扑） | MIT | 0 |
| `graphology-dag` | 拓扑排序 + 环检测 | MIT | 0 |

**四个包、零传递依赖。**

## 五、不采用的

| 方案 | 理由 |
|---|---|
| 自己做倒排索引 | `minisearch` 已经成熟，且支持中文接入 |
| 自己做中文分词 | 分词是 NLP 难题，`segmentit` 是现成的 |
| 自己做拓扑排序 | `graphology-dag` 已提供，且带环检测 |
| `flexsearch` | API 比 minisearch 复杂，收益不明显 |
| `nodejieba` / `@node-rs/jieba` | 需原生编译，插件安装失败率上升 |
