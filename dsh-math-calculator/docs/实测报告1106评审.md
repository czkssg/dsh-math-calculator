## 二、没有照做的三条（**重要：不要按报告的写法改**）

### ❌ 2.3 「面积单位只认上标，不认 m2 / 平方米」

**报告说**：`m²` ✓，`m2` / `m^2` / `平方米` ❌。

**实测（`units` 模式）**：

| 写法 | 结果 |
|---|---|
| `m²` | ✅ |
| `平方米` / `平米` | ✅ **报告说不支持，实际支持** |
| `公顷` / `平方公里` / `平方千米` | ✅ **报告说不支持，实际支持** |
| `m2` / `m^2` / `hectare` | ❌ 确实不支持 |

**报告的第二处偏差**：`m²` 在 **`evaluate` 模式**里根本不能运算
（`5 m²` → `Syntax error in part "²"`）。所以「只认上标」只在 `units` 里成立，
在表达式里连上标都不认。

**实际处理**：两条路都修 ——
· `units` 补 `m2` / `m^2` / `hectare` 别名
· `evaluate` 支持上标（正常化为 `^2`）与 `km2` 写法

**教训**：报告作者是在 `evaluate` 里踩的坑，但把结论写成了 `units` 的行为。
只按结论改会漏掉真正的问题。

### ❌ 3.1 「增加 unit 参数做量纲一致性检查，不同量纲就拒绝比值」

**这是报告认为最重要的一条建议**，我判断不能按它说的做。

**理由一：它假设的机制不存在。**

报告设想「工具检测到 `kg/day` 与 `unit/day` 不同量纲，拒绝给出比值」。
但 `expressions` 里**每条是独立求值**的 —— 工具从不做「两条之间求比值」，
**没有那个操作可拦**。

**理由二：量纲检查拦不住报告犯的那个错。**

报告 1.2 号错误（也是最严重的自省）是：

> 产能表测的是**生物陶瓷材料**（吨），生命之树测的是**生物步兵成品**（台），
> 我算出「差 36 万倍」并据此否证一个假说 —— 但这个比值本来就没有信息量。

问题的本质不是工具不知道量纲，是**人没意识到这是两个量纲** ——
即使工具给每条打上 `[质量]` / `[数量]` 标签，人照样会比。

除非工具**主动判断「你在做无效比较」**，而那需要理解上下文 —— 工具拿不到。

**理由三：与本项目定位冲突。**

本项目一贯是「不猜、只说明代价」。让工具替调用者判定「这个比较无意义」，是猜。

**替代方案（可做，成本低）**：不做拦截，做**提示**：

```
{label:"材料流", expr:"9e7*1e8", unit:"kg/day"}
{label:"成品流", expr:"1e8*25000", unit:"unit/day"}
→ 材料流 = 9e15 [质量/时间]
  成品流 = 2.5e12 [数量/时间]
→ 本批有 2 条量纲不同（质量 vs 数量），若要比较请确认口径
```

只打标签 + 汇总一句，不拒绝计算。**但这条也需要你拍板**：
它要往 `expressions` 元素里加 `unit` 字段，而那正是刚修好的「元素级未知键」位置，
必须同时把 schema 也补上。

### ⚠️ 2.7 「`workspace` 变量写入成功但读不回来」

**报告说**：「变量确实在，但取不出来 —— 这个功能实际不可用。」

**实测**：

```
① set 变量                            → ✓ 变量 2 个
② evaluate + useWorkspaceVariables:true → ✗ Undefined symbol   ← 报告停在这一步
③ set 开关 true（关键一步）             → ✓
④ evaluate total*2                     → 20   ✓ 能用！
```

**根因不是「读取链路损坏」，是使用路径与文档表述**：
`useWorkspaceVariables` 只作为 `action2:"set"` 的参数生效，
在 `evaluate` 上传它**会被忽略**。

而 `help` 里写的是：

```
命名变量：{action2:"set", workspaceVariables:{...}} 存进去
  默认不参与计算；要生效再传 useWorkspaceVariables:true（逐工作区）
```

这句话有歧义：「要生效再传」——传到哪里？读起来像传给 `evaluate`。
**报告就是这么理解的，我也是这么设计的 —— 所以是我的文档缺陷，不是功能损坏。**

**已修**：`help` 改成明确两句：

```
命名变量：{action2:"set", workspaceVariables:{...}} 存进去（默认不参与计算）
  启用：{action2:"set", useWorkspaceVariables:true}  ← 必须走 action2:"set"
  启用后 evaluate 可直接用变量名；本次 variables 参数优先于工作区值
```

**但报告暴露了一个真实的设计问题**：把一个开关放在 `evaluate` 上却无效，
比没有这个参数更糟 —— 正是本项目一直在打击的「以为做了其实没做」。
这条留作改进项。

## 三、报告里最有价值的不是任何技术建议

是这段自省：

> **工具算得准，但不会告诉你「这个算式该不该算」。**
> 它所有的错误都出在**语义层**，不是算术层。

这个判断是对的，而且它解释了为什么报告 3 条误判里有 2 条是
「要求工具做语义判断」—— **那恰恰是它做不到也不该做的事**。
