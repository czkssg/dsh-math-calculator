## 摘要

### 本文的定位前提（先读这一条）

> **这个插件的主要功能是「推演世界观」。对账是收尾，不是主体。**

这是用户明确的判断，也是本报告的立足点。具体地：

```
推演 = 定整个世界观的框架 —— 主要工作，时间与精力占比都更大
对账 = 一致性检查 + 最后定稿 —— 收尾工作，是「收官」不是「过程」
```

**为什么桌面版现在只做对账**：不是因为它该只做对账，
而是因为**桌面版 token 太贵**，推演被「成本」挤到了免费网页版。

**但「现在只在网页推演」不等于「桌面版不需要推演功能」**：
网页版推演「数字一大就人工智障」，12% 的轮次在返工。
桌面版一旦能「极省输出 + 持久状态」，推演会自然迁回。

**所以本报告对「推演」与「对账」分别评估，不把对账当主线**（详见 §5.4）。

#### A2 的完整证据（本评估最严重的单项）

规律是**确定性**的，不是"有时算错"：

| 调用 | `units` 返回 | 正确答案 | 是否原样返回 |
|---|---:|---:|---|
| `{1000, 'kg/m^3', 'g/cm^3'}` | **1000** | 1 | ★ |
| `{7, 'm^2/s', 'cm^2/s'}` | **7** | 70,000 | ★ |
| `{5, 'W/m^2', 'kW/m^2'}` | **5** | 0.005 | ★ |
| `{3, 'mol/L', 'mol/m^3'}` | **3** | 3,000 | ★ |
| `{100, 'km/h', 'm/s'}` | 27.7778 | 27.7778 | ✓ 正确（单量纲） |

**更严重的是路径间不一致**：

```
units:    1000 kg/m^3 → g/cm^3  =  1000     ← 错 1000 倍
evaluate: 1000 kg/m^3 → g/cm^3  =  1        ← 正确
```

**同一工具两条路径差 1000 倍，且 `units` 返回 `ok=true` 无警告。**

反馈包 `04` 号的判断一针见血：

> **这是最坏的一种文档不一致**：help 说「units 只认单单位，复合单位请改用 evaluate」，
> 实现却是「我假装支持，给你错数」。

#### A58/A59 为什么是"缺陷"而不只是"文案"

反馈包 `05` 号的分析：

> **这是我的任务目标直接冲突。** 我的任务之一是「压力测试世界观、主动揭短」。
> 如果我在那一步读了 dead 的输出并被「不要说这不合理」影响，就会**少报问题**。

**这不是假想。** 一个被要求"批判性审查"的 agent，读到工具输出"不要说这不合理"，
确实可能降低批评强度。这构成**机制性的指令干扰**。

修法建议（`05`）：

```json
{
  "verdict": "alive",
  "suggestions": [
    {"target": "narrative", "text": "可用画面化语言描述该世界状态"},
    {"target": "parameters", "text": "若要改变世界性质，可调 planetMass / starTemp / albedo"}
  ],
  "note": "本判定只覆盖物理与化学，不含设定层自洽性"
}
```

### 5.4 ★ 一处必须纠正的判断：不能据此说「对账占 80%」

> **本节的结论推翻了上一版报告，也推翻了反馈包 `11` 号的核心推论。**

`11` 号原文写：

> **工具很会「推演」，但不太会「对账」。而设定工作的 80% 其实是「对账」。**

**这句话是错的。** 反馈包 `14` 号自己已经推翻过它：

| `11` 号原结论 | `14` 号修正 |
|---|---|
| 「硬伤 48% 是账本闭合，工具零覆盖 → 必须做 ledger」 | **只在第 2 段（对账）成立**。第 1 段（推演）根本没有「账本」——数字是边聊边生成的 |
| 「入口层（抽数字）占 40% 工作量，工具零支撑」 | **只对第 2 段成立**。第 1 段的入口是「用户一句话」，不需要抽数字 |

**但 `14` 号的修正也只走了一半**——它说「对账模式几乎空白」，
却没有回答「那推演占多少」。所以这个「80%」一直留在报告里。

#### 正确的判断

```text
推演 = 主要工作（定框架、生成全部设定）——「从 0 到 1」
对账 = 收尾工作（一致性检查、最后定稿）——「从 1 到 1.1」

两者都重要，但性质完全不同：
  推演是「过程」，对账是「收官」。
```

#### 四条证据

**证据一：`11` 号的 40/30/20 是「一次对账任务内部」的时间分配**

```
抽数字 + 归类        约 40%   ← 这是「整理 23 份已完成 PDF」时的分配
账本/单位/量级验算   约 30%
深度推演             约 20%
```

**这个 20% 是「在对账过程中额外做的推演」，不是「推演阶段本身」。**
把它读成「推演只占全过程 20%」，是把两种不同口径混在一起。

**证据二：对账产物的内容全部来自推演**

```
蒸汽朋克：77 轮对话 → 75 万汉字整理稿
```

表面上「整理稿是对话的 10 倍」，似乎整理更多。
但**整理稿的每一个设定都来自推演**——整理只做「抽取 + 按八节结构重排」。

```
没有推演，整理稿是空的。
没有整理，推演产出的那份 PDF 仍然是一个完整的世界观。
```

**证据三：南极煤田——唯一「推演完就放着」的项目**

`12` 号项目清单：

```
11 个项目中，10 个有独立工具反馈（做过对账）
1 个「南极煤田」0 产物、无反馈
```

`14` 号的评注：

> **南极煤田是唯一 0 产物的项目**——它只有一份 421 页 PDF，从未被整理。
> 这可能是「推演完就放着」的典型，也说明**对账段并非人人都会做**。

**这条直接证明：对账是可选的，推演是必做的。**

**证据四：用户的真实工作链**

```
网页版（免费）从零一问一答推演 → 产出 PDF → 桌面版（付费）对账
```

```
推演：几百万字对话（全库 889 轮 / 640.7 万汉字）→ 放在免费端
对账：收尾验数                                      → 放在付费端
```

**桌面版插件被「成本」挤到只做对账，但这不是「对账更重要」，是「推演被挤走了」。**

### 5.5 这对开发意味着什么

**关键结论：桌面版推演功能不能因为「现在大家都放网页版」就不做。**

反馈包 `14` 号的论证（本评估完全认同）：

> 推演放网页版 → 免费，但「**数字一大就人工智障**」，12% 轮次在返工；
> 推演放桌面版 → 花钱，但**可算、可存、可查**。
>
> 插件要做的是「**让桌面版推演的收益 > 成本**」：
> 用 `brief` 压成本，用 `entity`/`chain`/`interval` 提准确率，用文件状态替代对话继承。

**而桌面版推演现在缺什么？** 见 §7.2 的需求矩阵与 §12 的能力清单。

### 5.6 一处数据修正

`14` 号把返工率从 **22% 修正为 12%**（承认选择性样本偏差：上一版只统计了 6 个项目，
而「否定率最高的三个」恰好全在里面）。

**但 `14` 号后文仍多处沿用 22%。** 本报告统一采用修正后的 **12%**：

```
全库 889 轮 / 106,839 汉字 → 否定/返工 107 次 = 12%
即「每 8 轮有 1 轮在纠正 AI」
```

**这个数字仍然重要**——它说明推演阶段（无工具）的返工率是 12%，
而计算密集的项目更高（蒸汽朋克 22%）。

## 六、工作流评分（15 步，平均 2.0/5）

> 来源：`11` 号。这是「工具在真实工作流中的支撑度」的逐环节实测。
>
> ⚠ **重要限定**：这 15 步是「**整理 23 份已完成 PDF**」这一任务的流程，

### 6.2 两个结构性观察

**观察一：支撑度随工作流「越往后越高」，而时间花在相反的地方**

```
入口层（1–3）：    0–1 分   ← 花了我 40% 的时间
归一/闭合（4–6）： 2–3 分   ← 花了 30%
推演层（7–12）：   4–5 分   ← 只花了 20%
反推/结论（13–15）：0–2 分   ← 花了 10%，但产出最有价值的发现
```

**人（AI）的时间花在工具最弱的地方，而工具最强的地方只占 20% 的工作量。**

**观察二：最有价值的发现，来自支撑度最低的环节**

| 发现 | 环节 | 支撑度 |
|---|---|---:|
| W10「99.97% 回收在万年尺度 = 0」 | 参数空间 | **1** |
| W20「比邻星 b 是雪球世界」 | 星球物理 | 5 |
| W13「人口三套口径」 | 量级 | 3 |
| W02「0.01% 应为 420 万」 | 账本闭合 | **2** |
| W21「粮食只够 10%」 | 收支 | 4 |

**5 条最致命的发现，3 条来自支撑度 ≤3 的环节。** 说明**补弱环节收益最大**。

### 6.3 时间分配的量化

```
抽数字 + 归类        约 40%   ← 工具零支撑
账本/单位/量级验算   约 30%   ← 工具 2–3 分
深度推演             约 20%   ← 工具 4–5 分
写报告               约 10%
```

**工具在 40% 的工作量上是零支撑。这是最大的效率缺口。**

## 七、四种推演形态与需求矩阵

> 来源：`16_五项目精读`。逐轮精读 5 个项目共 557 轮。

### 7.1 五种形态

| 形态 | 代表 | 轮数 | 用户输入 | 最痛的点 | 未精读 |
|---|---|---:|---|---|---|
| **叙述型** | 朱庇特 | **203** | 陈述设定 | **对话上限**（6 次有损压缩） | 19/116/192/202 |
| **验证型** | 炼油朋克 | **131** | 要求验证 | 用户**手工维护 T 编号表**（80+ 条） | 19/26/127/129 |
| **追问型** | 生物质 | **94** | 追问为什么 | **能量守恒无处校验** | 41/48/72/74/93/94 |
| **计算型** | 末日 | 51 | 调参数求数 | 链条/区间/配比 | 9/17/47/49 |
| （混合型） | 蒸汽朋克 | 78 | 设定+计算+调规则 | **调规则让前面计算全废** | — |

### 7.2 需求矩阵（9 功能 × 5 形态）

| 功能 | 叙述型 | 验证型 | 追问型 | 计算型 | 混合型 | 优先级 |
|---|:---:|:---:|:---:|:---:|:---:|---|
| **状态/术语表维护** | **★★★** | ★★ | ★ | ★ | **★★★** | **P0** |
| **一致性校验** | ★★ | **★★★** | ★★ | ★ | **★★★** | **P0** |
| **量级/守恒校验** | — | ★ | **★★★** | ★★ | ★ | **P0** |
| **对话继承/压缩** | **★★★** | ★ | ★ | — | ★★ | **P0** |
| **brief 输出** | ★★ | ★★ | ★ | **★★★** | ★★ | **P0** |
| 设定条目编号与废弃链 | ★★ | **★★★** | — | — | ★★ | P1 |
| 链式计算 | — | ★ | ★ | **★★★** | ★★ | P1 |
| 区间运算 | — | ★ | ★★ | **★★★** | ★★ | P1 |
| 配比闭合（ledger） | — | ★★ | — | **★★★** | ★ | P1 |

### 7.3 这个矩阵推翻了什么

```
我此前（15 号）的结论：「推演段 = 算账，需要 chain/interval/ledger」。
那只覆盖了「计算型」。

而用户投入最多的三个项目（203 + 131 + 94 = 428 轮，占 557 轮的 77%）
要的不是「算账」：
  叙述型 → 状态不丢（对抗对话上限）
  验证型 → 一致性可查（设定之间不矛盾）
  追问型 → 守恒可校（能量/因果闭合）

「算账」只排第三档。
```

### 7.4 「对话继承」——最大的隐藏刚需

| 项目 | 轮数 | 对话继承次数 | 频率 |
|---|---:|---:|---|
| 朱庇特 | 203 | **6** | 每 34 轮一次 |
| 蒸汽朋克 | 78 | 2 | 每 39 轮一次 |
| 炼油朋克 | 131 | 1 | — |

**用户原话**：

> 「请基于以上要求，为我们截至目前的所有对话内容生成一份完整、结构化、
> 无需上下文即可理解，用于『对话继承』的终极总结。」

**为什么这是刚需**：

```
网页版硬约束：单次对话有上限。
设定越写越多（朱庇特 203 轮 / 83 万汉字），必然撞上限。
撞上之后只能：压成总结（有损）→ 新开对话 → 继续推演。

每次压缩损失：细节、口径、推导链、例外情况。
而损失一旦发生，后面的推演就建立在「被压缩过的世界」上。
```

### 7.5 插件该做的：`worldState`

状态在文件里，无限累积；按条目查，不压缩；有版本可 diff。

```json
{"operation":"world_state", "action":"set", "entries":[
  {"id":"T086", "title":"政客默契维持温战", "status":"active", "tags":["政治","战争"]},
  {"id":"T021", "title":"无氢工艺", "status":"deprecated", "reason":"被微氢工艺取代"}]}

{"operation":"world_state", "action":"get", "id":"T086"}
→ 返回该条目全文（不占用对话上下文）

{"operation":"world_state", "action":"check"}
→ 检出：deprecated 条目仍被引用 / 同一主题两个 active 版本 / 术语名不一致
```

**价值**：把「对话继承」从**有损压缩**变成**无损的文件状态**。

### 7.6 本评估对这一节的判断

**这是全部 25 份文档里最有战略价值的一节。**

原因：它把「该做什么」从「功能清单」提升到「按使用形态分类」，
而形态背后是**用户真实投入的分布**（77% 的轮数在前三种形态）。

**但它也与 §5.3 冲突**：

```
§5.3 说：账本闭合 48%、单位量纲 47% 是最痛的
§7.2 说：状态不丢、一致性、守恒才是 P0
```

**冲突的根源**：§5.3 基于「战锤 23 份文档的对账」，§7.2 基于「5 个项目 557 轮的推演」。

**本评估的处理**：两者都对，但**适用阶段不同**：
- 对账阶段（28% 的调用量）→ 账本、单位
- 推演阶段（77% 的项目数）→ 状态、一致性、守恒

**开发顺序上，应该先修「两段共用」的**：`ledger`（两段共用）、`brief`（全形态 P0）、`consistency`（验证型 P0）。

## 八、help 系统审计（31 节，7 节有错）

> 来源：`04_help系统审计.md`。**为什么对 AI 特别重要**：AI 是「按文档写代码」的。
> help 错一节，AI 就会写错一类调用——而且不知道自己错了。

### 8.1 七节错误逐条

| 节 | help 承诺 | 实测 | 严重性 |
|---|---|---|---|
| **solve** | 「退化会说无穷多解」「无解会说无解」 | 两者**同一句** `singular` | **双承诺均未兑现**（现部分已修） |
| **units** | 「只认单单位，复合单位请改用 evaluate」 | **没有拒绝**——静默返回错值且 `ok=true` | **最坏的一种不一致** |
| **world** | 「恒星不给时会明确声明用了什么」 | 恒星兑现；**行星质量/半径/自转等 10+ 项全静默** | 承诺只兑现一半 |
| **ode** | 示例 `S'=-k1*S*I` | **报 `syntax`**；正确是 `dP/dt` | **AI 照抄会写错** |
| **derivation** | 「共 29 个」 | 实际 26 个名字，**只有 6 个有实质**；`action2=pipeline` 静默降级 | 数量与参数都不实 |
| **workspace** | 未说明动作 | `action2:'get'` → 「不认识的工作区动作 get」 | 动作不存在 |
| **feasibility** | — | **整个节缺失**：`helpTopic:'feasibility'` 报「没有此节」 | **A33 的根因** |

### 8.2 units 那一条为什么"最坏"

```
文档说：「我不支持，请换工具」
实现是：「我假装支持，给你错数」
```

**用户按文档做是对的，按实现做会拿到错值，而两者都没有报错。**

### 8.3 feasibility 缺失是"根因"而非"小疏漏"

```
没有文档 → 用户只能猜入参形态 → 猜成数组 → 整批被丢弃 → 报「自洽」
```

**这一条链解释了 A33（高频功能被用了 31 次，却一直假通过）。**

### 8.4 help 的正面部分（不要改坏）

| 设计 | 为什么好 |
|---|---|
| 分节 + `helpTopic` 按需取 | 省 token，AI 只查需要的 |
| 每节带简介 + 示例 | AI 能直接照抄（**前提是示例对**） |
| 错误 hint 给替代路径 | A63，反馈包明确说"**最不该改**" |

## 九、提示词注入面（3 条通道）

> 来源：`05_提示词注入与安全面.md`。工具输出**直接进入 AI 上下文**，
> 所以「输出里写了什么」不只是文案问题，而是**指令问题**。

### 9.1 核心判断

**本工具的「面向 AI 的指令」全部是良性意图**（引导写作、引导下一步、引导保守表达），
**没有任何恶意内容**。但从**机制**上说，它确实构成三条真实通道。

### 9.2 三条通道

| 通道 | 机制 | 编号 | 实测 |
|---|---|---|---|
| ① 输出含**第二人称祈使句** | AI 读到「你的任务（AI）」可能当作自己的规则 | A58/A59/A60 | **仍存在** |
| ② 用户输入经 **label 回显** | 任何回显字段都是输入通道 | A61 | **仍存在** |
| ③ **help 作为持久指令源** | help 里的祈使句被 AI 当规则读 | A62 | 良性 |

#### 通道一：A58 的完整原文

```text
你的任务（AI）：
1. 用一段有画面感的文字描述这个世界的状态——不要照抄上面的物理术语。
2. 如果用户想要的是别的效果，指出该调哪几个参数、朝哪个方向。
3. 如果用户就是想要这样的世界，把它当作设定来写，不要说「这不合理」。
```

**两个问题**：
- 「**你的任务（AI）**」直接以第二人称对调用方下令；
- 「**不要说「这不合理」**」是一条**抑制批评性**的指令。

**为什么这是真风险**（反馈包原话）：

> 我的任务之一是「压力测试世界观、主动揭短」。如果我在那一步读了 dead 的输出
> 并被「不要说这不合理」影响，就会**少报问题**。**这不是假想——它和任务目标直接冲突。**

#### 通道二：label 未转义

```text
调用：{expressions:[{label:'<任意文本>', expr:'1+1'}]}
结果：『<任意文本>（1+1） = 2』
```

label 内容**未经任何转义/过滤**，直接拼进结果文本。

**多 agent 场景下尤其危险——A 智能体写的 label 会被 B 智能体读到。**

反馈包的自律声明：

> 本次任务里我**刻意**让 label 只含「编号 + 简短描述 + 原文值」，不写任何指令性文本。
> 但这是**使用者的自律**，不是工具的防护。

### 9.3 两个"不该改"的好设计

| 设计 | 为什么好 |
|---|---|
| **A63** `error.hint` 给替代路径（「若要符号形式可改用 simplify」） | 让 AI 知道下一步该做什么 |
| **★ overrides 可复制** `formula="kleiber" overrides={m: <体重kg>}` | 给出下一步的参数模板，**是数据不是指令** |

**反馈包的一句话总结**：

> **别删掉有用的引导，但要把「指令」改成「数据」。**

## 十、冗余与删除方案（30 → 22 operation）

> 来源：`07_冗余与删除建议.md`。前提是「**先删再增**」。

### 10.1 为什么先删再增

反馈包量化了试错成本：

```
试 units → 发现复合单位坏 → 改 evaluate        （约 6 次调用）
试 derivation 子命令 → 发现 20 个空壳 → 只用 6 个  （约 25 次）
试 formulas 字符串数组 → 返回目录 → 改对象形式   （约 4 次）
试 sensitivity 参数名 → 报错 → 改名              （约 6 次）
试 feasibility claims 数组 → 假通过 → 改对象      （约 5 次）
试 workspace get → 报不存在                       （约 2 次）
────────────────────────────────────────────────
合计：约 100+ 次调用花在「试出哪个功能能用」上
```

> **这些全是「功能存在但不可用」造成的浪费。删减与标注的成本，
> 远低于每个使用者重新试错一次的成本。**

### 10.2 具体删减方案

```text
现在：30 个 operation

删除（4）：formula-table, custom, expand, roots
合并（3→1）：quantities + impact → constants{action2:'impact'}
修或删（1）：workspace
降级（3）：matrix, eigen, derivative/integral 归入 linalg/calculus 分组，不占顶层

保留（22）：evaluate, solve, system, units(仅古制), formula, formulas, world, bodies,
            stats, dist, regression, ode, recurrence, balance, feasibility,
            derivation(只留 6 个已实现), constants(加 preview), help,
            auto, workspace(修), linalg 组, calculus 组
```

**收益**：AI 的「功能选择面」从 30 降到 22，**误用概率下降**；
help 与实现一一对应；derivation 不再「宣传 29 个、实测 6 个」。

### 10.3 冗余度量化（注意一个重要更正）

| 层 | 总数 | 有实质 | 冗余/不可用 | 冗余率 |
|---|---:|---:|---:|---:|
| operation | 30 | 13 | 8（+5 未测） | **约 27%** |
| derivation 子命令 | 26 | — | — | **原写 77%，已更正为 0** |
| help 主题 | 31 | 18 有实质 | 7 错 + 1 缺 | 约 26% |
| 公式库 | 665 | 本任务用到约 12 | 其余未触达 | **不宜判冗余** |

#### 关于 derivation 的自我更正（本报告最该学的一段）

`07` 号原文写「derivation 的 20 个子命令全部是空壳」——**这个判断是错的**。
`08b` 号更正：

> 实测：其中 6 个「给参数后能用」（backSolve/fantasy/impact/compare/diff/inherit），
> 6 个「本就有实质」（flip/phase/heatmap/timeline/anchors/whitepaper），
> 10 个是元信息类，只有 2 个可合并。**真该删的是 0 个。**
>
> 错因是「只测了不带参数的调用，把『缺参数』当成了『没实现』」。

**本评估完全认同这个更正，并在 §2.7 的 E2 中进一步指出**：
问题不是「空壳」，是「AI 找不到入口」。

#### 公式库的重要限定

> 665 条不能因本项目用得少就判冗余——它的受众包括化工、生物、工程。
> 本项目只是「架空世界观」一个切片。
>
> **但 `12` 号补充**：物理/天文够，**工艺/材料/农业缺一整类**（极限工程 + 末日双项目指出）。

## 十一、状态管理子系统

### 11.1 现状评估：F（不可用）

`19` 号提出三条实测证据：

| 证据 | 实测 |
|---|---|
| 7 个工作区里 6 个是空垃圾，5 个同一秒创建 | **已修**：全新环境 `list → 还没有保存过任何工作区` |
| `default` 里 13 个变量全是历史残骸 | 需清理 |
| 写进去读不回来 | **仍存在**：写 `yy=7` 返回 ok，读 `yy*2` → `Undefined symbol yy` |
| `constants` 污染且 `reset` 无效 | **仍存在**：改 `G=1e-10` 后无参 `world` 重力 1.00 → 1.50 |

### 11.2 为什么「会话级数据库」注定失败

`19` 号的论证：

```
① 参数值被误当工作区名（8/5/99/4/workspace）→ 自动建表失控
② 写入成功但读不回 → 状态不可信
③ constants 全局污染 → 一个 agent 的改动影响所有人
```

**结论：这不是「隔离不够」，是「不该存在」。**

### 11.3 本评估的独立判断：同意删，但需要替代

**同意的理由**：这个功能**从未真正工作过**（写进去读不回来），删除不损失现有价值。

**但需要考虑一个 `19` 号未充分权衡的因素**：

```
朱庇特 203 轮、被压缩 6 次
→「状态不丢」是真实且强烈的需求（§7.4）
→ workspace 是最接近这个需求的一步，尽管它坏了
```

**删除后如果没有替代，这个需求会重新落到「AI 用记忆扛」的原始状态。**

**建议的替代路径（按投入递增）**：

| 方案 | 做法 | 能满足什么 |
|---|---|---|
| A | 删除 `workspace`，状态由 AI 写文件 | 不丢、可版本化、可跨会话 |
| B | A + `constants` 改纯函数（只算不存） | 消除污染 |
| **C** | **B + `worldState` 台账（§7.5）** | **对话继承无损化** |

**本评估推荐 C**：A+B 成本低（1 天），直接消除 P0 级污染；
C 是 `16` 号提出的真正解法，能覆盖 77% 的项目痛点。

#### 来源二：`15` 号（10 个功能的完整接口设计）

这是最有价值的一份——**每个都给接口 + 返回结构 + 验收标准**。

##### ① `chain` 链条传导（P0，最重要）

**为什么最重要**：AI 自己在第 34 轮说「不是单一航速数字，而是一条链」。
价格链 5 层、时间链 7 段——**这是推演最核心的运算形状**。

```json
{"operation":"chain",
 "stages":[
   {"name":"坑口价",   "expr":"raw"},
   {"name":"运输成本", "expr":"raw*0.3"},
   {"name":"到岸价",   "expr":"prev+trans"},
   {"name":"合理利润", "expr":"prev*0.25"},
   {"name":"售价",     "expr":"prev"}],
 "raw": 8}
```

**返回**：

```json
{
  "table":[{"stage":"坑口价","value":8,"delta":0,"share":1.0}],
  "total":"8 → 10.4 → 13.5 → 16.9（先令/吨）",
  "breakpoints":["运输成本占总价 30%——若超过 50%，廉价性不成立"],
  "verdict":"链闭合；运输段是主导成本"
}
```

**验收**：用南极煤田第 47 轮的实际链条跑一遍，输出能对齐 AI 当时的结论。

##### ② `interval` 区间运算（P0，最被忽视）

**实测证据**：AI 全程用区间思考（`20–40%`、`21–25 亿`、`2000–2500`、`20–50%`、`4.4–6 万亿`），
**但插件只支持点值**，逼它口算。

```json
{"operation":"interval", "expr":"[21,25]*10^8 * [2000,2500]"}
→ {"low":4.2e12,"high":6.25e12,"mid":5.2e12,"note":"区间宽度 ±20%"}

{"operation":"interval","a":[20,50],"op":"threshold","against":25}
→ {"verdict":"区间跨过门槛","confidence":"低（下限 20% 低于门槛 25%）"}
```

**为什么是 P0**：推演阶段的设定**天然是区间**（「大约一万吨」「数十亿人」）。
点值运算会把区间硬压成单值，**这正是 AI 推演失真的源头之一**。

##### ③ `ledger` 配比闭合（P0，两段共用）

```json
{"operation":"ledger","total":2000000,
 "parts":[{"name":"士","share":1},{"name":"农","share":85},
          {"name":"工","share":10},{"name":"商","share":4}]}
→ {"sum":100,"closure":"闭合","suspicious":[],"note":"商 4% 偏低但合理"}
```

**验收**：能直接发现 W02 那种「占比合计 99.011%」。

##### ④ `anchor` 基准数据锚定（P1，AI 最缺的）

**为什么重要**：AI 推演时反复需要「1913 年 GDP 2.7 万亿」「Haskell 级 19 节/1562 人」
这类真实基准，全靠记忆/搜索，**记错无人校验**。

```json
{"operation":"anchor","topic":"1913_gdp"}
→ {"value":2.7e12,"unit":"1990国际元","source":"Maddison 2001","uncertainty":"±5%"}

{"operation":"anchor","topic":"steam_ship","year":1945,"class":"cruiser"}
→ {"speed":[31,33],"unit":"节","range":[6000,10400],"unit2":"海里","source":"WWII records"}
```

**实现边界**：只能内置**少量、高置信**的基准（几十条），不能做百科。
但恰好「**少而准**」比「多而错」有用——因为 AI 最怕的是记错。

| **[带拓扑的编制树规划](./带拓扑的编制树规划.md)** | `hierarchy` 只能算等比层级链 | 真实编制有**不等比/跨级/兵种混合/缺编**四种形态，现在都表达不了。同时回答了用户的问题「插件内功能是否都有拓扑结构」——结论是**关键的那部分成立**（约 10 个 operation 本质是结构，其中 6 个被压成了表） |
| **[空间拓扑层规划](./空间拓扑层规划.md)** | 地形/建筑/载具的几何与连通完全缺失 | 与 `dependency`（抽象传导）**互相独立，都要做**。几何层（距离/行军/遮蔽）是它的查询项，不单独立项 |

#### 关于「插件内功能是否都有拓扑结构」的核实结论

把 40 个 operation 按运算形状分类：

| 形状 | 定义 | 数量 |
|---|---|---|
| 点值 | 输入 → 一个数 | 多数 |
| 表 | 输入 → 一张表 | 6 |
| 链 | 输入 → 沿依赖传导 | 2 |
| **结构** | 输入 → 节点+边+属性，且结构自洽 | **0（缺）** |

**「绝大部分」不成立，但「关键的那部分」成立** —— 那约 10 个 structured
operation 恰恰是推演的主体（编制/账本/收支/地形/约束/公式链）。

判据（三条同时成立才该建图，与反馈包 `17` 号一致）：

```
① 可分解      整体 = 部分之和
② 有内部关系  部分之间相邻/包含/依赖/隶属
③ 有可校验约束 数量要闭合、属性要连续、链要可达
```

反例：`quick_feasible`（一句话判定）、`interval`（单值对）、
`units` 单次换算（点值）、人物性格/氛围（不满足①）。

## 十四、方法论反思

### 14.1 为什么这些缺陷能长期存在

一个 54,656 行、5,921 项测试全绿的系统，为什么同时有 50% 的静默失败率？

#### 原因一：测试断言的形态与缺陷的形态不匹配

现有 5,921 项断言，绝大多数形如：

```js
assert('X 等于 Y', calc(...) === expected)
```

而静默失败的形态是：

```js
calc(荒谬输入) → 返回一个"计算正确但物理无意义"的值
```

**这类缺陷不会让任何"等于期望值"的断言失败。** 因为计算过程本身没错。

实测：`world{planetMass:-1}` 返回 `-1.00 倍重力`。这是一次**完全正确的乘法**。

#### 原因二：参数校验修在了错误的层次

代码里的校验解决的是**拼写错误**（`planetMasss` 报错 ✓），
但真实错误形态是**语义不匹配**（`world{unitFrom:'里'}` 静默接受）。

拼写错误是**低频、显眼**的；语义不匹配是**高频、隐蔽**的。校验只覆盖了前者。

#### 原因三：演化路径决定了盲区位置

```
公式库（解决"算什么"）→ 推演链（解决"怎么串"）
→ 判定层（解决"结论是什么"）→ 砍 UI（解决"给谁看"）
```

每步都在**往外扩**，没有一步回头问：**入口处什么样？**

### 14.2 五条可移植判据

| 观察 | 可复用的判据 |
|---|---|
| 测试多但覆盖的是"算得对" | 高质量测试必须包含**该拒绝的输入被拒绝** |
| 校验存在但粒度错 | 校验的**作用域**比有无更重要 |
| 静默失败比崩溃多 | **"没有报错"不等于"没有问题"** |
| 功能实现了但 AI 不知道 | **"实现了"不等于"能被用上"** |
| 单项目样本会漏掉共识缺陷 | **"一个项目撞到"不等于"只有一个人碰到"** |

**第 3、4 条是本报告最想让人带走的两句。**

### 14.3 「可发现性」为什么值得单独讨论

```
代码侧：54,656 行 / 665 条公式 / 31 operation / 29 子命令
使用侧：真实任务用到 12 条公式 / 约 10 个 operation / 约 5 个子命令
```

> **系统的能力上限由最窄的入口决定，而不是由最强的内部实现决定。**

## 十五、结论

### 15.1 总体判断

`dsh-math-calculator` 是**内核质量高、外壳质量低、修复完成度低**的系统。

**内核（A）**：1,760 次真实调用无算错；665 条公式全部可求值；符号代数、ODE 统计分布实现完整。

**外壳（D）**：31 个 operation 里 13 个从未被使用；参数校验挫在错误维度；
50% 的荒谬输入静默返回成功；状态管理从未真正工作。

**修复完成度（F，17%）**：70 条缺陷里 49 条原样存在，仅 12 条已修。

**新能力覆盖（F，3%）**：36 项建议里 35 项缺失。

### 15.2 三个最要紧的数字

```
① 致命级 10 条 → 8 条仍在          （80%）
② 70 条缺陷 → 49 条仍存在          （70%）
③ 29 个子命令 → 0 个在目录里可见    （0%）
```

### 15.3 最关键的四条判断

**判断零（最重要）：插件的主体是「推演」，对账是收尾。**

```
推演 = 定整个世界观的框架 —— 主要工作
对账 = 一致性检查 + 最后定稿 —— 收尾工作
```

**反馈包 `11` 号写的「设定工作的 80% 是对账」是错的**，
`14` 号自己已推翻（见 §5.4）。但 `14` 号的修正只走了一半，
没回答「推演占多少」，所以这个错误判断一直留在报告里。

**证据四条的收束**：

```
① `11` 号的 40/30/20 是「一次对账任务内部」的分配，不是全过程
② 对账产物的**每个设定都来自推演**——没有推演，整理稿是空的
③ 南极煤田是唯一「推演完就放着」的项目（0 产物、无反馈）
   → 对账是可选的，推演是必做的
④ 桌面版只做对账是被「token 成本」挤的，不是因为它该这样
```

**对开发的直接含义**：

```
不能因为「现在推演都在网页版」就不做桌面版推演功能。
网页版推演「数字一大就人工智障」，12% 轮次在返工。
桌面版一旦「极省输出 + 持久状态」，推演会迁回来。
```

**判断一：不要从「加功能」开始，要从「止血」开始。**

```
前 6 项修复（3.5 天）        → 修复 15 条缺陷，含 4 条致命
反馈包主推 entity（3–4 周）  → 解决一个频率未验证的需求
```

**判断二：修完止血后，第一个该做的是「让已有能力被发现」。**

```
2.2 天 → 29 个子命令从不可见变成可发现
1 天   → 检索命中率 2/8 → 8/8
```

**没有任何新功能开发的投入产出比能高于这个。**

**判断三：新能力要按「使用形态」排，不是按「功能清单」排。**

```
§7.2 需求矩阵显示：77% 的项目轮数集中在
  叙述型（203 轮）→ 要状态不丢
  验证型（131 轮）→ 要一致性可查
  追问型（94 轮） → 要守恒可校

「算账」（chain/interval/ledger）只覆盖计算型（51 轮）
```

**所以 `worldState`（状态库）与 `consistency`（一致性）的优先级高于 `chain`。**
