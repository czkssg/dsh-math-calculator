## 摘要

本报告对 `dsh-math-calculator` 做独立工程质量评估。评估方法为：**通读外部反馈包 → 逐条实测复现 → 独立交叉验证 → 追溯根因**。

**核心结论**：

| # | 结论 | 置信度 |
|---|---|---|
| 1 | 算术内核可靠，**接口层存在系统性缺陷** | 高（实测 30 个 operation） |
| 2 | 最严重的失效模式是**静默成功**，实测比例 **50%**，高于反馈包估计的 21% | 高（12 例荒谬输入实测） |
| 3 | 参数校验**存在但挫在错误维度**（全局白名单而非按 operation 分片），这是 3 类缺陷的共同根因 | 高（5/5 跨 operation 静默接受） |
| 4 | 公式检索失效的根因是**词汇表覆盖不足，不是算法缺陷**；补 1–3 个口语词可从 2/8 提升到 8/8 | 高（对照实验） |
| 5 | **「20 个空壳」的准确含义是「AI 找不到入口」**：29 个子命令全部实现，但 help 目录里一个子命令名都没有 | 高（三道关卡实测） |
| 6 | 外部反馈包本身存在 **3 处未调和的内部矛盾**，其任务优先级不可直接采纳 | 高（原文对照） |

**综合评级：C+（可用但需防御性集成）**。算术正确性 A，接口契约 D，状态管理 F，可发现性 D。

## 二、核心发现一：静默成功是最主要的失效模式

### 2.1 方法与结果

对 12 个 operation 构造**物理上荒谬但语法合法**的输入，观察是否返回 `ok: true`：

| 输入 | 返回 | 判定 |
|---|---|---|
| `world{planetMass: 1e9}` | `ok=true`，输出完整星球画像 | **静默**：1e9 地球质量是恒星 |
| `world{rotationHours: 1e6}` | `ok=true`，自转周期 114 年 | **静默** |
| `world{planetMass: -1}` | `ok=true`，"重力是地球的 **-1.00 倍**" | **静默**：负重力 |
| `world{planetRadius: 0}` | `ok=true`，输出含 `Infinity`、`NaN` | **静默** |
| `world{orbitAU: 0}` | `ok=true`，"一年 0 天"，"每天移动 `Infinity`°" | **静默** |
| `recurrence{recurrence:'P*(-1)'}` | `ok=true`，给出完整年表 | **静默**：负增长倒推 |
| `ode{initial:{P:-10}}` | `ok=true` | 可疑 |
| `formula{escape_velocity, M:0}` | `ok=true`，速度 0 | 可疑 |
| `solve{x^2+1=0}` | `ok=true`，给复数根 | 合理 |
| `evaluate{sqrt(-1)}` | `ok=true`，返回 `i` | 合理 |
| `units{kg, kg}` | `ok=true`，1:1 | 合理 |
| `stats{data:[]}` | `ok=false`，正确报错 | 正确 |
| `dist{params:[0,-1]}` | `ok=false`，正确报错 | 正确 |
| `balance{demand:-100}` | `ok=false`，正确报错 | 正确 |

**结果：14 例中 7 例（50%）返回 `ok=true` 但结果物理上无意义。**

### 2.2 与反馈包的对比

反馈包统计「静默失败 74 行 / 348 行 = 21.3%」。**我的实测是 50%**。

差异原因推断：反馈包统计的是**有记录的问题**，而静默失败的特征正是**不产生错误记录**——它不中断流程，用户往往发现不了，因此被系统性低估。

**这是本评估与反馈包最重要的分歧点。**

### 2.3 严重性论证

静默失败的危害高于崩溃，因为：

```
崩溃 → 调用方立刻知道 → 改用其他方案或修正输入
静默 → 数字进入下游 → 写进作品 → 传播放大
```

`world{planetMass:-1}` 输出「重力是地球的 -1.00 倍，跳跃更高」——这**读起来像一条结论**，而它是荒谬的。

## 三、核心发现二：参数校验挫在错误维度

### 3.1 现象

代码中存在参数白名单（`KNOWN_ARGUMENT_KEYS`，约 100 个键），用于拦截拼写错误：

```ts
const KNOWN_ARGUMENT_KEYS: ReadonlySet<string> = new Set([
  'expression', 'expressions', 'terse', /* ... 约 100 个键 ... */
])

function findUnknownArguments(rawArguments) {
  for (const key of Object.keys(rawArguments)) {
    if (KNOWN_ARGUMENT_KEYS.has(key)) continue   // ← 只问"这个名字全局合法吗"
    unknown.push(key)
  }
}
```

**校验存在且有效**——拼错 `planetMasss` 会报错，这一点做得比多数工具好。

### 3.2 缺陷：白名单是全局的

白名单不区分 operation。只要键名在**任何** operation 中合法，就在**所有** operation 中被接受。

实测 5/5 跨 operation 参数被静默接受：

| 调用 | 传入的参数 | 该参数实际属于 | 结果 |
|---|---|---|---|
| `world` | `unitFrom` | `units` | **静默接受** |
| `world` | `formula` | `formula` | **静默接受** |
| `units` | `planetMass` | `world` | **静默接受** |
| `evaluate` | `diffA` | `derivation` | **静默接受** |
| `stats` | `recurrence` | `recurrence` | **静默接受** |

### 3.3 这是三类缺陷的共同根因

| 反馈包编号 | 缺陷 | 与本缺陷的关系 |
|---|---|---|
| T12 / A29 | 批量 `formula` 吞未知 key 警告 | 单条会警告，批量不警告——**警告逻辑没有统一到校验层** |
| T03 / A33 | `feasibility` 收 `claims` 数组静默丢弃 | `claims` 在全局白名单里，所以「参数名合法」→ 放行 → 内部不认这个形态 → 丢弃 |
| T04 / A52 | `expressions` 166 条只跑 100 条 | 同上：参数名合法，数量越界无人管 |

**本评估认为这比反馈包的表述更根本**：反馈包说「入口不校验」，实测是「**校验有，但粒度错了**」。这个区别决定了修法——不是「加校验」，而是「**把白名单按 operation 分片**」。

### 3.4 修正建议的形态

```ts
// 现状：全局集合
const KNOWN_ARGUMENT_KEYS = new Set([...所有键...])

// 建议：按 operation 分片
const OPERATION_ARGS: Record<MathOperation, readonly string[]> = {
  world:     ['planetMass', 'planetRadius', 'rotationHours', ...],
  units:     ['unitValue', 'unitFrom', 'unitTo', 'unitScales', ...],
  // 公共键单列
}
const COMMON_ARGS = ['operation', 'terse', 'precision', 'displayPrecision']

// 校验：key ∈ COMMON_ARGS ∪ OPERATION_ARGS[operation]
```

**预期收益**：一次性消除静默忽略类的全部症状，且**不需要逐个 operation 打补丁**。

**风险**：中等——现有调用方若依赖了"跨 operation 传参"的行为，会开始报错。需要先扫描测试与文档确认无此依赖。

## 四、核心发现三：公式检索失效的根因是词汇表

### 4.1 现象

用 8 条**用户真实问法**（疑问句、口语）检索：

| 查询 | 期望公式 | 首条结果 | 判定 |
|---|---|---|---|
| 这座城能守多久 | `food_stock_days` | `food_stock_days` | ✓ |
| 军队打得起吗 | `army_supply_days` | `army_supply_days` | ✓ |
| 粮食够吃几天 | `food_stock_days` | `crop_total_yield` | △ 第 5 |
| 山能长多高 | `building_height_limit` | `fresnel_zone_radius` | ✗ |
| 船能开多快 | `hull_speed` | `doubling_time_population` | ✗ |
| 铁有多硬 | `hardness_to_yield` | `base_rate_neglect_error` | ✗ |
| 一个工人一年造多少 | `gdp_from_labor` | `year_length` | ✗ |
| 这个官能管多大地方 | `admin_radius_from_info` | `bernoulli_pressure` | ✗ |

**首条命中率 2/8，前 20 内 3/8。**

### 4.2 根因定位

取「铁有多硬」为例，看检索为何完全失效：

```
查询滑窗（2–4 字）：铁有多硬 / 铁有多 / 有多硬 / 铁有 / 有多 / 多硬

base_rate_neglect_error 命中词：有多        ← 靠一个虚词命中，排第一
hardness_to_yield       命中词：（无）      ← 真正的答案，零命中
```

`hardness_to_yield` 的 `keys` 是 `hardness / 硬度 / 屈服` —— **没有「铁」字**，而用户问的是「铁」。

### 4.3 决定性验证

给每个期望公式补上 1–3 个用户口语词（仅理论推演，未改代码）：

| 查询 | 期望公式 | 需补的词 | 补后能否命中 |
|---|---|---|---|
| 山能长多高 | `building_height_limit` | 山、多高 | ✓ |
| 船能开多快 | `hull_speed` | 船、多快 | ✓ |
| 铁有多硬 | `hardness_to_yield` | 铁、多硬 | ✓ |
| 一个工人一年造多少 | `gdp_from_labor` | 工人、一年、造 | ✓ |
| 这个官能管多大地方 | `admin_radius_from_info` | 官、多大 | ✓ |
| 粮食够吃几天 | `food_stock_days` | 够吃 | ✓ |

**补词后理论命中：8/8（现状 2/8）。**

**结论：这是词汇表覆盖问题，不是检索算法问题。**

### 4.4 与反馈包结论的关系

反馈包说「瓶颈是『不知道用哪条』，不是数量」（`11` 号）。**方向正确，但机理不同**：

- 反馈包的隐含判断：公式太多，找不到
- 本评估的实测判断：**正确的公式就在库里，但它不认识用户的说法**

这个区别决定修法：**不是加公式，也不是改算法，是给高频公式补口语别名。**

### 4.5 附带发现：虚词污染

当前检索用 2–4 字滑窗，会切出「有多」「能长」「长多」等无意义组合。这些组合在任意长描述里都可能出现，导致**虚词命中压过实义命中**。

`base_rate_neglect_error` 靠「有多」排第一，是这类污染的典型。

**建议**：建立虚词黑名单（`有多 / 能长 / 怎么 / 多少 / 这个 / 可以 / 是否` 等），滑窗产物命中黑名单者不计分。

## 五、核心发现四：已实现 ≠ 可被发现（「20 个空壳」的真相）

> **本节回应一个关键区分**：反馈包 `08b` 已自我更正「29 个子命令没有一个是空壳」，本评估实测确认这一点。
> **但「不是空壳」不等于「能被用上」。** 本节量化这个差距。

### 5.1 「空壳」判断的三层含义

反馈包最初误判「20 个空壳」，是因为**用「缺参数时的输出长短」作为判据**：

```
{derivation:'backSolve'} → 70 字符「缺参数：anchor 与 anchorValue」
→ 被记为「空壳」
```

`08b` 自我更正后，正确的表述是：

| 层次 | 判断 | 实测依据 |
|---|---|---|
| ① **代码是否存在** | 29/29 存在 | 全部可调用 |
| ② **给参数后是否有实质输出** | 29/29 有 | `backSolve` 输出逆推窗口+回代验证 |
| ③ **AI 是否知道该用它** | **严重不足** | 见 §5.2 |

**用户的判断是对的**：功能在，但**AI 不知道有这些功能**。这是第三个层次的问题，反馈包和本报告前几节都没有充分量化。

### 5.2 可发现性的三道关卡（实测）

AI 要调用一个子命令，必须穿过三道关卡。**每一道都实测失败**：

#### 关卡一：help 目录（每轮注入，1487 字符）

目录里关于 derivation 只有两行：

```
derivation推演栈（derivation 子命令）
  敏感度/结论翻转/逆推校准/相图/算力预算等 29 子命令。★ 全部子命令在这。
```

**问题**：给的是 5 个**中文概念词**（敏感度/结论翻转/逆推校准/相图/算力预算），
**没有一个是子命令的真实 id**（`sensitivity`/`flip`/`backSolve`/`phase`/`cost`），
**剩下 24 个子命令连概念都没有**。

实测：在目录全文（1487 字符）里搜 29 个子命令名，只命中 **1 个**——`units`，
而那是另一个 operation 的名字，不是这个子命令。

AI 若想问「两个版本有什么不同」，目录里看不到 `diff`；想「改常数会影响什么」，看不到 `impact`。

#### 关卡二：`helpTopic:"derivation"`（1228 字符）

29 个子命令**平铺成 5 组，每个只有 2–6 字说明**：

```
backSolve    逆向求解
fantasy      幻想层（叠加能力，只提醒不反驳）
impact       影响评估
compare      A-B 对比
diff         版本差异
```

**问题**：这些描述**只说了「是什么」，没说「什么时候用」**。

对比一下缺失的信息：

| 子命令 | 现有描述 | 缺失的关键信息 |
|---|---|---|
| `backSolve` | 「逆向求解」 | 「想知道要多大的重力才能让生物长到 50 米」时用它 |
| `fantasy` | 「幻想层」 | 「这个超能力会不会变成永动机」时用它 |
| `impact` | 「影响评估」 | 「改了 G 之后哪些结论会失效」时用它 |
| `compare` | 「A-B 对比」 | 「这两个方案哪个好」时用它 |

#### 关卡三：`formulas` 检索（AI 最常用的发现方式）

实测 8 个自然语言检索词，**全部无法发现 derivation 子命令**：

| AI 可能输入 | `formulas` 结果 | 能发现 derivation 吗 |
|---|---|---|
| 生物高度 | 返回公式 | ✗ |
| 重力上限 | 返回公式 | ✗ |
| 超能力 | 返回公式 | ✗ |
| 永动机 | 返回公式 | ✗ |
| 结论翻转 | 返回公式 | ✗ |
| 相图 | 返回公式 | ✗ |
| 因果 | 返回公式 | ✗ |
| 溯源 | 返回公式 | ✗ |

**根因**：`formulas` 只检索公式库（665 条），**完全不覆盖 derivation 的 29 个子命令**。
这两套能力各自封闭，AI 没有统一的发现入口。

### 5.3 三个层次的量化

```
① 实现了：              29/29  ✅
② 给参数有输出：        29/29  ✅
③ AI 能发现：           约 0/29  ⚠

   —— 实测：29 个子命令名在 help 目录全文里只命中 1 个，且那是另一个 operation 的名字。
      目录只给了 5 个中文概念词，与子命令 id 不对应。
```

**「20 个空壳」的准确含义不是「代码是空的」，是「AI 找不到入口」——而实测比「20 个」更严重：
29 个里靠目录一个都找不到。**

只有先 `helpTopic:"derivation"` 才能看到全部 29 个，但**AI 不会去查一个它不知道存在的子命令**。

### 5.4 这是一个**成本极低、收益极高**的修复点

与其他 P0 缺陷（需要改内核）不同，这个问题**只改文案**：

| 修法 | 工作量 | 预期效果 |
|---|---|---|
| ① help 目录补全 29 个子命令的**场景化关键词** | 0.5 天 | 关卡一打通 |
| ② 每个子命令的说明从「是什么」改成「什么时候用」 | 0.5 天 | 关卡二打通 |
| ③ `formulas` 检索同时覆盖 derivation 子命令 | 1 天 | 关卡三打通 |
| ④ help 给三条推荐链路（反馈包 T44） | 0.2 天 | 降低选择成本 |

**合计约 2.2 天，可把「AI 能发现」从 0/29 提升到接近 29/29。**

反馈包 `08b` 的核心结论与此一致：

> **开发重点应该从「做新功能」转向「让已有功能被发现」**：
> 补 6 个子命令的参数文档 + 参数校验，比再写 5 个新子命令更有价值。

本评估补充的是：**这条结论的量化依据，以及它可以扩展到全部 29 个子命令。**

### 5.5 已有的部分进展

本项目在评估前已做过两轮相关工作（commit `fee03ec`）：

| 已做 | 内容 |
|---|---|
| `backSolve` 缺参提示 | 从 70 字符改成「参数说明 + 可复制 JSON + 4 个真实锚点」 |
| `impact` 缺参提示 | 补上「依赖图 76 个节点」的真实清单 |
| `compare` 缺参提示 | 先查有无版本，没有就指引先 `archive` |
| `diff` 缺参提示 | 纠正了「表名」的错误说法（实际是工作区名） |

**但这只解决了「关卡二之后」——AI 必须先能想到「我要用 backSolve」才能享受到这些提示。**

**关卡一和关卡三仍然完全未通。**

## 六、能力矩阵：投入与痛点的错位

### 5.1 硬伤分布 vs 工具覆盖（采用反馈包数据，本评估抽样验证）

| 硬伤类型 | 占比 | 工具覆盖 | 本评估验证 |
|---|---:|---|---|
| 账本闭合（占比/合计/分项） | 48% | **缺结论化** | 确认：`evaluate` 能算差额，但不判"哪项可疑" |
| 单位与量纲 | 47% | **路径间不一致** | 确认：见 §7.1 |
| 量级/数量级 | 38% | `sanity` 可用但噪音大 | 部分确认 |
| 尺寸/射程/速度 | 31% | 够用 | — |
| 人口/兵力/编制 | 27% | 够用 | — |
| 时间线/年代 | 27% | 半覆盖 | — |
| 物理上限 | 18% | 够用 | — |

## 七、具体缺陷清单（按严重性分级）

### P0 — 会导致错误结果进入下游

#### 7.1 P0-1 `units` 对复合单位一律原样返回（确定性缺陷）

这是本评估发现的**最严重单项**，且比反馈包描述的更明确：不是"有时算错"，是**确定性原样返回输入值**。

**实测 4/4 全部原样返回**：

| 调用 | `units` 返回 | 正确答案 | 是否为输入值 |
|---|---:|---:|---|
| `{1000, 'kg/m^3', 'g/cm^3'}` | **1000** | 1 | ★ 原样 |
| `{7, 'm^2/s', 'cm^2/s'}` | **7** | 70,000 | ★ 原样 |
| `{5, 'W/m^2', 'kW/m^2'}` | **5** | 0.005 | ★ 原样 |
| `{3, 'mol/L', 'mol/m^3'}` | **3** | 3,000 | ★ 原样 |
| `{100, 'km/h', 'm/s'}` | 27.7778 | 27.7778 | ✓ 正确（单量纲） |

**规律**：单量纲换算正确，**复合单位一律返回输入值**，且 `ok=true` 无任何警告。

**更严重的是路径间不一致**：

```
units:    1000 kg/m^3 → g/cm^3  =  1000     ← 错 1000 倍
evaluate: 1000 kg/m^3 → g/cm^3  =  1        ← 正确
```

**同一个工具，两条路径给出相差 1000 倍的结果。**

这个缺陷的危害在于：`units` 的输出**看起来完全正常**（`1000` 是个合法数字），调用方无从发现。而密度、通量、摩尔浓度正是反馈包所说"47% 硬伤与单位相关"的高频场景。

**修法建议**：复合单位查表失败时**报 `unsupported_compound_unit`**，hint 指向 `evaluate`（`evaluate` 的路径是正确的）。

### 10.2 测试有效性评估

测试数量充足，但本评估发现一个**结构性盲区**：

**现有测试无法捕获静默失败。** 因为：

```

静默失败的表现是「算出来了，但没有意义」
```

例如 `world{planetMass:-1}` 会算出 `-1.00 倍重力`——这是一次**完全正确的计算**，任何断言期望值的测试都会通过。

| 交叉一致性 | 同一物理量用两条路径算，断言相等 | 路径间不一致（如 `units` vs `evaluate`） |
| 契约稳定性 | 断言同一 operation 两次调用的字段集一致 | `succeeded` 时有时无 |

## 十二、方法论反思：为什么这些缺陷能长期存在

这一节回答一个比"有哪些缺陷"更重要的问题：**为什么一个 54,656 行、5,921 项测试全绿的系统，会同时存在 50% 的静默失败率？**

### 10.1 三个结构性原因

#### 原因一：测试断言的形态与缺陷的形态不匹配

现有 5,921 项断言，绝大多数形如：

```js
assert('X 等于 Y', calc(...) === expected)
```

而静默失败的形态是：

```js
calc(荒谬输入) → 返回一个"计算正确但物理无意义"的值
```

**这类缺陷不会让任何"等于期望值"的断言失败。** 因为计算过程本身没错——错的是"允许这个输入进来"。

实测：`world{planetMass:-1}` 返回 `-1.00 倍重力`。这是一次**完全正确的乘法**。任何断言 `surfaceGravity(-1, R)` 等于某个值的测试都会通过。

**这是测试数量的假象**：断言多，但覆盖的是"算得对不对"，不是"该不该算"。

#### 原因二：参数校验修在了错误的层次

代码里的参数校验（`findUnknownArguments`）解决的是**拼写错误**：

```
planetMasss → 报错 ✓
```

但真实世界的错误形态是**语义不匹配**：

```
world{unitFrom:'里'} → 静默接受，什么都没发生
```

拼写错误是**低频、显眼**的；语义不匹配是**高频、隐蔽**的。校验只覆盖了前者。

#### 原因三：演化路径决定了盲区的位置

从代码结构可推断演化顺序：

```
公式库（解决"算什么"）→ 推演链（解决"怎么串"）→ 判定层（解决"结论是什么"）→ 砍 UI（解决"给谁看"）
```

每一步都在**往外扩**，没有一步回头问：**入口处什么样？**

于是入口层成了"最后才被想到"的部分，而它恰好是用户接触的第一个环节。

### 11.2 这个模式的可移植结论

| 观察 | 可复用的判据 |
|---|---|
| 测试多但覆盖的是"算得对" | 高质量测试必须包含**该拒绝的输入被拒绝** |
| 校验存在但粒度错 | 校验的**作用域**比有无更重要 |
| 静默失败比崩溃多 | **"没有报错"不等于"没有问题"** |
| **功能实现了但 AI 不知道** | **"实现了"不等于"能被用上"** —— 可发现性是一等公民 |

**第 3、4 条是本报告最想让读者带走的两句。**

### 11.3 「可发现性」为什么值得单独讨论

本项目有一个鲜明的反差：

```
代码侧：54,656 行 / 665 条公式 / 31 个 operation / 29 个 derivation 子命令
使用侧：真实任务里用到 12 条公式 / 约 10 个 operation / 约 5 个子命令
```

**不是功能不够，是入口太窄。**

这和一个更普遍的现象同构：**系统的能力上限由最窄的入口决定，而不是由最强的内部实现决定。**

38 个已实现但 AI 找不到的 derivation 子命令与公式，其价值等于 0——**除非有人先知道它们存在。**

修复成本对比：

| 做法 | 成本 | 收益 |
|---|---|---|
| 再写 5 个新子命令 | 约 5 天 | +5 个能力（可能同样无人发现） |
| 让 29 个既有子命令可被发现 | **2.2 天** | **+29 个能力真正可用** |

**这是本报告认为性价比最高的单项改进。**

## 十三、结论

### 11.1 总体判断

`dsh-math-calculator` 是一个**内核质量高、外壳质量低**的系统。

**内核（A）**：算术正确性在 1,760 次真实调用中未发现算错；公式库 665 条全部可求值；符号代数、ODE、统计分布等子系统实现完整。

**外壳（D）**：31 个 operation 里 13 个从未被使用；参数校验挫在错误维度；50% 的荒谬输入静默返回成功；状态管理子系统从未真正工作。

### 11.2 最关键的一条

> **这个工具最需要的不是新功能，而是「让已有功能不被静默绕过」。**

四条 P0 各需半天，合计 2.5 天，可消除：
- 参数静默忽略的全部症状
- 物理上不可能的 `world` 结果
- 常数污染
- 单位换算错 1000 倍

相比之下，反馈包主推的 `entity`（3–4 周）解决的是一个**尚未验证频率**的需求。

### 11.3 对反馈包的最终评价

| 维度 | 评分 | 说明 |
|---|---|---|
| 证据质量 | A | 每条可复现 |
| 诚实度 | A | 主动撤销误判 |
| 结论可用性 | **C** | 3 处内部矛盾未调和，优先级需重排 |
| 前瞻性 | B | 准确指出"算一个数 vs 算一张表"的结构问题 |
