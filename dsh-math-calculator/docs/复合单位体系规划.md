# 复合单位体系规划

> 用户指示（2026-11-12）：**不要写一种就修一种**，而是先把常见复合单位**做全**，
> 再慢慢加冷门的。并指出：复合单位这么普遍，开源社区一定有成熟实现。
>
> 本文只做规划与选型结论，**不开工**。

## 一、现状：补丁式修复已经证明无效

实测三种写法：

```
kg/m^3  → g/cm^3    ✓ 可用（走 mathjs）
kg/m3   → g/cm3     ✓ 可用（走 mathjs）
kg/m³   → g/cm³     ✗ 不认识单位「kg/m³」   ← 中文设定里最常用的写法
```

根因：`isCompound` 只认 `/·*`，上标 `³` 不在其中；而 `findUnit` 查表也查不到。
**每发现一种写法就补一个分支，永远补不完**——这正是用户说的「写一种修一种」。

### 1.1 已经踩过的坑（说明为什么必须换思路）

| 时间 | 修了什么 | 结果 |
|---|---|---|
| 早期 | `1000 kg/m³` 返回输入值 1000（静默错值） | 改走 mathjs 后变成 1 ✓ |
| 中期 | `isCompound` 放宽到含逗号/上标 | **误伤** `sr`/`公顷`/`平方米`/`deg^2`，4 个套件红 |
| 现在 | 收紧到只认 `/·*` | 上标写法又不认了 |

**三次都只修了症状。** 问题的本质是：本项目的单位表是**自建的扁平表**
（462 个标量单位 + 手写 compound 判定），而复合单位需要的是
**量纲代数**（exponent vector）+ **词法解析器**。

## 二、开源选型：三个候选的实地核查

### 候选 A：`@lhncbc/ucum-lhc`（**推荐**）

| 项 | 实测值 |
|---|---|
| 版本 | **8.0.1**（23 天前更新，61 个版本） |
| 周下载 | **269,411** |
| 维护方 | **美国国立医学图书馆（NLM）Lister Hill 中心** |
| 许可 | SEE LICENSE IN LICENSE.md（需核实是否为 MIT 兼容） |
| 依赖 | 9 个 |
| 标准 | UCUM（Regenstrief Institute 制定，医疗与科学界公认） |

**能力**：

```
validateUnitString(uStr, suggest)     ← 校验并可给「你是不是想写 X」建议
convertUnitTo(from, val, to, opts)    ← 带完整失败码
convertToBaseUnits(from, val)         ← 转成基本单位的指数向量
commensurablesList(from, categories)  ← 列出所有可换算单位
checkSynonyms(term)                   ← 同义词搜索（如 pound → 5 种磅）
```

**关键价值**：

- **通过 UCUM 官方功能测试**（仅四舍五入差异）
- **± 内置错误诊断**：缺括号、缺乘号、拼错，都能报出来并给建议
- **分子量/电荷参数**：支持 mass ↔ mole ↔ equivalents（本项目的 `mol/L` 正需要）
- **不四舍五入**（明确的设计选择：早舍入会丢精度）——与本项目的精度原则一致

### 候选 B：`@atomic-ehr/ucum`

| 项 | 实测值 |
|---|---|
| 版本 | 0.2.5（**一年前发布**） |
| 周下载 | 2,826 |
| 依赖 | **0 个** |
| 许可 | **MIT** |
| 标准 | UCUM 2.1 |

**能力**：`validate` / `convert` / `quantity` / 加减乘除 / `info`（返回量纲向量）/ 特殊单位（温度/对数/角度/百分比）

**优势**：零依赖、MIT、TypeScript 原生、API 更现代（`ucum.quantity(10,'N')` 直接做算术）

**劣势**：0.2.5 版本号 + 一年未更新 + 下载量只有 A 的 1%，**成熟度远不如 A**

### 候选 C：`mathjs`（已在使用）

本项目已经在用 mathjs，它本身的单位系统支持 `kg/m^3` 这类写法。

**局限**：mathjs 的单位表是**英文为中心**的，中文单位（里/丈/亩/时辰）需要本项目
自己维护 —— 而现在的问题是**两套单位表并存**（mathjs 的 + 本项目的 462 条）。

### 候选 D：`convert-units` / `js-quantities`

`convert-units`（v2.3.4）只做**预定义类别**之间的转换（长度/质量/温度…），
不支持任意复合表达式。<br>
`js-quantities` 支持复合单位但已多年未更新，且同样是英文中心。

## 三、我的选型判断

**分三层，各用各的：**

```
第 1 层：词法解析       ← 用 UCUM 库（把 "kg/m³" 解析成 (kg)^1 · (m)^-3）
第 2 层：中文单位       ← 保留本项目自建表（462 条），但改成量纲向量表示
第 3 层：数值计算       ← 继续用 mathjs / BigNumber（精度与符号能力不能丢）
```

**为什么不整体换成 UCUM 库**：

本项目有 462 条中文单位（里/丈/亩/时辰/贯/石…），UCUM 里**没有这些**。
UCUM 是国际科学标准，不负责中国古制单位。所以：

```
UCUM 库   负责「复合表达式的解析与量纲代数」  ← 这是它最强的地方
本项目表  负责「中文单位的存在与其换算因子」   ← 这是 UCUM 没有的
```

**两者用「量纲向量」对接**：中文单位登记时声明自己的量纲向量
（`里` → `{L:1}`、`亩` → `{L:2}`、`时辰` → `{T:1}`），于是中文单位
自动参与复合表达式运算，不需要为每个组合再写一条规则。

## 四、要预先做全的常见复合单位（不是补丁，是清单）

### 4.1 量纲代数层（先做这个，一次解决 90%）

```
① 解析        把 "kg/m³" "N·m" "mol/(L·s)" "W/m²K" 解析成指数向量
② 归一        所有单位 → 基本量纲向量 {M, L, T, I, Θ, N, J}
③ 运算        加减要求量纲相同；乘除时指数相加
④ 输出        反查最合适的单位组合（如 J/s → W）
```

**上标、^、** 三种写法都要认**：

```
1 kg/m³ ≡ 1 kg/m3 ≡ 1 kg/m^3      ← 同一物理量，三种输入都该给同一答案
```

### 4.3 中文复合单位的特殊写法

这是 UCUM 库**不管**、必须本项目支持的部分：

```
吨/立方米     吨每立方米    吨每立方
公斤/公顷     kg/亩
立方米每秒    立方米每秒
千瓦时        度（= kWh）
公里每小时    km/h
焦每千克      J/kg
```

**判据**：中文以「每」为主要连接词，还有「每秒/每平方米」这类后缀形式。
需要在解析前做**中文→符号**的归一（这一步本项目已有雏形，但是零散的）。

## 五、实施顺序（若开工）

| 步骤 | 内容 | 成本 | 为什么这个顺序 |
|---|---|---|---|
| **1** | 引入量纲向量层（`{M,L,T,I,Θ,N,J}`） | 1.5 天 | 一次解决「上标/^/** 三种写法」与所有复合运算 |
| **2** | 中文单位补量纲声明（462 条逐条标） | 1 天 | 让中文单位进入量纲代数，此后自动支持任意组合 |
| **3** | 用 UCUM 库做词法解析与校验 | 1 天 | 直接得到「你是不是想写 X」的诊断能力 |
| **4** | 4.2 清单逐类验证 | 1 天 | 每类至少 3 个真实算例 |
| **5** | 冷门单位渐进补充 | 持续 | 用户明确「再慢慢加」 |

**合计约 4.5 天**（不含第 5 步的持续补充）。

## 六、必须守住的边界

```
✗ 不整体换成 UCUM 库          —— 它没有 462 条中文单位
✗ 不丢掉 mathjs 的符号与精度   —— 那是本项目立身之本
✗ 不为每种组合写一条规则       —— 那正是「写一种修一种」的老路
✓ 用「量纲向量」做唯一中介     —— 所有单位都转成指数向量，运算只在向量上做
```

## 七、一处需先确认

**UCUM 库的许可**：`@lhncbc/ucum-lhc` 写的是「SEE LICENSE IN LICENSE.md」，
不是直接的 MIT。开工前必须核实它是否允许本项目（MIT）使用。
`@atomic-ehr/ucum` 是明确的 MIT，但成熟度差很多。

**建议**：若 `ucum-lhc` 许可不兼容，退而用 `@atomic-ehr/ucum` 的
**解析器部分**（零依赖、MIT），自己补中文单位表 —— 因为它有
`parseUnit` / `toCanonicalForm` 两个直接可用的导出。
