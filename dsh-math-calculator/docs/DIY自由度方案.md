# 公式库覆盖度评估的核实结论，与「DIY 自由度」方案

> 针对 `实践文档/公式库覆盖度评估与改进建议.md`（2026-11-08）。
> 本文只做分析与方案设计，**不含代码改动**。
> 所有结论均以 2.3.0 实测为准，逐条可复现。

---

## 一、核实结果：文档哪几条站得住

| # | 文档主张 | 核实 | 判定 |
|---|---|---|---|
| 1 | 公式库 471 条，生物学 31 条 | biology/physiology 20 + biology/ecology 11 = 31 | **准确** |
| 2 | 缺 12 条公式，缺口率 55% | 见第二节：其中 6 条只是四则运算 | **夸大** |
| 3 | 实际只用 2/471 = 0.4% | 该项目的调用统计属实 | **数据真，结论过强** |
| 4 | `metabolic_generic` 要自己填 k 和 exponent，等于没给公式 | 实测 `k=70`、`exponent=0.75` **都有默认值**，只需填 `mass` | **误判** |
| 5 | `unitFrom/unitTo` 不参与计算 | **2.3.0 已修复**：`V:324375, unitFrom:'L'` 正确缩小 1000 倍 | **已过时** |
| 6 | 参数多是地球人类标定，量级不匹配 | 属实。`oxygen_depletion` 的 `consumption=0.0003 m³/min` 确为成人基准 | **准确且关键** |
| 7 | 中文参数名不支持 | 属实（作用域限制），但报错现已点名可用参数 | **准确（设计取舍）** |
| 8 | 长期建议：场景预设 / 可变系数 / 单位体系 | 方向对 | **有价值** |

### 值得单独表扬的一条

文档第 48 行说的「**公式多为地球人类标定，参数量级完全不同**」，是整份文档里
**最有价值的一句**——它比「缺 12 条」重要得多。

因为缺的公式可以补，而「参数标定不匹配」是**认知层面的问题**：作者看到
`oxygen_depletion` 有 `consumption=0.0003` 这个数，会以为公式只适用于人，
而不知道该参数本来就可以被 overrides 改。这是**可发现性**问题，不是能力问题。

## 二、12 条「缺口」逐条核查：只有一半真需要公式库

我把文档列表里的每一条都用 `evaluate` 实跑了一遍，结果全部一次通过：

| 文档说「缺」的 | 实际一行 evaluate | 结果 |
|---|---|---|
| 换气极限时间 | `324375 L / 20 L/min / 60` | 4.505 h ✓ |
| 摄食量与储能 | `47 * 60 * 1000 * 6.212 * 0.8 / 1e6` | 14.014 PJ ✓ |
| 质量预算加总 | `610+2000+2100+1500+175+800+1800` | 8985 ✓ |
| 步行能耗 CoT | `6.4e6 / (3200 * 24000)` | 0.0833 J/(kg·m) ✓ |
| 代谢抑制比 | `20 / 841 * 100` | 2.378% ✓ |
| 耗氧率换算 | `10000e6 MJ / 21100 kJ/L / 1440` | 329.12 L/min ✓ |
| 磷虾热值反算 | `(0.246*39.5 + 0.49*23.6 + 0.025*17.6) * 0.286` | 6.2122 ✓ |
| 鳃膜供氧能力 | `600000 * 6.3 * 0.8 / 1000` | 3024 L/min ✓ |

**这 8 条一条都不该进公式库。**

公式库的价值是**记住非平凡的物理关系与行业系数**（`W = b·h²/6`、`BMR = k·M^0.75`），
不是替人做四则运算。把这些做成公式条目只会：

- 增加 471 → 479 的认知负担，检索更难命中
- 每条都要写参数说明、单位、适用域，而它们没有适用域
- 真正的通用性（任意单位、任意量级）反而被固定参数名限制住

**真正值得做公式的只有 3 条**（有非平凡结构）：

| 候选 | 为什么它不是四则运算 |
|---|---|
| `gill_oxygen_limitation`（GOL 鳃氧限制） | 有多参数耦合与水-气两相氧分压差，不是单个乘法 |
| `metabolic_suppression_range`（潜水哺乳动物代谢抑制） | 核心是「20-40% 区间 + 体重标度」的外部锚点，价值在**区间判断**而非算式 |
| `krill_energy_density`（磷虾热值加权） | 三元组分加权 + 含水率修正，是物种相关的经验组合 |

其余建议（`filter_feeding_efficiency`、`mass_budget_closure`、`food_energy_intake`、
`giant_organism_oxygen_store`）**不建议做成内置公式**，理由见第四节：它们应该由用户自己攒。

## 三、真正的根因：DIY 能力早已存在，但没人知道怎么用

这是本次核实最重要的发现。文档说「公式库几乎未被使用」，并归因于「条数不够」。
但实测发现：**工具早就提供了三层 DIY 能力，且全部工作正常**。

### 3.1 三层 DIY 现状（实测）

| 层 | 能力 | 实测结果 |
|---|---|---|
| **L1 常数** | `workspaceVariables` + `useWorkspaceVariables` | 存入 `{O2_ENERGY:21100, KRILL_CV:6.212, OX_CONV:0.8}`，随后 `10000e6 / O2_ENERGY / 1440` → **329.12** ✓ |
| **L2 本工作区公式** | `formula-table` + `tableAction:"add"` | 加入「鳃膜供氧」自定义公式 → 公式数 471 → **472**，可直接调用 ✓，且 `formulas query="鳃"` **能检索到** ✓ |
| **L3 跨工作区公式包** | `formula-table` + `global-add`（存 `formula-packs/global.json`） | 文件级持久化，所有工作区共享，可被另一个 AI 读懂与审查 |
| **覆盖内置** | `tableAction:"override"` | 把 `kleiber` 的 `B0` 改成 30 → 生效 ✓，`show` 显示「被覆盖: 1 条」✓ |

**结论：文档提的「中期建议——增加专用公式」，其中 4 条用 L2 层用户自己就能加；**
**「长期建议——场景预设」，用 L1（常数）+ L3（公式包）也能拼出来。**

### 3.2 那为什么用不起来？三个摩擦点

**摩擦点 ①：字段名不一致，必然撞坑（我自己撞了两次）**

```
内置公式定义用    expr:        { id, name, expr: 'a*b', params: {...} }
自定义公式入参用  expression:  { customFormula: { id, name, expression: 'a*b' } }
```

我第一次按内置的字段名写 `expr`，报 `customFormula.expression 必须是非空字符串`；
改对才成功。**这是个纯粹的命名不一致，没有任何理由**，而它会让每一个
「照着内置公式的写法去加自己的」人卡住。

**摩擦点 ②：内置公式的必填参数太多**

```
kleiber    B0=必填  m0=必填  m=必填    ← 只想问「9e6 kg 的代谢率」也要填三个
```

而 `B0=1000 W`、`m0=1 kg` 是**人类代谢标定的常识值**，完全该给默认值。
只给 `m` 却报「缺少 B0, m0」，会让人以为公式不能用——这很可能就是文档作者
「曾试 formula kleiber」失败的真实原因。

**摩擦点 ③：help 里对 L2/L3 只有一句话，零示例**

`helpTopic:"formula"` 关于自定义公式的全部内容是：

> `formula-table` 两级扩展：工作区临时公式（覆盖/自定义/停用）+ 全局公式包

没有字段名、没有 params 写法、没有一条可照抄的 JSON。用户不知道「自定义」
该传什么形状的对象——于是放弃，回去手写 evaluate。

## 四、方案：把 DIY 做成「一等公民」

设计原则：**不增加新能力，而是把已有能力做成可发现、可照抄、不撞坑、可带走。**

### 4.1 目标形态

让用户的**真实工作流**变成这样（当前需要摸索，改造后可照抄）：

```
① 第一次算「换气极限」：
   evaluate  "324375 L / 20 L/min / 60"      → 4.505 h
   顺手登记常数：workspace set vars {O2_STORE:324375, O2_RATE:20}

② 第二次算同类问题（换个数）：
   evaluate  "O2_STORE / O2_RATE / 60"         ← 只改一个数

③ 发现这个式子要反复用 → 升成公式（L2）：
   formula-table add { id:"vent_limit", expression:"store / rate / 60",
                       params:{ store:{desc:"氧储 L"}, rate:{desc:"耗氧 L/min"} },
                       unit:"h", name:"换气极限时间" }

④ 这套设定里的公式攒多了 → 导出成公式包（L3），换个项目直接导入
```

这条路径现在**每一步都能走**，但②③④三步都需要猜字段名。

### 4.2 改造清单（按优先级）

#### P0：修掉必然撞的坑（低成本、高确定性）

**P0-1 统一字段名**

- 自定义公式的 `customFormula` 同时接受 `expr` 与 `expression`，两者等价
- 报错文案改成列出**可用的字段名**，而不是只说「必须是非空字符串」
- 成本：一处解构 + 一处报错文案。风险：零（纯新增别名）

**P0-2 给内置公式补常识默认值**

这是「参数标定不匹配」这个真问题的**最便宜解法**：不改公式逻辑，只补默认值。

| 公式 | 现状 | 建议默认值 | 依据 |
|---|---|---|---|
| `kleiber` | B0/m0/m 全必填 | `B0=1000`、`m0=1` | 人类代谢标定：1 kg → 1000 W 是 Kleiber 式在该区间的常用取值 |
| `oxygen_depletion` | `consumption=0.0003` | 保持，但 **desc 里注明「成人基准，巨兽请按体重标度重算」** | 文档的痛点正是不知道这个数可以改 |
| `body_surface_area` | 已用 Du Bois | desc 补一句「超大体型外推会失真，>100 t 建议用几何包络」 | 文档第 18 行正是这个用法 |

**P0-3 help 给出可照抄的三层配方**

`helpTopic:"formula"` 增加一节「自己加公式」，内容是一段**完整可粘贴的 JSON**
（含 id / name / expression / params / unit），再加上下文三条经验：

- 只算一次 → `evaluate`；会反复用 → 升成自定义公式
- 参数名用英文；中文写在 `desc` 里（`desc` 会显示在参数表上）
- 自定义公式立刻能用 `formulas query="关键词"` 检索到（实测 verfied）

顺带把 `workspace` 节的 L1 用法与 `formula-table` 的 L2 用法**串成一条工作流**，
而不是分在两节各说一半。

#### P1：降低「攒公式」的摩擦（中成本）

**P1-1 `from-expression` 快捷式**：把一条算过的表达式直接升成公式

```
formula-table add { fromExpression:"store / rate / 60",
                    id:"vent_limit", name:"换气极限时间", unit:"h" }
```

- 工具自动从表达式里**提取变量名做参数**，每个参数 `desc` 留空待用户补
- 参数名必须合法标识符，提取时逐个校验；非法名（如 `O2_STORE` 里的大写）照收
- 收益：把「写四个字段」降成「写三个字段 + 抄一条表达式」
- 风险：自动提取的参数缺 desc，公式表里会出现无说明参数——但比「卡在字段名」好

**P1-2 导出 / 导入公式包**

- 已有 `global-add` 是**逐条**加的；补一个「把当前工作区所有自定义公式导出成文件」
  与「从文件一次导入」
- 用途：把某个世界观的公式集当**资产**带走、版本化、交给另一个 AI
- 这一步是「DIY 自由度」从「能用」变成「可积累」的关键

#### P2：场景预设（文档的长期建议，换个更省的实现）

文档建议 `preset="giant_marine_filter_feeder"` 自动填 9000 吨级默认参数。

**我的判断：不做内置 preset 表。** 理由：

1. 每个世界观的「巨兽」参数都不同，预设值必然错，而错得很隐蔽
2. 预设需要维护一张「物种 × 参数」表，那是另一个公式库
3. **用 L1 已经能实现同样的效果，且由用户自己定义**：

```
workspace set vars { MY_BEAST_MASS: 9e6, MY_BEAST_B0: 3000, MY_BEAST_K: 0.62 }
// 之后所有计算引用这些名字 —— 这就是「自定义 preset」，且它属于你的世界
```

所以 P2 真正该做的是：**让 L1 的常数能在公式 overrides 里直接用**。

现状：`overrides` 只认公式参数名与世界常数（g/c/G），**不认工作区变量**。
若能让 `overrides:{m: "MY_BEAST_MASS"}` 解析成工作区值，「预设」这件事就免费了。

这是本方案里**性价比最高的一处能力缺口**，值得单列。

### 4.3 明确不做的事

| 不做 | 理由 |
|---|---|
| 把 8 条四则运算做成公式 | 四则运算的正确归属是 `evaluate`；做成公式只增检索负担 |
| 内置「巨兽专用公式」一批 | 参数与场景太特殊，一批内置式必然大半用不上；L2 让用户自己攒更准 |
| 内置 preset 表（物种×参数） | 见 4.2 P2：预设值必然错，且 L1 已能覆盖这个需求 |
| 支持中文参数名 | 参数名要进 mathjs 作用域，中文会引入词法歧义（与单位名、量级词的边界）。报错点名可用参数名已足够 |
| `unit_system` 参数切换 | 2.3.0 已支持参数带单位（`V:"324375 L"`）与整批 `unitFrom`，再加一层 `unit_system` 是重复抽象 |

## 五、优先级与成本

| 项 | 收益 | 成本 | 风险 | 优先级 |
|---|---|---|---|---|
| P0-1 统一 `expr`/`expression` | 消除必然撞的坑 | 极小 | 零 | **最优先** |
| P0-3 help 补三层配方 | 让能力可发现 | 小（纯文档） | 零 | **最优先** |
| P0-2 补内置默认值 | 让「地表标定」不再挡住使用 | 小 | 低（改默认值会改变既有输出，需测试） | **高** |
| P2 工作区变量可用于 overrides | 让「自定义预设」免费 | 中 | 中（要处理解析与缓存指纹） | **高** |
| P1-1 fromExpression 快捷升格 | 降低攒公式摩擦 | 中 | 中（参数提取要校验） | 中 |
| P1-2 导出/导入公式包 | 让 DIY 成果可积累、可带走 | 中 | 低 | 中 |

**建议的落地顺序**：P0-1 → P0-3 → P2 → P0-2 → P1-1 → P1-2。

理由：前两项是「零风险且立刻见效」；P2 促成最大的一次体验跃迁；
P0-2 会改变既有输出（需配套测试），放到之后。

## 六、一句话总结

> 这份文档观察到的**现象**（公式库用不起来）是真的，
> 但它给的**诊断**（条数不够、需要更多内置公式）偏了。
>
> 真实原因是：**三层 DIY 能力早已齐备且可用，却没人知道怎么用** ——
> 一个字段名不一致、一批不必要的必填参数、help 里零示例，
> 三者叠加，就把用户推回了「手写 evaluate」。
>
> 所以这一轮该做的不是「补 12 条公式」，
> 而是**把「攒自己的公式与常数」做成可发现、可照抄、可带走的一等公民**。
