# 功能重复盘点与合并（2026-11-16）

> 用户要求：全量耦合、功能重复的合并或取舍，不要大量重复功能。

## 一、盘点（61 个 operation）

### 已合并（保留旧名，内部转发）

| 重复项 | 主入口 | 别名 | 说明 |
|---|---|---|---|
| 快速可行性判定 | `feasibility` + `quick:true` | `quick_feasible` | 同一套 claim 解析，只是完整版多跑约束 |
| 完整世界编排 | `world` + `profile:"full"` | `world-build` | 编排就是 world 画像 + 跨模块汇总 |
| 公式参数表 | `formulas` + `query:"table"` | `formula-table` | 同一份表，同一条读取路径 |

### 保留（分工不同，不是重复）

| 看起来像 | 实际分工 |
|---|---|
| `compare` vs `derivation compare` | 前者=方案对比（多方案取舍），后者=版本对比（归档两版）——**同名不同义**，文档已注明 |

### 复核后判定为「保留」（第二轮决定）

| 项 | 复核结论 |
|---|---|
| `custom` vs `constants` | **保留**：custom 有「自定义表达式 + 量纲校验 + 工作区存」，constants 只有常数表——输入契约不同 |
| `scaling` vs `formula square_cube_law` | **保留**：scaling 给「面积×s²、体积×s³」的**全套倍数与判定**，公式只给一个比值——输出侧重不同 |
| `world_state` vs `data` | **仍有合并价值**（设定库可成为 data 的 kind:"setting"），但需一次性数据迁移，单独立项 |

## 二、合并的方式（统一规则）

**旧名全部保留为别名**，内部转发到主入口：

    if (operation === 'quick_feasible') return dispatchNew('feasibility', { ...args, quick: true })
    if (operation === 'world-build') return dispatchNew('world', { ...args, profile: 'full' })

好处：既有调用零破坏；AI 只需记主入口。

## 三、踩到的坑

**别名互相转发 → 无限递归**：

    formula-table → formulas(query:table) → formula-table → …

第一次同时加了双向转发，直接 `Maximum call stack size exceeded`。
规则：**只允许单向**（旧名 → 主入口），主入口不得转发回旧名。
## 四、第二轮复核（2026-11-16 晚）

用户要求「全量耦合、重复的合并或取舍」。第二轮把剩余三项逐个查了实现：

**① custom 不能并入 constants**

```
constants：常数表（name→value），只读/覆盖
custom：  自定义表达式 + 量纲校验（expectedDimension）+ 工作区持久化
```

`custom` 的输入契约是「表达式 + 期望量纲」，constants 是「名字 + 数值」——**不是同一件事**。

**② scaling 不能并入 formula**

```
scaling：from/to → 面积倍数 s²、体积倍数 s³、强度判定（一整套）
square_cube_law：s → 输出一个比值 s（单条）
```

scaling 的输出是**判定 + 倍数表**，公式是**一个数**。硬合并会让调用方拿不到判定。

**③ world_state 确实该并入 data**，但要一次性迁移既有 `world-state.json` 里已登记的设定条目——单独立项，不混在合并里做。

## 五、结论：真正该合并的只有 3 组

其余「看起来像」的都是**输入契约不同**或**输出侧重不同**。这本身是取舍结论：
合并的收益是「少记入口」，代价是「要么丢判定、要么丢契约」——不值得。
